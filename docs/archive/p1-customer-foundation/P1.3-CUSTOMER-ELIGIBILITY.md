# P1.3 Customer Limits, Eligibility & Product Enrollment

## Scope

P1.3 adds the internal customer eligibility, limits, product enrollment, operating permission, and restriction domain on top of the completed P1.2 onboarding workflow.

This milestone does not create wallets, post ledger journals, execute transfers, process deposits or withdrawals, execute payments, change balances, authenticate users, authorize users, call external services, or send notifications.

## Domain entities

| Entity                        | Purpose                                                                                                 |
| ----------------------------- | ------------------------------------------------------------------------------------------------------- |
| `CustomerEligibility`         | Current eligibility status and its onboarding evidence reference.                                       |
| `CustomerLimitProfile`        | Current customer transaction and balance limit configuration. Amounts are stored as minor-unit strings. |
| `CustomerProductEnrollment`   | Customer enrollment state for one normalized product identifier.                                        |
| `CustomerOperatingPermission` | One enabled or disabled permission record per permission type.                                          |
| `CustomerRestriction`         | One active or inactive restriction record per restriction type.                                         |

All entities use UUID identifiers, timestamps, soft deletion, and TypeORM optimistic version columns. PostgreSQL partial unique indexes exclude soft-deleted rows.

## Eligibility lifecycle

| Current      | Allowed next statuses                            |
| ------------ | ------------------------------------------------ |
| `PENDING`    | `ELIGIBLE`, `INELIGIBLE`, `SUSPENDED`, `REVOKED` |
| `ELIGIBLE`   | `INELIGIBLE`, `SUSPENDED`, `REVOKED`             |
| `INELIGIBLE` | `PENDING`, `SUSPENDED`, `REVOKED`                |
| `SUSPENDED`  | `PENDING`, `ELIGIBLE`, `INELIGIBLE`, `REVOKED`   |
| `REVOKED`    | None                                             |

An eligibility record is created as `PENDING` by default. `ELIGIBLE` may only be created or reached when a non-deleted P1.2 onboarding record for the customer is `COMPLETED`. An active `BLACKLISTED` restriction blocks both creation and transition to `ELIGIBLE`.

Only one non-deleted eligibility record exists per customer. Eligibility status changes use an optional expected version and are audited.

## Product enrollment lifecycle

| Current     | Allowed next statuses           |
| ----------- | ------------------------------- |
| `PENDING`   | `ACTIVE`, `SUSPENDED`, `CLOSED` |
| `ACTIVE`    | `SUSPENDED`, `CLOSED`           |
| `SUSPENDED` | `ACTIVE`, `CLOSED`              |
| `CLOSED`    | None                            |

An enrollment is normalized to a lowercase product identifier. Only an `ELIGIBLE` customer may create or transition an enrollment to `ACTIVE`. An active `FROZEN` restriction blocks that operation. One non-deleted enrollment is allowed per customer and product.

## Limits

A customer has one non-deleted active limit profile. The profile contains:

- `currency`
- `dailyTransactionCount`
- `dailyTransactionAmountMinor`
- `singleTransactionAmountMinor`
- `monthlyTransactionAmountMinor`
- `walletBalanceMinor`

Limit profiles are configuration only. P1.3 does not evaluate, reserve, deduct, or otherwise apply limits to financial transactions.

## Permissions and restrictions

Permission records contain a permission `type`, an `enabled` flag, and an optional reason. Restriction records contain a restriction `type`, an `isActive` flag, and an optional reason.

The following restrictions affect operating status:

- `BLACKLISTED` produces `BLACKLISTED` operating status and blocks eligibility approval.
- `FROZEN` produces `FROZEN` operating status and blocks new active enrollments.
- `LIMITED` and `MANUAL_REVIEW` produce `RESTRICTED` operating status.
- `NONE` is retained as a record but is not an active blocking restriction.

P1.3 exposes create and read APIs for permission and restriction records. There is no hard-delete operation and no later external screening integration.

## Operating status

`GET /api/v1/customers/:id/operating-status` returns:

- `status`: `OPERABLE`, `INELIGIBLE`, `RESTRICTED`, `SUSPENDED`, `FROZEN`, `BLACKLISTED`, or `REVOKED`.
- `canOperate`: true only when status is `OPERABLE`.
- The current eligibility status.
- Active restriction types.
- Active enrollment products.
- Enabled permission types.
- Blocking reasons.

The response is a decision view only. It does not execute or authorize any financial operation.

## APIs

All routes use the global `/api/v1` prefix.

| Method  | Route                                              | Purpose                                                        |
| ------- | -------------------------------------------------- | -------------------------------------------------------------- |
| `POST`  | `/customers/:id/eligibility`                       | Create the current eligibility record.                         |
| `GET`   | `/customers/:id/eligibility`                       | Read the current eligibility record.                           |
| `PATCH` | `/customers/:id/eligibility`                       | Apply a validated eligibility transition or update its reason. |
| `POST`  | `/customers/:id/limit-profile`                     | Create the current limit profile.                              |
| `GET`   | `/customers/:id/limit-profile`                     | Read the current limit profile.                                |
| `PATCH` | `/customers/:id/limit-profile`                     | Update limit profile fields.                                   |
| `POST`  | `/customers/:id/product-enrollment`                | Create a product enrollment.                                   |
| `GET`   | `/customers/:id/product-enrollments`               | List product enrollments.                                      |
| `PATCH` | `/customers/:id/product-enrollments/:enrollmentId` | Apply a validated enrollment transition.                       |
| `POST`  | `/customers/:id/permission`                        | Create one permission record.                                  |
| `GET`   | `/customers/:id/permissions`                       | List permission records.                                       |
| `POST`  | `/customers/:id/restriction`                       | Create one restriction record.                                 |
| `GET`   | `/customers/:id/restrictions`                      | List restriction records.                                      |
| `GET`   | `/customers/:id/operating-status`                  | Calculate the operating-status decision view.                  |

## Audit behavior

The existing immutable `AuditService` is called in the same TypeORM transaction as each create or update mutation. Audit entity types are:

- `CUSTOMER_ELIGIBILITY`
- `CUSTOMER_LIMIT_PROFILE`
- `CUSTOMER_PRODUCT_ENROLLMENT`
- `CUSTOMER_OPERATING_PERMISSION`
- `CUSTOMER_RESTRICTION`

No audit records are generated by the read-only operating-status calculation.

## PowerShell manual verification

### Setup

Run from the repository root:

```powershell
$ErrorActionPreference = 'Stop'
$BaseUrl = 'http://localhost:3000/api/v1'
$Headers = @{ 'Content-Type' = 'application/json' }

npm ci
npm run migration:run
npm run start:dev
```

Use a second PowerShell window for API requests. Complete the P1.1 and P1.2 manual verification first, or use an existing `$CustomerId` whose onboarding status is `COMPLETED`.

### 1. Confirm completed onboarding

```powershell
$Onboarding = Invoke-RestMethod `
  -Method Get `
  -Uri "$BaseUrl/customers/$CustomerId/onboarding"

$Onboarding | ConvertTo-Json -Depth 8
if ($Onboarding.status -ne 'COMPLETED') {
  throw 'Customer onboarding must be COMPLETED before eligibility can become ELIGIBLE'
}
```

### 2. Create and approve eligibility

```powershell
$EligibilityBody = @{
  status = 'PENDING'

  actor = 'eligibility-ops'
} | ConvertTo-Json

  -Headers $Headers `
  -Body $EligibilityBody
```

```powershell
$EligibleBody = @{
```
