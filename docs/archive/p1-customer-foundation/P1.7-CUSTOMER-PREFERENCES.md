# P1.7 Customer Preferences & Notification Settings

## Scope

P1.7 adds an internal customer preference profile that stores language, theme, notification-channel settings, and security settings.

This milestone does not send notifications, integrate email, SMS, or push providers, authenticate users, authorize users, execute financial operations, or invoke external services.

## Domain model

`CustomerPreference` is the single active profile owned by a customer. The profile embeds four typed preference value objects:

| Value object             | Stored settings                                                                         |
| ------------------------ | --------------------------------------------------------------------------------------- |
| `LanguagePreference`     | Customer language.                                                                      |
| `ThemePreference`        | `SYSTEM`, `LIGHT`, or `DARK`.                                                           |
| `NotificationPreference` | Email, SMS, push, and in-app channel booleans.                                          |
| `SecurityPreference`     | Login alerts, transaction alerts, device-registration alerts, and biometric permission. |

`PreferenceHistory` is an append-only record of profile creation and updates. The value objects are embedded in `customer_preferences`; they do not create separate tables.

## Supported values

### Languages

- `EN`
- `FR`
- `HA`
- `IG`
- `YO`

### Themes

- `SYSTEM`
- `LIGHT`
- `DARK`

### Notification channels

- `EMAIL`
- `SMS`
- `PUSH`
- `IN_APP`

Notification channels are represented by the `email`, `sms`, `push`, and `inApp` boolean fields in the API.

### Security settings

- `LOGIN_ALERTS`
- `TRANSACTION_ALERTS`
- `DEVICE_REGISTRATION_ALERTS`
- `BIOMETRIC_ALLOWED`

Security settings are represented by the `loginAlerts`, `transactionAlerts`, `deviceRegistrationAlerts`, and `biometricAllowed` boolean fields in the API.

## Rules

- A customer must exist before a preference profile is created.
- Only one non-deleted active profile exists per customer.
- A soft-deleted profile does not block creation of a replacement profile.
- Preferences are versioned with TypeORM optimistic locking.
- Updates are partial and preserve unspecified nested settings.
- Preference history is append-only.
- Every profile or history mutation creates an immutable audit event.
- Preference values do not cause notification delivery or financial activity.

## DTO payloads

### Create preferences

```json
{
  "language": "EN",
  "theme": "SYSTEM",
  "notifications": {
    "email": true,
    "sms": false,
    "push": true,
    "inApp": true
  },
  "security": {
    "loginAlerts": true,
    "transactionAlerts": true,
    "deviceRegistrationAlerts": true,
    "biometricAllowed": false
  },
  "actor": "preference-ops"
}
```

### Update preferences

```json
{
  "language": "YO",
  "theme": "DARK",
  "notifications": {
    "email": false
  },
  "security": {
    "biometricAllowed": true
  },
  "actor": "preference-ops"
}
```

Only supplied top-level and nested fields are changed. An optional `version` property can be supplied for optimistic-lock validation.

## APIs

All routes use the global `/api/v1` prefix.

| Method  | Route                                | Purpose                                         |
| ------- | ------------------------------------ | ----------------------------------------------- |
| `POST`  | `/customers/:id/preferences`         | Create the customer preference profile.         |
| `GET`   | `/customers/:id/preferences`         | Read the active preference profile.             |
| `PATCH` | `/customers/:id/preferences`         | Partially update the active preference profile. |
| `GET`   | `/customers/:id/preferences/history` | Read append-only preference history.            |

## Audit behavior

The existing immutable `AuditService` records:

- `CUSTOMER_PREFERENCE` `CREATED` events.
- `CUSTOMER_PREFERENCE` `UPDATED` events.
- `PREFERENCE_HISTORY` `CREATED` events.

Audit calls occur in the same TypeORM transaction as the preference or history write. Read endpoints create no audit events.

## Database migration

Migration `1785753600014-CreateCustomerPreferences.ts` creates:

- `customer_preferences`
- `preference_histories`

`customer_preferences` stores the embedded language, theme, notification, and security columns. It includes a soft-deletion-aware unique customer index, enum checks, timestamps, and an optimistic version column. Earlier migrations are unchanged. Production startup compatibility expects migration head `1785753600014 / CreateCustomerPreferences1785753600014`.

## PowerShell manual verification

### Setup

Run from the repository root:

```powershell
$ErrorActionPreference = 'Stop'
$BaseUrl = 'http://localhost:3000/api/v1'
$Headers = @{ 'Content-Type' = 'application/json' }

npm ci
npm run migration:run
npm run start:dev
```

Use a second PowerShell window and set `$CustomerId` to an existing customer UUID:

```powershell
$CustomerId = '<customer-uuid>'
```

### 1. Create the preference profile

```powershell
$PreferenceBody = @{
  language = 'EN'
  theme = 'SYSTEM'
  notifications = @{
    email = $true
    sms = $false
    push = $true
    inApp = $true
  }
  security = @{
    loginAlerts = $true
    transactionAlerts = $true
    deviceRegistrationAlerts = $true
    biometricAllowed = $false
  }
  actor = 'preference-ops'
} | ConvertTo-Json -Depth 8

$Preferences = Invoke-RestMethod `
  -Method Post `
  -Uri "$BaseUrl/customers/$CustomerId/preferences" `
  -Headers $Headers `
  -Body $PreferenceBody

$Preferences | ConvertTo-Json -Depth 8
$PreferenceId = $Preferences.id
```

Expected values:

- `language` is `EN`.
- `theme` is `SYSTEM`.
- `notifications.sms` is `false`.
- `security.biometricAllowed` is `false`.
- No email, SMS, push, or in-app notification is sent.

A second create request for the same customer must return `409`:

```powershell
try {
  Invoke-RestMethod `
    -Method Post `
    -Uri "$BaseUrl/customers/$CustomerId/preferences" `
    -Headers $Headers `
    -Body $PreferenceBody
  throw 'Duplicate preference profile unexpectedly succeeded'
} catch {
  $_.Exception.Response.StatusCode.value__
}
```

### 2. Read preferences

```powershell
Invoke-RestMethod `
  -Method Get `
  -Uri "$BaseUrl/customers/$CustomerId/preferences" | ConvertTo-Json -Depth 8
```

### 3. Partially update preferences

```powershell
$UpdateBody = @{
  language = 'YO'
  theme = 'DARK'
  notifications = @{
    email = $false
  }
  security = @{
    biometricAllowed = $true
  }
  actor = 'preference-ops'
} | ConvertTo-Json -Depth 8

$UpdatedPreferences = Invoke-RestMethod `
  -Method Patch `
  -Uri "$BaseUrl/customers/$CustomerId/preferences" `
  -Headers $Headers `
  -Body $UpdateBody

$UpdatedPreferences | ConvertTo-Json -Depth 8
```

Expected values:

- `language` is `YO`.
- `theme` is `DARK`.
- `notifications.email` is `false`.
- `notifications.sms`, `push`, and `inApp` retain their prior values.
- `security.biometricAllowed` is `true`.
- Unspecified security settings retain their prior values.
- `version` is returned by the API and changes after a persisted update.

### 4. Verify optimistic version validation

Use a deliberately stale version:

```powershell
$StaleUpdateBody = @{
  language = 'FR'
  version = 1
  actor = 'preference-ops'
} | ConvertTo-Json

try {
  Invoke-RestMethod `
    -Method Patch `
    -Uri "$BaseUrl/customers/$CustomerId/preferences" `
    -Headers $Headers `
    -Body $StaleUpdateBody
  throw 'Stale preference version unexpectedly succeeded'
} catch {
  $_.Exception.Response.StatusCode.value__
}
```

The request must return `409` after the profile version has advanced beyond `1`.

### 5. Read preference history

```powershell
$History = Invoke-RestMethod `
  -Method Get `
  -Uri "$BaseUrl/customers/$CustomerId/preferences/history"

$History | ConvertTo-Json -Depth 12
```

History must contain `CREATED` and `UPDATED` entries with previous and new preference values. History records are append-only.

### 8. Verify no notification or financial side effects

P1.7 stores preference state only. It does not send email, SMS, push, or in-app notifications and does not interact with wallets, balances, payments, transfers, ledger journals, or reconciliation.
