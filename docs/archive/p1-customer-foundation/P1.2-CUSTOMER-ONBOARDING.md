# P1.2 Customer Onboarding, Risk Profiling & Customer Lifecycle

## Scope

P1.2 adds the internal customer onboarding and lifecycle domain on top of P1.1. It provides:

- One active onboarding workflow per customer.
- Explicit onboarding lifecycle transitions.
- Versioned customer agreement evidence.
- One current customer risk profile.
- Required and optional onboarding tasks.
- Latest approval-decision history.
- Onboarding readiness evaluation.
- Immutable audit events for onboarding-domain mutations.

The module does not create wallets, post ledger journals, execute transfers, process deposits or withdrawals, call payment rails, call external KYC providers, authenticate users, authorize users, send notifications, or call external services.

## Domain entities

| Entity                     | Purpose                                                                                        |
| -------------------------- | ---------------------------------------------------------------------------------------------- |
| `CustomerOnboarding`       | Customer onboarding workflow, status, lifecycle timestamps, and optimistic version.            |
| `CustomerAgreement`        | Agreement version, required flag, acceptance state, acceptance timestamp, and accepting actor. |
| `CustomerRiskProfile`      | Current internal risk classification and assessment rationale.                                 |
| `CustomerOnboardingTask`   | Required or optional onboarding work item and completion state.                                |
| `CustomerApprovalDecision` | Approval workflow decision history with one latest decision.                                   |

All five entities use UUID identifiers, PostgreSQL persistence, timestamps, a soft-deletion column, and a TypeORM optimistic version column. Foreign keys reference the existing `customers` and the P1.2 onboarding workflow.

## Lifecycle rules

### Onboarding transitions

| Current           | Allowed next states           |
| ----------------- | ----------------------------- |
| `NOT_STARTED`     | `IN_PROGRESS`                 |
| `IN_PROGRESS`     | `AWAITING_REVIEW`, `REJECTED` |
| `AWAITING_REVIEW` | `APPROVED`, `REJECTED`        |
| `APPROVED`        | `COMPLETED`                   |
| `REJECTED`        | None                          |
| `COMPLETED`       | None                          |

An onboarding workflow is active while its status is `NOT_STARTED`, `IN_PROGRESS`, `AWAITING_REVIEW`, or `APPROVED`. Rejected and completed workflows are terminal and do not prevent a later workflow from being created. A partial unique index prevents more than one active workflow for a customer.

### Approval transitions

- A first decision may be `PENDING`, `APPROVED`, `REJECTED`, or `ESCALATED`.
- `PENDING` may become `APPROVED`, `REJECTED`, or `ESCALATED`.
- `ESCALATED` may become `PENDING`, `APPROVED`, or `REJECTED`.
- `APPROVED` and `REJECTED` are terminal.
- Repeating the latest decision is rejected as a duplicate.
- A new decision supersedes the previous latest decision and audits the supersession.

A `PROHIBITED` current risk profile cannot produce an `APPROVED` approval decision or move onboarding to `APPROVED`.

## Completion readiness

`GET /api/v1/customers/:id/onboarding-readiness` evaluates:

- Customer status is `ACTIVE`.
- An active or latest onboarding workflow exists and is not `REJECTED`.
- An active customer profile exists.
- At least one non-deleted address exists.
- At least one non-deleted identity document exists.
- At least one required agreement exists and every required agreement is accepted.
- At least one required task exists and every required task is `COMPLETED`.
- The current risk profile is not `PROHIBITED`.
- The onboarding status is `APPROVED` or `COMPLETED` for `READY` readiness.

The response includes `status`, `canComplete`, `missing`, and individual boolean checks. Completion is only permitted by the `APPROVED` to `COMPLETED` transition when `canComplete` is true.

## DTO payloads

The global validation pipe transforms DTOs, rejects unknown properties, validates enums, and rejects malformed values.

### Create onboarding

```json
{
  "actor": "onboarding-ops"
}
```

### Update onboarding

```json
{
  "status": "IN_PROGRESS",
  "actor": "onboarding-ops"
}
```

An optional optimistic-lock field may be supplied:

```json
{
  "status": "AWAITING_REVIEW",
  "version": 2,
  "actor": "onboarding-ops"
}
```

### Create agreement

```json
{
  "type": "TERMS_AND_CONDITIONS",
  "version": "2026.08",
  "isRequired": true,
  "accepted": true,
  "acceptedBy": "customer",
  "actor": "onboarding-ops"
}
```

`acceptedBy` is optional. When `accepted` is true and it is omitted, the audit actor is used as the accepting actor.

### Create risk profile

```json
{
  "riskLevel": "LOW",
  "rationale": "Standard internal assessment",
  "assessedBy": "risk-ops"
}
```

### Create onboarding task

```json
{
  "type": "PROFILE_COMPLETION",
  "status": "COMPLETED",
  "isRequired": true,
  "completedBy": "onboarding-ops",
  "notes": "Profile evidence reviewed",
  "actor": "onboarding-ops"
}
```

`status` defaults to `PENDING`. `completedBy` is optional and is required only as a separate value when a completed task needs a distinct completer.

### Create approval decision

```json
{
  "decision": "PENDING",
  "reason": "Awaiting final review",
  "decidedBy": "review-ops"
}
```

## APIs

All routes use the global prefix `/api/v1`.

| Method  | Route                                 | Purpose                                           |
| ------- | ------------------------------------- | ------------------------------------------------- |
| `POST`  | `/customers/:id/onboarding`           | Create a `NOT_STARTED` onboarding workflow.       |
| `GET`   | `/customers/:id/onboarding`           | Get the latest onboarding workflow.               |
| `PATCH` | `/customers/:id/onboarding`           | Apply a validated lifecycle transition.           |
| `POST`  | `/customers/:id/agreements`           | Add an agreement version and acceptance decision. |
| `GET`   | `/customers/:id/agreements`           | List customer agreement records.                  |
| `POST`  | `/customers/:id/risk-profile`         | Create the current risk profile.                  |
| `GET`   | `/customers/:id/risk-profile`         | Get the current risk profile.                     |
| `POST`  | `/customers/:id/onboarding-task`      | Add an onboarding task.                           |
| `GET`   | `/customers/:id/onboarding-tasks`     | List onboarding tasks.                            |
| `POST`  | `/customers/:id/approval`             | Create or advance the latest approval decision.   |
| `GET`   | `/customers/:id/approval`             | Get the latest approval decision.                 |
| `GET`   | `/customers/:id/onboarding-readiness` | Calculate completion readiness.                   |

## Audit behavior

The existing immutable `AuditService` records:

- Onboarding creation and status changes.
- Agreement creation.
- Risk-profile creation.
- Task creation.
- Approval creation and supersession.

Customer onboarding audit entity types are `CUSTOMER_ONBOARDING`, `CUSTOMER_AGREEMENT`, `CUSTOMER_RISK_PROFILE`, `CUSTOMER_ONBOARDING_TASK`, and `CUSTOMER_APPROVAL_DECISION`.

Migration `1785753600009-CreateCustomerOnboarding.ts` creates the five P1.2 tables, foreign keys, enum check constraints, soft-deletion-aware unique indexes, query indexes, and optimistic version columns. ### 8. Validation and negative checks

```powershell
$InvalidBody = @{
  firstName = 'Unexpected'
  lastName = 'Property'
  actor = 'manual-verification'
} | ConvertTo-Json

try {
  Invoke-RestMethod `
    -Method Post `
    -Uri "$BaseUrl/customers/$CustomerId/onboarding" `
    -Headers $Headers `
    -Body $InvalidBody
  throw 'Unexpected validation success'
} catch {
  $_.Exception.Response.StatusCode.value__
}
```

The invalid payload must return a validation error. Repeating an active onboarding creation, repeating a current risk profile creation, repeating the latest approval decision, attempting an invalid lifecycle transition, or attempting completion before all required evidence is present must return a conflict response.
