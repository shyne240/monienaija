# P1.6 Customer Beneficiaries & Trusted Recipients

## Scope

P1.6 adds internal customer beneficiary registration and trusted-recipient lifecycle management. It records who a customer has saved for possible future transfers.

This milestone does not execute transfers, debit or credit wallets, create journals, interact with the ledger, integrate banks or NIBSS, validate account ownership externally, or invoke reconciliation.

## Domain entities

| Entity                    | Purpose                                                                                  |
| ------------------------- | ---------------------------------------------------------------------------------------- |
| `CustomerBeneficiary`     | Customer beneficiary identity, destination details, lifecycle status, and verified flag. |
| `BeneficiaryOwnership`    | Immutable customer-to-beneficiary ownership record.                                      |
| `BeneficiaryVerification` | Append-only beneficiary verification evidence.                                           |
| `BeneficiaryHistory`      | Append-only lifecycle, verification, and ownership history.                              |

Each beneficiary uses a UUID, belongs to one UUID customer, stores timestamps, has soft deletion, and uses an optimistic version column. Ownership, verification, and history records are soft-deletion-aware.

## Supported values

### Beneficiary types

- `INTERNAL_CUSTOMER`
- `BANK_ACCOUNT`
- `MOBILE_MONEY`
- `CASH_AGENT`

### Beneficiary statuses

- `PENDING`
- `ACTIVE`
- `SUSPENDED`
- `DELETED`

## Beneficiary attributes

A beneficiary stores:

- Customer UUID.
- Beneficiary type.
- Display name.
- Globally unique normalized reference.
- Destination identifier and normalized destination identifier.
- Optional destination name.
- Optional destination institution.
- Optional nickname.
- Lifecycle status.
- Verified flag.
- Created and updated timestamps.
- Soft-deletion timestamp.
- Optimistic version.

Destination identifiers are normalized to lowercase with whitespace, parentheses, and hyphens removed for duplicate detection. Duplicate destinations are rejected for the same customer while the existing beneficiary is not soft-deleted.

References are normalized to lowercase and globally unique across all records, including soft-deleted records, so references cannot be reused.

## Lifecycle rules

| Current     | Allowed next statuses            |
| ----------- | -------------------------------- |
| `PENDING`   | `ACTIVE`, `SUSPENDED`, `DELETED` |
| `ACTIVE`    | `SUSPENDED`, `DELETED`           |
| `SUSPENDED` | `ACTIVE`, `DELETED`              |
| `DELETED`   | None                             |

A suspended beneficiary may be explicitly reactivated. A deleted beneficiary cannot become active again. Soft-deleted beneficiaries are excluded from normal list and detail reads, while their ownership and history remain queryable for audit purposes.

## Verification

`POST /verify` creates an append-only verification record containing:

- `verifiedBy`
- `verifiedAt`
- `verificationMethod`
- `remarks`

Verification sets the beneficiary `verified` flag to true without executing any transfer or external ownership check. Verification of a deleted beneficiary is rejected. Repeated verification requests append new verification evidence and history records.

## Ownership, history, and audit

Ownership is created in the same transaction as beneficiary creation and has no update endpoint. Ownership transfer is not implemented.

History actions are:

- `CREATED`
- `OWNERSHIP_CREATED`
- `STATUS_CHANGED`
- `VERIFIED`

Every beneficiary, ownership, verification, and history mutation uses the existing immutable `AuditService` in the same transaction. Audit entity types are:

- `CUSTOMER_BENEFICIARY`
- `BENEFICIARY_OWNERSHIP`
- `BENEFICIARY_VERIFICATION`
- `BENEFICIARY_HISTORY`

## DTO payloads

The global validation pipe transforms DTOs, rejects unknown properties, validates enums, and validates UUID route parameters in the service.

### Create beneficiary

```json
{
  "type": "BANK_ACCOUNT",
  "displayName": "Main recipient",
  "reference": "recipient-001",
  "destinationIdentifier": "0123456789",
  "destinationName": "Recipient Name",
  "destinationInstitution": "Example Bank",
  "nickname": "Main recipient",
  "actor": "beneficiary-ops"
}
```

`destinationName`, `destinationInstitution`, and `nickname` are optional.

### Update beneficiary

```json
{
  "status": "ACTIVE",
  "actor": "beneficiary-ops"
}
```

An optional optimistic-lock version may be supplied:

```json
{
  "status": "SUSPENDED",
  "version": 2,
  "actor": "beneficiary-ops"
}
```

### Verify beneficiary

```json
{
  "verifiedBy": "review-ops",
  "verificationMethod": "MANUAL_REVIEW",
  "remarks": "Recipient details reviewed"
}
```

## APIs

All routes use the global `/api/v1` prefix.

| Method  | Route                                                   | Purpose                                                 |
| ------- | ------------------------------------------------------- | ------------------------------------------------------- |
| `POST`  | `/customers/:id/beneficiaries`                          | Register a customer beneficiary.                        |
| `GET`   | `/customers/:id/beneficiaries`                          | List non-deleted customer beneficiaries.                |
| `GET`   | `/customers/:id/beneficiaries/:beneficiaryId`           | Read one non-deleted beneficiary.                       |
| `PATCH` | `/customers/:id/beneficiaries/:beneficiaryId`           | Apply a validated status transition.                    |
| `POST`  | `/customers/:id/beneficiaries/:beneficiaryId/verify`    | Append verification evidence and set the verified flag. |
| `GET`   | `/customers/:id/beneficiaries/:beneficiaryId/history`   | Read append-only beneficiary history.                   |
| `GET`   | `/customers/:id/beneficiaries/:beneficiaryId/ownership` | Read immutable beneficiary ownership.                   |

## Database migration

Migration `1785753600013-CreateCustomerBeneficiaries.ts` creates:

- `customer_beneficiaries`
- `beneficiary_ownerships`
- `beneficiary_verifications`
- `beneficiary_histories`

It adds customer and beneficiary foreign keys, enum constraints, a globally unique reference constraint, soft-deletion-aware destination and ownership indexes, query indexes, and optimistic version columns. Earlier migrations are unchanged. Production startup compatibility expects migration head `1785753600013 / CreateCustomerBeneficiaries1785753600013`.

## PowerShell manual verification

### Setup

Run from the repository root:

```powershell
$ErrorActionPreference = 'Stop'
$BaseUrl = 'http://localhost:3000/api/v1'
$Headers = @{ 'Content-Type' = 'application/json' }

npm ci
npm run migration:run
npm run start:dev
```

Use a second PowerShell window. Set `$CustomerId` to any existing customer UUID. P1.6 beneficiary registration requires the customer to exist and does not execute financial activity.

```powershell
$CustomerId = '<customer-uuid>'
```

### 1. Register a beneficiary

```powershell
$BeneficiaryBody = @{
  type = 'BANK_ACCOUNT'
  displayName = 'Main recipient'
  reference = "recipient-$([guid]::NewGuid().ToString('N').Substring(0, 10))"
  destinationIdentifier = '0123456789'
  destinationName = 'Recipient Name'
  destinationInstitution = 'Example Bank'
  nickname = 'Main recipient'
  actor = 'beneficiary-ops'
} | ConvertTo-Json

$Beneficiary = Invoke-RestMethod `
  -Method Post `
  -Uri "$BaseUrl/customers/$CustomerId/beneficiaries" `
  -Headers $Headers `
  -Body $BeneficiaryBody

$Beneficiary | ConvertTo-Json -Depth 8
$BeneficiaryId = $Beneficiary.id
```

Expected values:

- `status` is `PENDING`.
- `verified` is `false`.
- `reference` is normalized lowercase.
- No payment, wallet-balance, ledger, bank-provider, or transfer fields are returned.

### 2. Read beneficiary, ownership, and initial history

```powershell
Invoke-RestMethod `
  -Method Get `
  -Uri "$BaseUrl/customers/$CustomerId/beneficiaries" | ConvertTo-Json -Depth 8

Invoke-RestMethod `
  -Method Get `
  -Uri "$BaseUrl/customers/$CustomerId/beneficiaries/$BeneficiaryId" | ConvertTo-Json -Depth 8

$Ownership = Invoke-RestMethod `
  -Method Get `
  -Uri "$BaseUrl/customers/$CustomerId/beneficiaries/$BeneficiaryId/ownership"

$History = Invoke-RestMethod `
  -Method Get `
  -Uri "$BaseUrl/customers/$CustomerId/beneficiaries/$BeneficiaryId/history"

$Ownership | ConvertTo-Json -Depth 8
$History | ConvertTo-Json -Depth 8
```

Ownership must contain the original `$CustomerId` and `$BeneficiaryId`. History must include `CREATED` and `OWNERSHIP_CREATED`.

### 3. Verify the beneficiary

```powershell
$VerificationBody = @{
  verifiedBy = 'review-ops'
  verificationMethod = 'MANUAL_REVIEW'
  remarks = 'Recipient details reviewed'
} | ConvertTo-Json

$Verification = Invoke-RestMethod `
  -Method Post `
  -Uri "$BaseUrl/customers/$CustomerId/beneficiaries/$BeneficiaryId/verify" `
  -Headers $Headers `
  -Body $VerificationBody

$Verification | ConvertTo-Json -Depth 8
```

```powershell
$CurrentBeneficiary = Invoke-RestMethod `
  -Method Get `
  -Uri "$BaseUrl/customers/$CustomerId/beneficiaries/$BeneficiaryId"

$CurrentBeneficiary | ConvertTo-Json -Depth 8
if ($CurrentBeneficiary.verified -ne $true) {
  throw 'Beneficiary was not verified'
}
```

```powershell
Invoke-RestMethod `

```

```powershell
$SuspendedBody = @{
  status = 'SUSPENDED'

Invoke-RestMethod `
  -Method Patch `
  -Uri "$BaseUrl/customers/$CustomerId/beneficiaries/$BeneficiaryId" `
```

### 5. Verify duplicate destination and reference rejection

```powershell
try {
  Invoke-RestMethod `
    -Method Post `
    -Uri "$BaseUrl/customers/$CustomerId/beneficiaries" `
    -Headers $Headers `
    -Body (@{
      type = 'MOBILE_MONEY'
      displayName = 'Duplicate destination'
      reference = "other-$([guid]::NewGuid().ToString('N').Substring(0, 10))"
      destinationIdentifier = '01 234 567 89'
      actor = 'beneficiary-ops'
    } | ConvertTo-Json)
  throw 'Duplicate destination unexpectedly succeeded'
} catch {
  $_.Exception.Response.StatusCode.value__
}

try {
  Invoke-RestMethod `
    -Method Post `
    -Uri "$BaseUrl/customers/$CustomerId/beneficiaries" `
    -Headers $Headers `
    -Body (@{
      type = 'CASH_AGENT'
      displayName = 'Duplicate reference'
      reference = $Beneficiary.reference.ToUpper()
      destinationIdentifier = 'different-destination'
      actor = 'beneficiary-ops'
    } | ConvertTo-Json)
  throw 'Duplicate reference unexpectedly succeeded'
} catch {
  $_.Exception.Response.StatusCode.value__
}
```

Both requests must return `409`.

### 6. Soft-delete and verify deleted-beneficiary protection

```powershell
$DeleteBody = @{
  status = 'DELETED'
  actor = 'beneficiary-ops'
} | ConvertTo-Json

Invoke-RestMethod `
  -Method Patch `
  -Uri "$BaseUrl/customers/$CustomerId/beneficiaries/$BeneficiaryId" `
  -Headers $Headers `
  -Body $DeleteBody | ConvertTo-Json -Depth 8
```

```powershell
try {
  Invoke-RestMethod `
    -Method Patch `
    -Uri "$BaseUrl/customers/$CustomerId/beneficiaries/$BeneficiaryId" `
    -Headers $Headers `
    -Body $ActiveBody
  throw 'Deleted beneficiary unexpectedly became ACTIVE'
} catch {
  $_.Exception.Response.StatusCode.value__
}

try {
  Invoke-RestMethod `
    -Method Post `
    -Uri "$BaseUrl/customers/$CustomerId/beneficiaries/$BeneficiaryId/verify" `
    -Headers $Headers `
    -Body $VerificationBody
  throw 'Deleted beneficiary unexpectedly verified'
} catch {
  $_.Exception.Response.StatusCode.value__
}
```

The activation request must return `409`, the verification request must return `404`, and the normal beneficiary list must exclude the soft-deleted row. History and ownership remain readable for audit purposes.

### 7. Verify history and audit events

```powershell
Invoke-RestMethod `
  -Method Get `
  -Uri "$BaseUrl/customers/$CustomerId/beneficiaries/$BeneficiaryId/history" | ConvertTo-Json -Depth 8

Invoke-RestMethod `
  -Method Get `
  -Uri "$BaseUrl/internal/audit?entityType=CUSTOMER_BENEFICIARY&entityId=$BeneficiaryId&limit=100" | ConvertTo-Json -Depth 8

Invoke-RestMethod `
  -Method Get `
  -Uri "$BaseUrl/internal/audit?entityType=BENEFICIARY_VERIFICATION&entityId=$($Verification.id)&limit=100" | ConvertTo-Json -Depth 8
```

History must include creation, ownership creation, verification, and status-change events. Audit results must include beneficiary, ownership, verification, and history mutations.

### 9. Verify no financial side effects

P1.6 does not import or invoke wallet, ledger, payment, transfer, bank, NIBSS, or reconciliation modules. Beneficiary requests create no ledger journals, ledger lines, wallet debits, wallet credits, transfers, or payments.
