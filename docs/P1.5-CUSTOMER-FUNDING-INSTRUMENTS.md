# P1.5 Customer Funding Instruments

## Scope

P1.5 adds internal registration and lifecycle management for customer funding instruments. It records the customer’s declared instrument, ownership, verification history, and lifecycle history.

This milestone does not execute payments, debit or credit wallets, post ledger journals, integrate banks, create cards, create transfers, create virtual accounts, invoke reconciliation, or call external services.

## Domain entities

| Entity                          | Purpose                                                                                          |
| ------------------------------- | ------------------------------------------------------------------------------------------------ |
| `CustomerFundingInstrument`     | Customer-owned funding instrument identity, reference, lifecycle status, and verification state. |
| `FundingInstrumentOwnership`    | Immutable customer-to-instrument ownership record.                                               |
| `FundingInstrumentVerification` | Append-only verification evidence record.                                                        |
| `FundingInstrumentHistory`      | Append-only lifecycle and ownership history.                                                     |

Each instrument uses a UUID, belongs to one UUID customer, stores timestamps, has a soft-deletion field, and uses an optimistic version column. Ownership, verification, and history records are also soft-deletion-aware.

## Supported values

### Instrument types

- `BANK_ACCOUNT`
- `MOBILE_MONEY`
- `CASH_AGENT`
- `INTERNAL_SETTLEMENT`

### Instrument statuses

- `PENDING`
- `VERIFIED`
- `SUSPENDED`
- `INACTIVE`
- `REJECTED`

### Verification states

- `UNVERIFIED`
- `VERIFIED`
- `REJECTED`

Verification state is stored separately from lifecycle status so the instrument’s registration state and verification evidence remain explicit.

## Lifecycle rules

The supported status transitions are:

| Current     | Allowed next statuses               |
| ----------- | ----------------------------------- |
| `PENDING`   | `SUSPENDED`, `INACTIVE`, `REJECTED` |
| `VERIFIED`  | `SUSPENDED`, `INACTIVE`, `REJECTED` |
| `SUSPENDED` | `PENDING`, `INACTIVE`, `REJECTED`   |
| `INACTIVE`  | `PENDING`, `REJECTED`               |
| `REJECTED`  | None                                |

`VERIFIED` is reached through the verification endpoint, not through a direct status patch. Rejected instruments cannot become verified. Deleted instruments cannot be verified.

A `PENDING` status has `UNVERIFIED` state. A `REJECTED` status has `REJECTED` state. Suspending or inactivating an instrument preserves its prior verification state.

## References and ownership

References are trimmed, normalized to lowercase, validated against the internal safe-reference format, and globally unique. The database uniqueness constraint includes soft-deleted rows, so a reference cannot be reused after an instrument is soft-deleted.

Ownership is created in the same transaction as the instrument and has no update endpoint. P1.5 does not support ownership transfer.

## Verification

`POST /verify` creates a new append-only verification record containing:

- `verifiedBy`
- `verifiedAt`
- `verificationMethod`
- `remarks`

Verification is allowed for `PENDING` and `SUSPENDED` instruments. A verification request changes the instrument status to `VERIFIED`, changes its verification state to `VERIFIED`, creates a verification history event, and creates immutable audit events.

## History and audit

History actions are:

- `CREATED`
- `OWNERSHIP_CREATED`
- `STATUS_CHANGED`
- `VERIFIED`

Every instrument, ownership, verification, and history mutation uses the existing immutable `AuditService` in the same transaction. Audit entity types are:

- `CUSTOMER_FUNDING_INSTRUMENT`
- `FUNDING_INSTRUMENT_OWNERSHIP`
- `FUNDING_INSTRUMENT_VERIFICATION`
- `FUNDING_INSTRUMENT_HISTORY`

History and verification records are append-only. No update endpoint is exposed for either record type.

## DTO payloads

The global validation pipe transforms DTOs, rejects unknown properties, validates enums, and validates UUID route parameters in the service.

### Create funding instrument

```json
{
  "type": "BANK_ACCOUNT",
  "displayName": "Main account",
  "reference": "bank-001",
  "actor": "funding-ops"
}
```

### Update funding instrument

```json
{
  "status": "SUSPENDED",
  "actor": "funding-ops"
}
```

An optional optimistic-lock version may be supplied:

```json
{
  "status": "INACTIVE",
  "version": 2,
  "actor": "funding-ops"
}
```

### Verify funding instrument

```json
{
  "verifiedBy": "review-ops",
  "verificationMethod": "MANUAL_DOCUMENT_REVIEW",
  "remarks": "Evidence inspected"
}
```

## APIs

All routes use the global `/api/v1` prefix.

| Method  | Route                                                        | Purpose                                                        |
| ------- | ------------------------------------------------------------ | -------------------------------------------------------------- |
| `POST`  | `/customers/:id/funding-instruments`                         | Register a customer funding instrument.                        |
| `GET`   | `/customers/:id/funding-instruments`                         | List customer funding instruments.                             |
| `GET`   | `/customers/:id/funding-instruments/:instrumentId`           | Read one funding instrument.                                   |
| `PATCH` | `/customers/:id/funding-instruments/:instrumentId`           | Apply a lifecycle status transition.                           |
| `POST`  | `/customers/:id/funding-instruments/:instrumentId/verify`    | Append verification evidence and mark the instrument verified. |
| `GET`   | `/customers/:id/funding-instruments/:instrumentId/history`   | Read append-only history.                                      |
| `GET`   | `/customers/:id/funding-instruments/:instrumentId/ownership` | Read immutable ownership.                                      |

## Database migration

Migration `1785753600012-CreateCustomerFundingInstruments.ts` creates:

- `customer_funding_instruments`
- `funding_instrument_ownerships`
- `funding_instrument_verifications`
- `funding_instrument_histories`

It adds customer and instrument foreign keys, enum constraints, a globally unique reference constraint, soft-deletion-aware ownership indexes, query indexes, and optimistic version columns. Earlier migrations are unchanged. Production startup compatibility expects migration head `1785753600012 / CreateCustomerFundingInstruments1785753600012`.

## PowerShell manual verification

### Setup

Run from the repository root:

```powershell
$ErrorActionPreference = 'Stop'
$BaseUrl = 'http://localhost:3000/api/v1'
$Headers = @{ 'Content-Type' = 'application/json' }

npm ci
npm run migration:run
npm run start:dev
```

Use a second PowerShell window. Set `$CustomerId` to any existing customer UUID. P1.5 registration requires the customer to exist; it does not execute or provision a financial wallet.

```powershell
$CustomerId = '<customer-uuid>'
```

### 1. Register a funding instrument

```powershell
$InstrumentBody = @{
  type = 'BANK_ACCOUNT'
  displayName = 'Main account'
  reference = "bank-$([guid]::NewGuid().ToString('N').Substring(0, 10))"
  actor = 'funding-ops'
} | ConvertTo-Json

$Instrument = Invoke-RestMethod `
  -Method Post `
  -Uri "$BaseUrl/customers/$CustomerId/funding-instruments" `
  -Headers $Headers `
  -Body $InstrumentBody

$Instrument | ConvertTo-Json -Depth 8
$InstrumentId = $Instrument.id
```

Expected values:

- `status` is `PENDING`.
- `verificationState` is `UNVERIFIED`.
- `reference` is normalized lowercase.
- The response contains no payment, wallet-balance, ledger, or bank-provider fields.

### 2. Read the instrument, ownership, and initial history

```powershell
Invoke-RestMethod `
  -Method Get `
  -Uri "$BaseUrl/customers/$CustomerId/funding-instruments" | ConvertTo-Json -Depth 8

Invoke-RestMethod `
  -Method Get `
  -Uri "$BaseUrl/customers/$CustomerId/funding-instruments/$InstrumentId" | ConvertTo-Json -Depth 8

$Ownership = Invoke-RestMethod `
  -Method Get `
  -Uri "$BaseUrl/customers/$CustomerId/funding-instruments/$InstrumentId/ownership"

$History = Invoke-RestMethod `
  -Method Get `
  -Uri "$BaseUrl/customers/$CustomerId/funding-instruments/$InstrumentId/history"

$Ownership | ConvertTo-Json -Depth 8
$History | ConvertTo-Json -Depth 8
```

Ownership must contain the original `$CustomerId` and `$InstrumentId`. History must include `CREATED` and `OWNERSHIP_CREATED`.

### 3. Verify the funding instrument

```powershell
$VerificationBody = @{
  verifiedBy = 'review-ops'
  verificationMethod = 'MANUAL_DOCUMENT_REVIEW'
  remarks = 'Evidence inspected'
} | ConvertTo-Json

$Verification = Invoke-RestMethod `
  -Method Post `
  -Uri "$BaseUrl/customers/$CustomerId/funding-instruments/$InstrumentId/verify" `
  -Headers $Headers `
  -Body $VerificationBody

$Verification | ConvertTo-Json -Depth 8
```

```powershell
$CurrentInstrument = Invoke-RestMethod `
  -Method Get `
  -Uri "$BaseUrl/customers/$CustomerId/funding-instruments/$InstrumentId"

$CurrentInstrument | ConvertTo-Json -Depth 8
if ($CurrentInstrument.status -ne 'VERIFIED') {
  throw 'Funding instrument was not verified'
}
if ($CurrentInstrument.verificationState -ne 'VERIFIED') {
  throw 'Funding instrument verification state was not updated'
}
```

A second verification request for an already verified instrument must return `409`.

### 4. Exercise status transitions

```powershell
$SuspendedBody = @{
  status = 'SUSPENDED'
  actor = 'funding-ops'
} | ConvertTo-Json

Invoke-RestMethod `
  -Method Patch `
  -Uri "$BaseUrl/customers/$CustomerId/funding-instruments/$InstrumentId" `
  -Headers $Headers `
  -Body $SuspendedBody | ConvertTo-Json -Depth 8
```

```powershell
$PendingBody = @{
  status = 'PENDING'
  actor = 'funding-ops'
} | ConvertTo-Json

Invoke-RestMethod `
  -Method Patch `
  -Uri "$BaseUrl/customers/$CustomerId/funding-instruments/$InstrumentId" `
  -Headers $Headers `
  -Body $PendingBody | ConvertTo-Json -Depth 8
```

```powershell
Invoke-RestMethod `
  -Method Post `
  -Uri "$BaseUrl/customers/$CustomerId/funding-instruments/$InstrumentId/verify" `
  -Headers $Headers `
  -Body (@{
    verifiedBy = 'review-ops'
    verificationMethod = 'MANUAL_RECHECK'
    remarks = 'Rechecked after pending state'

```

The status changes must append `STATUS_CHANGED` history records and the verification must append a `VERIFIED` history record.

### 5. Verify duplicate reference rejection

```powershell
try {
  Invoke-RestMethod `
    -Method Post `
    -Uri "$BaseUrl/customers/$CustomerId/funding-instruments" `
    -Headers $Headers `
    -Body (@{
      type = 'MOBILE_MONEY'
      displayName = 'Duplicate reference'
      reference = $Instrument.reference.ToUpper()
      actor = 'funding-ops'
    } | ConvertTo-Json)
  throw 'Duplicate funding instrument reference unexpectedly succeeded'
} catch {
  $_.Exception.Response.StatusCode.value__
}
```

The duplicate reference request must return `409`. References remain unavailable after soft deletion.

### 6. Verify rejected instruments cannot be verified

```powershell
$RejectedInstrument = Invoke-RestMethod `
  -Method Post `
  -Uri "$BaseUrl/customers/$CustomerId/funding-instruments" `
  -Headers $Headers `
  -Body (@{
    type = 'CASH_AGENT'
    displayName = 'Rejected instrument'
    reference = "rejected-$([guid]::NewGuid().ToString('N').Substring(0, 10))"
    actor = 'funding-ops'
  } | ConvertTo-Json)

Invoke-RestMethod `
  -Method Patch `
  -Uri "$BaseUrl/customers/$CustomerId/funding-instruments/$($RejectedInstrument.id)" `
  -Headers $Headers `
  -Body (@{
    status = 'REJECTED'
    actor = 'review-ops'
  } | ConvertTo-Json) | ConvertTo-Json -Depth 8

try {
  Invoke-RestMethod `
    -Method Post `
    -Uri "$BaseUrl/customers/$CustomerId/funding-instruments/$($RejectedInstrument.id)/verify" `
    -Headers $Headers `
    -Body $VerificationBody
  throw 'Rejected instrument unexpectedly became VERIFIED'
} catch {
  $_.Exception.Response.StatusCode.value__
}
```

The verification request must return `409`.

### 7. Verify soft-deleted instruments cannot be verified

This test uses a direct soft-delete SQL statement for a disposable test instrument. It does not hard-delete the row:

```powershell
$DeletedInstrument = Invoke-RestMethod `
  -Method Post `
  -Uri "$BaseUrl/customers/$CustomerId/funding-instruments" `
  -Headers $Headers `
  -Body (@{
    type = 'INTERNAL_SETTLEMENT'
    displayName = 'Soft delete test'
    reference = "deleted-$([guid]::NewGuid().ToString('N').Substring(0, 10))"
    actor = 'funding-ops'
  } | ConvertTo-Json)

$DeletedId = $DeletedInstrument.id

docker compose exec postgres psql -U monienaija -d monienaija -c "UPDATE customer_funding_instruments SET deleted_at = NOW() WHERE id = '$DeletedId';"
```

```powershell
try {
  Invoke-RestMethod `
    -Method Post `
    -Uri "$BaseUrl/customers/$CustomerId/funding-instruments/$DeletedId/verify" `
    -Headers $Headers `
    -Body $VerificationBody
  throw 'Deleted instrument unexpectedly verified'
} catch {
  $_.Exception.Response.StatusCode.value__
}
```

The verification request must return `404`.

### 10. Verify no financial side effects

P1.5 does not invoke the financial wallet, ledger, payment, or reconciliation modules. No ledger journals, ledger lines, wallet balances, payments, or transactions are created by the funding-instrument requests.
