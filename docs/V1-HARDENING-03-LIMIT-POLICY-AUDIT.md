## 1. Executive Summary

MonieNaija **V1 in-house NGN wallet** has a **complete limit configuration architecture but no authoritative runtime limit enforcement** in the customer-facing money paths. The authoritative V1 handoff/scope documents **describe limits as an A4 capability-policy concern with explicit per-type ownership, but every in-house V1 transfer path today checks only ledger-derived balance / no-overdraft** (`422 INSUFFICIENT_FUNDS`) **and not limits**. The repository already contains:

- **Customer limit profiles** (`customer_limit_profiles` `v1` `1785753600010` — `singleTransactionAmountMinor`, `dailyTransactionAmountMinor`, `dailyTransactionCount`, `monthlyTransactionAmountMinor`, `walletBalanceMinor`, `currency`, `version`, soft-delete) managed via `CustomerEligibilityService` (`createLimitProfile`/`updateLimitProfile`/`getLimitProfile`) and exposed as **A4 evidence** (`CustomerLimitProfileSourceEvidenceReader` → `CustomerLimitProfilePolicyEvidenceAdapter`).
- **Agent class applicable limits** (`agent_classes.applicable_limits` `JSONB` nullable) managed via `AgentClassService` (`create`/`update` with `applicableLimits`).
- **Pure calculators** `LimitEngine` (`evaluate`: `SINGLE_TRANSACTION_LIMIT_EXCEEDED` / `DAILY_LIMIT_EXCEEDED` / `MONTHLY_LIMIT_EXCEEDED`) + `POST /limits/evaluate` — **not called by `TransferService`**.
- **Pilot control** (`pilot_controls` `1785753600025` — `controlKey='wallet.transfer.create.v1'`, `capability='wallet.transfer'`, `action='create'`, `scope='INTERNAL_CUSTOMER_TO_CUSTOMER'`, `enabled`, `cohortCustomerIds[]`, `currency='NGN'`, `minTransactionAmountMinor`/`maxTransactionAmountMinor`, `dailyTransactionCountLimit`, `dailyTransactionAmountMinor`, `safetyThresholds` JSONB, `updatedBy`, `version`) evaluated via `PilotControlService.evaluate` (`PILOT_DISABLED` / `PILOT_CURRENCY_DENIED` / `PILOT_COHORT_DENIED` / `PILOT_AMOUNT_BELOW_MINIMUM` / `PILOT_TRANSACTION_LIMIT_EXCEEDED` / `PILOT_DAILY_COUNT_LIMIT_EXCEEDED` / `PILOT_DAILY_AMOUNT_LIMIT_EXCEEDED` / `PILOT_ALLOWED`).
- **A4 internal-transfer gate** (`InternalTransferGateService` — `SERIALIZABLE` `wallet.transfer.create.v1` `IdempotencyService`, `AuthorizationService` + `PilotControlService` + `CapabilityPolicyEvaluationService` + `PolicySourceEvidenceCoordinator` + `CustomerFinancialAccountBinding` validation) — **existing but not used by `POST /customers/me/transfers` (customer-app delegates directly to `TransferService`)**.

Authoritative V1 (A1-A8 handoffs, `V1-008`, hardening audits) describes limits as **A4-governed capability limits (`ALLOW_WITH_LIMITS` / exact `limits[]` minor-unit outputs)** that **must be enforced at command time with durable usage counting**, but the **in-house V1 pilot** is **disabled by default** (`PilotControl.enabled=false`, empty cohort) and `V1-008 M1` explicitly tags `Fees/Limits` as `METADATA-ONLY` with `REQUIRES PRODUCT/OPERATIONAL DECISION` (mirroring fees). No authoritative document provides a **closed NGN amount / count value, ownership matrix, or per-flow limit table** for the 11 audited flows — the only concrete values are **per-customer profile defaults expressed as configurable policy**, not a fixed V1 launch threshold.

**Therefore the correct classification is OUTCOME B:**

**`BLOCKED — V1 LIMIT POLICY REQUIRES PRODUCT/OPERATIONAL DECISION`** — the architecture is present, but authoritative V1 scope does **not** define the exact in-house launch limits, ownership, and enforcement window sufficiently to implement without inventing operational values. The customer-app transfer path is **currently `VERIFIED` as balance-only** (no silent mis-enforcement), but **not** `VERIFIED` as limit-enforced — a future wiring is required once product decides.

## 5. Customer Limits (Step 4)

`customer_limit_profiles` (`src/customer-eligibility/customer-limit-profile.entity.ts:15-65`, `src/migrations/1785753600010-CreateCustomerEligibility.ts:41-69`):

- **Per-transaction limit:** **Yes** — `single_transaction_amount_minor` (`bigint` `chk_customer_limit_profiles_amounts_non_negative`) — single W→W `amountMinor` vs `singleTransactionAmountMinor`.
- **Daily limit:** **Yes, two** — `daily_transaction_amount_minor` (sum of `amountMinor` per calendar day) + `daily_transaction_count` (`integer` `>=0`, count of W→W per day).
- **Monthly limit:** **Yes** — `monthly_transaction_amount_minor` (sum per calendar month).
- **Cumulative / transaction-count limit:** Daily count is the only count limit; no cumulative lifetime count — **no** unbounded cumulative except via `wallet_balance_minor`.
- **Velocity limit:** **No explicit velocity** (e.g., 5 per minute) — only daily count / daily amount windows.
- **Wallet balance limit:** **Yes** — `wallet_balance_minor` (`bigint` `>=0`) — max wallet `CUSTOMER_FUNDS` `NGN` balance (distinct from per-transaction limit).
- **Configurable overrides:** **Yes per-customer per-currency** — one active row per `customer_id WHERE deleted_at IS NULL` (`uq_customer_limit_profiles_active_customer`), `currency` indexed, soft-delete for deactivation, `version` optimistic.
- **Effective dates:** **No `effective_from` / `effective_until`** — `created_at`/`updated_at`/`deleted_at` only; effective window is “active until soft-deleted.”
- **Status:** **Implicit** — `deleted_at NULL = active`, `deleted_at NOT NULL = inactive`. No `status` enum beyond `version`.

## 9. Concurrency Analysis (Step 6)

**Current (no limits):** Concurrency is safe **for balance** — `TransferService.executeWithinTransaction` does `dataSource.transaction('SERIALIZABLE')` + `lockWallets(manager, [source,destination] ORDER BY id FOR UPDATE)` + `LedgerService.postJournalInTransaction` which does `SELECT ledger_accounts ... FOR UPDATE` + `SELECT SUM(CASE WHEN direction=normal_balance ...)` for balance check + deferred `CONSTRAINT TRIGGER ledger_journal_must_balance`. Two concurrent `80k` `W→W` with `balance 100k` correctly serializes: one commits, the other sees `INSUFFICIENT_FUNDS` on retry `40001→Conflict`. `IdempotencyService.reserve` uses `pessimistic_write` + `SERIALIZABLE` on `idempotency_records` — duplicate `Idempotency-Key` → single journal (hardening-01 `29` concurrent same key).

**If limits (e.g., `daily 100k`) were enforced naïvely with separate `SELECT SUM(amountMinor) FROM transfers WHERE customerId AND createdAt BETWEEN dayStart AND dayEnd` outside the same `SERIALIZABLE` or without `SELECT ... FOR UPDATE` on the usage row**, the system **would not** prevent double-spend over limit: two concurrent `80k` requests each read `dailyUsed=0`, each compute `0+80k ≤100k → allow`, each insert `transfers` + `ledger_lines`, combined `160k` > `100k` — `SERIALIZABLE` alone **does** detect write-write conflicts **only if** both transactions write to a row that is read with a predicate that conflicts under `SERIALIZABLE` **or** if a dedicated `customer_daily_usage` row is locked. Reading `transfers` via `SUM` without locking the counter row can still **anomalize** under `SERIALIZABLE` with `40001` serialization failure, but the current `TransferService` **does not** have such a counter and `lockWallets` does **not** cover the `transfers` aggregate. Therefore a naive `dailyUsed = await transferRepository.sum(...)` would be **insufficient**.

**What primitive would be needed (not implemented):**

- **Dedicated `customer_daily_usage` (or `agent_daily_usage`) row per `customer_id` per `calendar_date` per `currency`**, with `daily_count` / `daily_amount_minor` columns, `UNIQUE(customer_id, date, currency)`, `version`/`updated_at`, created on first transfer of day, **locked `FOR UPDATE`** inside the same `SERIALIZABLE` transaction that inserts the `transfer` + `ledger_lines`. Limit check (`if dailyAmount+amount > limit → DENY`) and increment (`UPDATE ... SET daily_amount_minor = daily_amount_minor + amount, daily_count = daily_count +1`) must happen **atomically** with the `transfer` insert and **before** `postJournal`. **Idempotency `reserve` must happen first** (so replay does not double-increment, see §10). Alternatively, use `SERIALIZABLE` with `SELECT ... FOR UPDATE` on the `usage` row and retry `40001` — the existing `MAX_SERIALIZABLE_ATTEMPTS=3` pattern in `TransferService` already retries `40001`.

**Current is `NO` for concurrency-safe limits** — would need the above.

## 10. Idempotency Analysis (Step 7)

Current (no limits): `requestHash = sha256(canonicalJson{source,destination,amount,currency,reference,narration})` (**PIN never in hash**, beneficiary resolution `resolvedDestinationWalletId` canonical — hardening-01 `22/23`). `idempotencyKey` unique `uq_transfers_idempotency_key` → same key + same hash → `REPLAYED` same `transferId` (no second journal); different hash same key → `409`. `AgentFinancialExecutionService` uses `scope agent-financial.v1:${agentId}` + `requestHash` covering `lines` + `metadata`.

If limits were later enforced, idempotency must **not double-count**:

- **Retry of same transaction (same `Idempotency-Key` + same `requestHash`):** **Must consume limit once.** Achieved by **reserving idempotency first, checking `REPLAY` before any `customer_daily_usage` increment**, and on `REPLAY` returning stored `transferId` without re-evaluating limits. Current `InternalTransferGateService` ordering (`idempotency.reserve` → `PilotControlService.evaluate` → `Policy` → `Binding` → `audit`) already does `REPLAY` before `evaluate`, but `TransferService` **reverses** (`find existing` before `lockWallets`, but limit check would be after). For future limit wiring, the **correct order** is: `IdempotencyService.reserve` (`pessimistic_write` + `SERIALIZABLE`) → if `REPLAY` return stored result **without** limit re-evaluation → else `SELECT ... FOR UPDATE customer_daily_usage` → limit check → `INSERT transfer` → `postJournal` → `idempotency.complete` + `audit`.
- **Failed transaction:** **Must not consume limit.** `TransferService` currently inserts `TransferStatus.FAILED` (`failureCode`/`failureMessage`) with no journal; daily count should **not** increment for `FAILED`. Implementation must only increment on `COMPLETED` path.
- **Already-completed idempotent retry re-evaluates limit?** **No** — `REPLAY` path skips re-evaluation.
- **Expired Cash→Cash transfer:** **Must not count as completed usage** toward sender’s daily. Expiry sweep (`AddExpiry` `1785753600059` → `AgentCashToCashExpiryService` `DEBIT unclaimed CREDIT pool`) is a **reversal**, not a new limit consumption; sender’s `dailyUsed` should be **reversed or not counted** for expired (policy decision — see §14).
- **Rejected transaction:** **No limit consumption** — `LIMIT_EXCEEDED` itself should be ` audit` `LIMIT_DENIED` with no `daily_usage` increment and no journal.

Current repository behavior (no limits) already satisfies the **no-double-count on retry** for journals (hardening-01 `29`), but **not yet for a future `customer_daily_usage` counter** — that counter would need the reservation-first primitive above.

## 11. Security / Authority Analysis (Step 8)

**Where limit decisions must be made:** Inside the **authoritative financial execution transaction** (`dataSource.transaction('SERIALIZABLE')` in `TransferService` / `AgentFinancialExecutionService` / `CustomerFundingService`), **not** in the controller/DTO/client.

**Can client influence limits today?**

- `POST /customers/me/transfers` `CreateTransferDto` (`sourceWalletId`, `destinationWalletId` *or* `beneficiaryId`, `amountMinor`, `currency`, `reference`, `narration`, `pin` + `Idempotency-Key` header) — **no** `limit`, `remainingAllowance`, `approvedAmount`, `bypassFlag`, `dailyUsed` fields. `ValidationPipe whitelist` strips unknown `feeMinor`/`limit` fields; `TransferService.normalizeCommand` constructs `requestHash` only from business params (`source/dest/amount/currency/reference/narration`). Extra `"limit":"10000000"` → still `201` `feeMinor 0` (tested harness).
- `POST /agents/me/cash-in|out|cash-to-cash` — DTOs `amountMinor`/`currency`/`customerId` etc., **no** `applicableLimits` override; `AgentFinancialExecutionService` lines are **server-constructed** (`AgentCashInService` builds `lines=[DEBIT pool CREDIT wallet]`), agent cannot supply arbitrary `applicable_limits` JSON — `AgentClass.applicable_limits` is **read** (if it were enforced) from `agent_classes` row, not from request.
- `POST /limits/evaluate` — `LimitEngine` is **pure** but takes **caller-supplied** `singleTransactionLimitMinor`/`dailyLimitMinor`/`dailyUsedMinor` — **must not** be trusted at financial execution time. The controller is **not** used by `TransferService`; it is a **metadata calculator** for admin preview, not authority. The authoritative path **must** fetch `customer_limit_profiles` row **inside** `SERIALIZABLE` (`FOR UPDATE`) and compute `dailyUsed` via `SELECT SUM` over `transfers`/`ledger_lines` **or** `customer_daily_usage` row, not accept client `dailyUsed`.

**Are current HTTP controllers able to bypass limits?** **No** — there is **no bypass flag**; the bypass is **structural**: customer-app simply **does not evaluate limits at all**, so no explicit bypass is needed. A malicious client cannot “supply a higher limit” because the server never reads a limit from the request — the vulnerability is **absence of enforcement**, not authority override. `CustomerAppController` never calls `CustomerEligibilityService.getLimitProfile` or `PilotControlService.evaluate`; `RoutePolicyRegistry` `CUSTOMER SELF` + `CustomerTransactionPinService` + `SENSITIVE_KEY_NAMES` redaction ensure `pin` never leaks, but **not limits**.

**Therefore security is `VERIFIED` for “no client-controlled limit” (no injection vector) but `NOT VERIFIED` for “authoritative enforcement” — because there is none.**

## 13. Current Gaps (Step 3 cross-check)

- **Customer W→W / Wallet→Cash / Cash→Wallet + Cash→Cash (4/5/2/3) via customer-app/agent-me are `LIMIT_NOT_ENFORCED`** — `TransferService` / `AgentFinancialExecutionService` / `AgentCashToCashService` never call `LimitEngine` / `PilotControlService` / `CustomerEligibilityService.getLimitProfile`; only `INSUFFICIENT_FUNDS` is enforced. `LimitEngine.evaluate` remains **pure endpoint** (`POST /limits/evaluate`) not wired. `InternalTransferGateService` **exists** but customer-app bypasses it — `V1-PRODUCT-COMPLETION-AUDIT` `cannot enforce limits (customer could transfer 10B)` is still true.
- **Agent `applicable_limits` JSONB is never read at execution** — `AgentServiceCapabilityService.canPerform` checks `applicable_services` only.
- **No durable `customer_daily_usage` counter** — `customer_limit_profiles.dailyTransactionCount` *is* the limit value, not the usage; usage is **not** tracked as a row. A future limit implementation **must** persist usage `per (customer_id, date, currency)` and lock it `FOR UPDATE` inside the same `SERIALIZABLE` transfer transaction (see §9).
- **No idempotent usage accounting** — if limits later added without reservation-first, retry of same `Idempotency-Key` would double-increment (see §10).
- **Pilot control is disabled by default and cohort-empty** — even if customer-app were changed to call `InternalTransferGateService.validate`, pilot would return `PILOT_DISABLED` / `PILOT_CONTROL_UNAVAILABLE` for every customer not in `cohortCustomerIds[]` (currently `[]`).
- **No per-transaction vs daily vs monthly vs wallet-balance distinction at runtime** — `CustomerLimitProfile` has all four fields (`single`/`dailyAmount`/`dailyCount`/`monthly`/`walletBalance`) but none are enforced, so `singleTransactionAmountMinor=0` (meaning no limit) vs `0` as “must be 0 amount” ambiguity exists — product must define `0` as “no limit” vs `null`.
- **No velocity / burst control** — not in `CustomerLimitProfile` nor `PilotControl`; `dailyTransactionCountLimit` is the closest (per-day count) but no per-minute/hour `velocity`.

**None of these gaps blocks `V1-HARDENING-03` audit** — this is audit-only. They are **gaps against a hypothetical V1 limit policy**, not gaps against the current **fee-free, balance-only V1 pilot** which `V1-008` tags as `METADATA-ONLY / REQUIRES PRODUCT DECISION`.

## 15. Implementation Dependencies (if unblocked → READY)

If product decides V1 **must** enforce limits (outcome → `READY`), the wiring is **not** greenfield — it reuses existing primitives:

- **Source of truth:** Keep **both** `customer_limit_profiles` (per-customer) **and** `pilot_controls` (global/ cohort guard) — A4 is the **decision aggregator**, A5 is the **command-time enforcer**.
- **Enforcement point:** **Inside** `TransferService.executeWithinTransaction` (and symmetrically `AgentFinancialExecutionService.execute`) — **same** `SERIALIZABLE` transaction that does `lockWallets` + `insert transfer` + `postJournal` + `idempotency.complete` + `audit` + `outbox`. **Order:** `IdempotencyService.reserve` (or `find existing` check) → `SELECT customer_limit_profiles WHERE customer_id FOR SHARE` → `SELECT customer_daily_usage WHERE customer_id AND date=canonicalDate FOR UPDATE` (create row if absent) → compute `dailyUsedAmountMinor = SUM(...)/usage.daily_amount_minor` **inside** transaction (or use `usage` row), call `LimitEngine.evaluate` **with resolved** `singleLimit` (`min(customer.singleTransactionAmountMinor, pilot.maxTransactionAmountMinor)` per policy) + `dailyUsed` + `amountMinor` → if `!allowed` throw `InternalTransferGateException` `PILOT_DAILY_*` / `LIMIT_EXCEEDED` `409/422` with `audit` `LIMIT_DENIED` (no journal) → else `UPDATE customer_daily_usage SET daily_amount_minor = daily_amount_minor + amount, daily_count = daily_count +1` + `INSERT transfer` + `postJournal`.
- **Pilot wiring for customer-app:** **Route customer-app `W→W` through `InternalTransferGateService.validate`** (or fold `PilotControlService.evaluate` directly into `TransferService`) — currently customer-app **bypasses** the gate; the gate already has `limitUsage` pass-through (`dailyUsedCount`/`dailyUsedAmountMinor`) and the correct `SERIALIZABLE`+`IdempotencyService`+`AuthorizationService`+`audit` pattern.
- **Agent wiring:** `AgentClass.applicable_limits` needs a **schema** (`zod` `jsonb` `{"CASH_IN":{"max":...,"dailyCount":...}}`) and `AgentCashInService`/`CashOutService`/`CashToCashService` must read `agentClass.applicable_limits` **inside** their `SERIALIZABLE` with `FOR UPDATE` on a future `agent_daily_usage` row if daily agent limits are decided.
- **No new ledger account** — limits do **not** require `FEE-REVENUE`/`COMMISSION` etc. (02A already `BLOCKED` separately) — this is **orthogonal**.
- **No new migration if `customer_daily_usage` is added as `transfers` aggregation** — one could compute `dailyUsed = SELECT SUM(amountMinor) FROM transfers WHERE sourceCustomerId=:id AND status='COMPLETED' AND createdAt BETWEEN dayStart AND dayEnd` **without** a new table, but that is **not concurrency-safe** without `FOR UPDATE` on a counter row (see §9) — so a **new `customer_daily_usages` migration** (`customer_id, date, currency, daily_count, daily_amount_minor, version, UNIQUE(customer_id,date,currency)`) is the correct primitive and **would be 1 migration `1785753600066-*`** (not 0) — **not created in this audit**.
