## Delivered boundaries

1. **Independent subscription.** `notification.v1` uses `notification_outbox_receipts`, not shared `outbox_events.status`, `attempts`, `published_at`, `last_error`, or another consumer's receipt. A row lock with `SKIP LOCKED` serializes one event's notification materialization. Every delivery/suppression and its receipt commit in one PostgreSQL transaction; provider calls happen afterwards. SQL/lookup failures roll back every intended row and create a separate safe `FAILED` receipt, bounded to five materialization attempts before quarantine. Replay converges on the existing `(event_key, recipient_id, channel)` unique key. `event_key` or `occurred_at` must be stable.
2. **Explicit non-delivery.** Unrecognized event types and schema versions, zero/partial transfer intents and unknown support-message visibility are `QUARANTINED` with fixed reason codes; known internal support notes are `SUPPRESSED`. They are not described as successfully sent. A `MATERIALIZED` receipt means all *currently specified* intents or skips are durable, not that any recipient received a message. No provider sends occur inside the materialization transaction.
3. **Owned sends.** `notification_delivery_attempts` and unique lease tokens fence concurrent workers. PENDING and explicitly retryable FAILED work is claimable. Every claim increments the attempt counter durably. An expired `CLAIMED` lease can be retried within the cap because no send was started; an expired `STARTED` lease, provider timeout/network exception, or indeterminate post-provider write becomes `UNKNOWN`, and is **not** automatically resent. Explicit permanent failures and exhausted retries are `DEAD`; explicit 4xx rejections other than 408/409 are bounded retries. No provider's idempotency window is assumed to be universal. `SENT` means provider acceptance, not delivery, read or settlement.
4. **SMS and direct security.** `NormalizingSmsNotificationProvider` wraps the existing configurable SMS token, not Arena 2's adapter. The registration OTP, temporary credential, desk OTP, ordinary SMS and controlled test-send paths use that token. Nigerian NSN, national `0`, bare `234` and `+234` forms converge to E.164 once; invalid/other-country formats fail before transport. The implementation reuses the existing Nigerian shape validator, not an allocation/carrier lookup or a multi-country numbering policy.
5. **Contacts and preferences.** Ordinary CUSTOMER SMS/email resolves only verified, undeleted contacts and an explicitly true channel preference; missing preference suppresses, and lookup errors fail closed and retry. Verification, opt-out and destination are rechecked immediately before send. Direct security flows remain separate and do not write OTPs/temporary credentials to the outbox. Transactional and informational customer notices both honor channel opt-outs pending explicit policy; no marketing consent is inferred or broadened. The existing C2C beneficiary exception permits an unregistered PHONE recipient only for `cash_to_cash.created`; a matching registered contact must be verified and every associated preference explicitly enabled.
6. **Privacy.** Ordinary persisted/provider payloads are event-specific allowlisted projections, not a generic denylist: ledger/journal IDs, rejection prose, contacts, unknown fields and credential values do not enter the new ordinary delivery payload. C2C keeps its narrower sender/amount/NGN/HTTPS-locator subset. Console SMS/email simulators retain only synthetic reference/time and emit fixed structured metadata, never body, subject, destination, recipient or payload. Direct security failure logs no longer interpolate untrusted provider errors/exceptions. Provider errors in new attempts are fixed first-party diagnostic codes. Stored message/destination and rendered email remain sensitive operational data requiring access control and retention policy.
7. **Email fidelity.** Materialization snapshots the subject, full text (up to 4,000 characters) and derived HTML. Retries use those exact stored representations rather than the then-current template; the event/channel enabled gate and contact/preferences are still rechecked. Legacy unresolved deliveries are quarantined instead of being rendered from new templates.
8. **Diagnostics.** Existing authorized delivery diagnostics accept `UNKNOWN` and `DEAD` and expose only allowlisted reason codes. `GET /internal/notifications/outbox-receipts` uses the existing `notification.view_deliveries` authorization and returns only notification consumer checkpoint metadata, without payload, destination, shared consumer data or message. There is no new Admin Web/mobile UI and no automatic redrive or reconciliation endpoint.

## Migration and upgrade behavior

New additive migration: `src/migrations/1785753600101-NotificationReliability.ts`. It adds receipts, attempt records, lease/scheduling and email snapshot columns; expands the delivery status check and message length. The existing production schema-compatibility marker is updated to 0101 so an entirely migrated schema is recognized; this is not a production-readiness assertion. It does not alter financial tables or shared-outbox consumer state. Historical `PUBLISHED` events are recorded as `QUARANTINED / LEGACY_PUBLISHED_UNVERIFIED`; legacy PENDING/FAILED deliveries become `UNKNOWN / LEGACY_DELIVERY_OUTCOME_UNKNOWN`, because older code could have called a provider without persisting the outcome. These are preserved for controlled investigation, not silently resent. SENT/SKIPPED evidence remains in place. The migration is intentionally **forward-only**: a down migration would destroy acknowledgements and re-enable unsafe resend semantics. A reviewed forward repair, deployment plan, backup/restore, data retention and operational reconciliation are still required before production use.

The subscriber does not use shared `available_at` as its retry gate, because another consumer can modify it. No current producer sets a future `availableAt`; a future scheduled-event producer needs an independently versioned notification not-before contract before use. The receipt table deliberately has no cascading outbox FK, so another consumer's retention operation cannot silently erase acknowledgement evidence. Attempt history protects against deleting a referenced delivery. Capacity/backfill impact, retention, orphan handling, legal holds and alerting require an Ops/Security design. Unknown non-notification events can create quarantine noise; a jointly owned subscription filter and reprocessing procedure remain open.

- **Arena 3 producer integration:** `src/transfer/transfer.service.ts` and `src/transfer/transfer-events.ts` must supply approved versioned source/destination customer IDs and safe event facts for completed transfers; the new subscriber quarantines zero/partial intended audiences rather than guessing. Coordinate with `src/notification/notification-event-map.ts`, `notification-template.service.ts`, `notification-channel-resolver.service.ts`, dispatcher/processor, migration 0101 and receipt diagnostic contract. Product/domain owners must separately decide deposit/withdrawal, agent cash-in/out, C2C claim/expiry and support audience/status contracts; no producer changes were invented here. No automatic C2C expiry refund, release, fee, commission or physical-handover rule was introduced.
- **Arena 4 independent acceptance:** test the final integrated SHA, not this handoff as independent evidence. Reproduce clean and 0100-to-0101 upgrades; two independent shared-outbox consumers; unknown/zero/schema cases; insert rollback; replay; real concurrent PostgreSQL claims; claim/started crash and stale-owner fencing; post-acceptance database failure; bounded explicit rejection versus ambiguous timeout; phone/C2C/OTP fake transport; verification, consent and DB outages; 3,800-character email template drift; log/HTTP/DB sentinels; disabled configuration; funding and transfer accounting invariants; current maker-checker/MFA/egress controls; and Arena 2 F-01/F-05. - No receipt/webhook ingestion, end-recipient delivery confirmation, operational redrive/reconciliation, provider failover, approved alerting, retention/legal-hold policy or rollout/rollback runbook is delivered. A provider timeout is deliberately ambiguous and needs operator reconciliation. A preference/contact can change between the last check and the network call; stronger revocation guarantees require product/security design. Existing historical payloads/logs were not scrubbed by this migration. Financial IDs remain in shared outbox/domain data where already present; this work minimizes the notification delivery projection, not every authorized financial/audit surface.
- Worker enablement and email remain dark by default; there is no change to production configuration, authorization catalogue, compliance policy, agent mobile, Admin Web, funding controllers or financial accounting code. Provider test adapters retain requests only in explicit test fixtures. Production-like console policy and staging misuse prevention still require owner review even though console output is redacted.
