# ADR-0023: Customer Identifier and Reference Conventions

- **Status:** Proposed for A1 architecture review
- **Date:** 2026-08-05
- **Decision owners:** Architecture, Customer Engineering, Security, Operations, Wallet, Ledger, Finance, Risk, Compliance, and future partner owners
- **Scope:** Customer, account, reference, event, correlation, causation, request, trace, and idempotency identifiers
- **Task:** A1T11 — Draft ADR-0022 and ADR-0023
- **Implementation status:** Decision input only; no identifier service, schema, API, migration, or runtime behavior is implemented

## Context

MonieNaija has several identifier classes with different owners and lifecycles:

- Customer UUIDs and customer references.
- Customer-wallet, financial-wallet, ledger-account, journal, and line IDs.
- Case numbers, beneficiary references, funding-instrument references, aliases, and payment references.
- Event, audit, correlation, causation, request, and trace IDs.
- Idempotency scopes, keys, and request hashes.
- Provider and external identifiers that must be mapped without replacing internal identity.

A single generic “reference” rule would create collisions, leak sensitive values, or allow a display/provider value to be treated as financial truth. A bare idempotency key also cannot safely deduplicate commands from different owners. The A1 identifier/privacy review defines the current conventions; this ADR provides the identifier contract required by A2, A3, and A5.

## Decision

### 1. Canonical versus reference identifiers

- `Customer.id` is the canonical customer UUID for customer-owned records. It is generated once, immutable, serialized in lowercase hyphenated form, and never reused.
- Each bounded context owns its record UUIDs. A record UUID identifies that record type; it does not become a customer, wallet, ledger, or provider identity merely because it is copied into another table.
- Customer references, wallet aliases, case numbers, beneficiary references, funding-instrument references, and payment references are lookup/display/correlation values. They cannot authorize a command, prove ownership, establish settlement, or replace a canonical foreign key.
- Wallet and ledger IDs remain owned by `wallet`/`ledger`. Customer-wallet metadata requires an explicit A3 binding and may not copy balances or journal truth.
- Provider identifiers remain in a provider/type namespace and require an explicit mapping to an internal record. A provider value cannot replace an internal UUID or ledger identifier.

### 2. Normalization

For a value used in lookup or uniqueness, the owner validates type and length, trims surrounding whitespace, applies only its declared domain rule, validates the normalized result, and enforces the rule in both the owning service and database constraint/index.

Current canonical rules are:

- **UUID:** accept valid UUID syntax at an internal boundary and serialize lowercase hyphenated text. Do not recycle after soft deletion.
- **Safe internal reference:** customer references, case numbers, beneficiary references, funding-instrument references, wallet aliases, and MFA enrollment references use trimmed lowercase ASCII safe form `^[a-z0-9][a-z0-9_.:-]{0,159}$` unless a domain-specific contract states otherwise.
- **Beneficiary destination comparison:** customer-beneficiary duplicate detection uses a trimmed/lowercase comparison value with whitespace, `(`, `)`, and `-` removed. It is scoped to the customer and active/non-deleted beneficiary records; destination values remain sensitive.
- **Payment reference:** generated by the shared payment-reference registry as `MN` plus a zero-padded sequence. It is immutable and globally unique across its participating payment types.
- **External identifier:** preserve provider-required representation and normalize only under the provider contract. Namespace by provider and identifier type.
- **Request/correlation/trace ID:** bounded printable values at the HTTP boundary; propagate existing values rather than generating module-local replacements. They are operational context, not business keys.
- **Causation ID:** the immediate parent command/event identity in a future versioned event envelope. It is not a customer reference or a newly generated unrelated value.
- **Idempotency key:** trim at the command boundary, reject empty/overlong values, preserve case as an opaque token, and never place personal data or secrets in it. Hash the canonical command request separately.

Free-form names, comments, narration, evidence descriptions, and display labels are not identifier namespaces. They are trimmed and bounded but are not lowercased or made unique by this ADR.

### 3. Uniqueness scope

| Identifier namespace           | Owner                              | Uniqueness scope                                                                           | Soft deletion / expiration                                                      |
| ------------------------------ | ---------------------------------- | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------- |
| Customer UUID                  | `customer`                         | Canonical platform customer identity                                                       | Never reused                                                                    |
| Customer reference             | `customer`                         | Global customer-reference namespace                                                        | Not reused, including soft-deleted customer records                             |
| Customer-wallet UUID           | `customer-wallet`                  | Customer-wallet record type                                                                | Never reused                                                                    |
| Financial wallet UUID          | `wallet`                           | Wallet record type; customer/currency uniqueness is a separate invariant                   | Never reused                                                                    |
| Ledger account UUID/code       | `ledger`                           | Ledger account identity/code namespace                                                     | Not reused without ledger governance                                            |
| Journal UUID and line number   | `ledger`                           | UUID per journal; `(journalId, lineNumber)` for a line                                     | Posted financial records are retained and immutable                             |
| Compliance case number         | `customer-compliance`              | Global case-number namespace                                                               | Not reused, including soft-deleted cases                                        |
| Customer beneficiary reference | `customer-beneficiary`             | Global beneficiary-reference namespace                                                     | Not reused, including soft-deleted records                                      |
| Funding-instrument reference   | `customer-funding-instrument`      | Global instrument-reference namespace                                                      | Not reused, including soft-deleted records                                      |
| Wallet alias                   | `customer-wallet`                  | Global among active/non-deleted aliases                                                    | Reuse is a separate alias policy; wallet UUID is never reused                   |
| Beneficiary destination        | `customer-beneficiary`             | `(customer UUID, normalized destination)` among active/non-deleted records                 | Lifecycle rule controls reuse; preserve history                                 |
| Payment reference              | `payment` registry                 | Global across transfer/deposit/withdrawal/quote/virtual-account records using the registry | Never released                                                                  |
| Provider account/reference     | Provider adapter / financial owner | `(provider, identifier type, provider value)`                                              | Provider contract controls reuse; preserve mappings                             |
| Event/outbox/audit ID          | Operations/event owner             | One immutable persisted event/audit record                                                 | Retention may remove the record; the ID is not reassigned                       |
| Correlation/request/trace ID   | Production/HTTP or workflow owner  | Request/trace/workflow scope; no business uniqueness guarantee                             | Retained only under operational evidence schedule                               |
| Causation ID                   | Command/event producer             | Reference to one immediate parent fact                                                     | Retained with event/command evidence                                            |
| Idempotency key                | Operations plus command owner      | `(command scope, key)` while retained/unexpired                                            | Expiry permits a future new reservation; it does not delete the source resource |

“Global” is global within the declared namespace or registry, not a requirement that human references across unrelated domains share one table. Database constraints remain the final concurrency guard.

### 4. Idempotency contract

A retryable command must define:

- Command owner and explicit scope.
- Opaque idempotency key.
- Canonical request hash.
- Resource type and resource ID when an outcome exists.
- Retention/expiry period.
- Replay behavior for an identical request.
- Conflict behavior when the same `(scope, key)` is used with a different request hash.

The shared Operations primitive uses `(scope, idempotencyKey)` uniqueness. Financial command tables may also enforce a local key where the command lifecycle requires it, but the local rule must not contradict the command owner’s scope. An idempotency key is not a permanent business ID, credential, authorization token, or substitute for the created resource ID.

### 5. Correlation and event identifiers

A command/event chain uses distinct identifiers:

```text
requestId + traceId + correlationId
        |
        +--> command scope + idempotency key + request hash
        |
        v
aggregate/entity UUID + customer UUID where applicable
        |
        +--> audit event ID and entity ID
        +--> journal ID and payment reference where financial
        +--> outbox event ID + aggregate ID + event type
                         |
                         +--> causation ID for the immediate parent fact
                         +--> same workflow correlation ID
```

- `requestId` identifies an HTTP request attempt.
- `traceId` identifies an observability trace.
- `correlationId` joins a business/request workflow and may cross commands/events.
- `causationId` identifies the immediate parent command or event.
- `eventId` identifies one durable event fact; it does not identify the aggregate or source resource.
- `aggregateId` remains owned by the aggregate domain.
- `entityId` in an audit event identifies the audited record; audit ownership remains Operations.

The current outbox record persists event and aggregate IDs but does not yet have explicit persisted correlation/causation columns. Before external publication or a broker/inbox is introduced, the versioned event envelope must carry these fields with a minimal payload. This ADR does not change the outbox schema.

### 6. External identifiers

- Store a provider name, identifier type, provider value, and mapped internal record where an external boundary exists.
- Validate callbacks and provider references as untrusted input; matching a string is not proof of authenticity or settlement.
- Do not expose internal UUIDs, ledger IDs, idempotency keys, or operational correlation trails to a provider unless an approved contract requires a mapped value.
- Do not use an external account number, phone number, bank code, provider reference, or partner ID as the canonical customer or financial identifier.
- Field-level classification, retention, consent, and sharing rules remain governed by A1T07 and later ADR-0024 review.

## Alternatives considered

### Use customer references as primary keys across modules

Rejected. References are human/API values with domain-specific normalization and disclosure concerns. Canonical UUID ownership is safer for joins, migrations, and lifecycle history.

### Make all references globally unique in one universal registry

Rejected. It would couple unrelated namespaces and make provider, case, financial, and customer lifecycle rules harder to evolve. Global uniqueness is required only where the owner declares it.

### Treat a bare idempotency key as globally unique

Rejected. Different command owners or tenants can legitimately issue the same opaque key. `(scope, key)` is the minimum safe uniqueness boundary.

### Reuse references after soft deletion by default

Rejected. Reuse can cause support, audit, legal-hold, and external-mapping ambiguity. Reuse is allowed only for a specifically approved active-only namespace such as wallet aliases.

### Put correlation and causation into one generic ID

Rejected. Correlation joins a workflow; causation explains the immediate parent. Combining them breaks replay analysis, tracing, and support evidence.

### Let provider identifiers replace internal identifiers

Rejected. External namespaces, lifecycle, reuse, and trust assumptions differ. An explicit adapter mapping preserves internal authority and reconciliation.

## Consequences

### Positive

- Customer identity, financial identity, operational context, and provider identity remain separate.
- Retry behavior is deterministic and scoped to the command owner.
- A5 can correlate HTTP requests, commands, audits, journals, outbox facts, and reconciliation evidence without treating them as one identity.
- Global uniqueness is preserved where history and external mapping require it, while local namespaces remain decoupled.
- Future A2/A3/A5/A6 work has explicit identifier inputs before adding runtime boundaries.

### Trade-offs

- Owners must maintain normalization and database constraints together.
- Support and reconciliation tools need mapping tables/queries instead of guessing from display values.
- Event envelope evolution is required before external publication.
- Retention and legal-hold decisions can delay deletion of operational identifier records.
