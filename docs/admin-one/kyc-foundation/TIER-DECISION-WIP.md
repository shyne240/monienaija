# Tier decision work in progress — not a transition service

This increment implements only a pure, unconnected Tier 1/Tier 2 candidate evaluator in `src/kyc-verification/kyc-tier-decision.ts`. **No customer KYC assessment or tier is changed, no job is scheduled, and no automatic transition is operational.** Do not wire this function to a customer mutation or treat its return value as authorization.

The evaluator requires an explicitly effective, approved, regulatory-reviewed policy; applies the requested BVN-or-NIN Tier 1 and BVN-and-NIN Tier 2 floor; and combines separate regulatory and operator requirements additively. Tier 2 inherits Tier 1 requirements. It does not claim that the requested floor alone is sufficient under applicable regulation. It excludes synthetic, expired, rejected and revoked evidence; flags invalid, conflicting, mismatched or ambiguous evidence for review; and returns only selected evidence identifiers. Review and unconfigured results have no proposed tier. Tier 3 and Class of Service are not implemented.

The policy approval flag and provenance values are **inputs to an isolated algorithm, not trusted attestations**. A future authorized service must load an independently governed policy and verify provenance, consent, subject/identity binding, and evidence state from authoritative stores under appropriate locks. Passing a caller-created object to this function cannot establish any of those facts. The test fixtures imitate trusted evidence solely to exercise the algorithm; no real provider was contacted.

## Blocking integration findings

1. `CustomerService.createKycAssessment` currently updates `customers.kyc_level` and `customers.kyc_status` and supersedes the current `customer_kyc_assessments` record. Existing direct assessment creation has not been removed, so it can still bypass this evaluator. A complete implementation must replace or mediate every tier-changing path without introducing a second source of truth.
2. Existing Cash-to-Cash cash payout checks both the customer and current assessment for `APPROVED` in `src/agent/agent-cash-to-cash-claim.service.ts`. Other transaction code also uses `customers.kyc_status`. Automatically writing `APPROVED` can therefore affect financial eligibility even if no wallet or transaction-permission code changes. This conflicts with the instruction not to change transaction permissions unless the intended boundary is clarified; no such behavior was introduced here.
3. The current registration provider is synthetic-only, and Monnify is explicitly unavailable. `kyc_verification_attempts` is an isolated foundation, not a production-wired, authorized evidence ingestion pipeline; the existing advisory method needs a trusted identity binding supplied by its caller. An untrusted provenance string or dummy identity cannot establish real evidence.
4. There is no approved persisted regulatory policy, policy approval workflow, trusted event producer, reevaluation queue/worker, expiry scheduler, or transactional decision/audit adapter in this increment. These must be designed and tested before real transitions. Historical legacy assessments also need an explicit safe compatibility and downgrade/revocation approach.
5. A complete implementation needs concurrency/idempotency, evidence and policy-change race tests, authorization, approval/downgrade audit completeness, PostgreSQL 16 integration and full application/migration-chain validation. None of those are claimed by the pure-function tests here.

No migration, live-provider call, production configuration change, customer state change, wallet activation, transaction permission change or deployment is included.
