# Secure KYC foundation — Batch 1 implementation report

## Status and safety boundary

This is a **partially completed, isolated foundation, not an onboarding or production-ready KYC system**. No endpoint, Nest module, worker, existing customer flow, tier, permission, wallet, transaction, configuration, `.env`, existing database, or deployed environment has been wired or changed. No live provider calls or credentials were used. The migration is additive and has not been applied to any actual database. **Do not enable or integrate this code until the remaining controls below are completed and approved.**

The existing generic `IdempotencyService` removes expired records and cannot safely guard a paid request of unknown outcome indefinitely; this batch therefore adds a separate persistent reservation rather than reusing its expiry behavior. It uses existing TypeORM transaction patterns and the existing Monnify adapter, but places narrowly scoped KYC metadata in a separate private audit table rather than exposing it through the generic audit listing. Existing KYC assessments and eligibility/financial engines are not modified.

## Implemented

- `src/kyc-verification/kyc.types.ts`, `kyc-orchestrator.ts`: provider-agnostic contract, explicit policy, validation, safe attempt reservation before calling the provider, HMAC-bound request/idempotency identity, bounded provider deadline, and fixed non-PII errors. Exceptions, timeouts, unrecognized provider outcomes and outages are `UNKNOWN`, not mismatch. No automatic provider retries; `REVIEW` can be retried only subject to explicit caps and cooldowns. Disabled policy blocks dispatch.
- `monnify-kyc.provider.ts`: wraps the existing Monnify adapter without rewriting it. BVN uses its details-match result; NIN compares provider-returned first name, last name and date of birth against supplied trusted registration details, not the provider's `ninInformationMatch` flag. Discrepancies are `REVIEW`, not a fraud verdict. The caller must independently establish identity ownership and load authoritative customer data; matching alone cannot establish ownership or approval.
- `postgres-kyc.store.ts` and migration `1785753600104`: customer-bound, versioned consent grants and withdrawal; append-style attempt history, request MAC and version, timestamps, bounded evidence validity, HMAC-only provider-reference correlation, and private consent/attempt audit records. Existing customer rows and a provider lock serialize reservations; scoped request UUIDs are unique and never expire. Same-key replay cannot redispatch; changed request content conflicts. In-flight, unknown or consent-withdrawn attempts block new requests for that customer's identifier kind even under a new key or consent. Existing unexpired matches also block repeats. Explicit policy controls per-consent attempt cap, customer/provider windows and cooldown. Reservation and private audit are atomic. A crash before completion leaves `DISPATCHING`, requiring review; completion after withdrawal/expiry cannot produce a usable match.
- `kyc-policy.ts`: explicit, fail-closed **advisory** evidence evaluator. `PostgresKycStore.evaluate` filters BVN/NIN evidence to current matching, unrevoked consents and compares a keyed MAC of the current trusted identity details against the original. Missing/changed identity, expiry, withdrawal or missing policy cannot satisfy the evidence check. Other evidence must come from trusted server-side sources. The evaluator does **not** automatically run on customer events or write KYC levels/eligibility/permissions. History returns historical outcomes, not a live entitlement decision.
- `kyc-future-capabilities.ts`: contracts only for biometric and future digital address, utility and GPS capabilities; no provider implementation or Tier 3 activation.
- No raw BVN, NIN, name, phone, DOB, provider response, or credentials are persisted in the new tables. MACs and verification metadata remain sensitive personal data and require access controls, key protection and retention governance. Provider references are stored only as irreversible keyed MACs, so operational reconciliation requiring the actual reference is **not yet supported**.

## Remaining blockers before Batch 1 is production-ready / before any live use

1. **Authorization and consent:** authenticate the customer or authorized assisted-onboarding actor, bind the subject and trusted profile/verified phone to the request, enforce purpose and immutable notice/version/fee disclosure, provide restricted history/audit access, and establish appropriate legal/privacy, retention, encryption-at-rest and database access controls. Internal store methods alone are not authorization.
2. **Provider/config governance:** define and approve persisted provider and KYC policy configuration, supported methods, budget/fee rules, provider-level rate configuration shared consistently across instances, secret management and audited maker-checker controls. The injected policy is not an Admin configuration system. HMAC key provisioning, secure rotation/version lookup and recovery are not implemented; changing the key version causes old evidence/replays to fail closed.
3. **Reconciliation and fraud:** implement authorized resolution of stranded/unknown operations with Monnify's confirmed billing and reconciliation contract. Do not retry them automatically. Uniqueness is customer/request and customer/kind scoped; it does not detect shared identifiers across different customers, different applications or external systems. A protected identity-ownership/duplicate-risk design is still required. A provider reference MAC alone is not sufficient for all reconciliation cases.
4. **Eligibility/tier lifecycle:** hook evaluation to trusted, versioned evidence and customer profile changes, decide expiry/revocation/downgrade/re-verification rules, and provide transactional checks at the point of any tier change. The present evaluator is callable but not automatically triggered, and writes no assessment. Add restricted audited tier changes and conflict/race handling only after policy approval. Existing registration may still activate customers before KYC; this batch does not enforce the requested new Tier 1 financial restriction and does not change legacy behavior.
5. **Operational readiness:** review migration and test on the supported PostgreSQL 16 stack in an isolated environment; ensure private audit records cannot be read through broad DB roles; build safe access/review APIs, monitoring, recoverability, idempotent history retention and load/concurrency tests. Provider network cancellation is best-effort; an adapter may complete after orchestrator timeout, so `UNKNOWN` must remain blocked.
6. **Provider access:** Monnify account entitlement and actual billing remain unverified. Its official NIN endpoint and BVN response examples conflict; see `docs/admin-one/monnify-batch-1/README.md`. Resolve contract, account/IP access and cost, and obtain separate explicit live authorization before any live request. Biometric capabilities are not attributed to Monnify.

No KYC tier, class, transaction limit or financial privilege is granted by this batch. Policies for customer classes, verification fees and funding remain outside this batch and disabled/unimplemented.

## Verification performed

- Targeted TypeScript `npx tsc --noEmit --incremental false --pretty false` and ESLint on all new TS files passed.
- Four targeted unit/regression suites: 43 tests passed, including 8 KYC foundation tests and 24 existing Monnify adapter tests. A parallel run emitted a worker-exit warning; a serial `--detectOpenHandles` rerun passed without a warning. This does not prove the full suite passes.
- Nine synthetic SQL integration tests passed on a newly initialized disposable PostgreSQL **18.4**, using a unique Unix socket and synthetic-only schema, no TCP listener, no application `.env` or existing database. They exercised concurrent idempotency, changed input conflict, private audit rollback, consent withdrawal during dispatch, outage unknown handling, cooldown and changed retry cap, cross-customer provider rate limit, crash reservation, and refusal to destructively roll back history. The cluster was stopped and deleted. PostgreSQL 16 and full migrations remain untested.
- The isolated test is deliberately outside the normal Jest `*.spec.ts` and PostgreSQL integration suite; its test file checks the socket path and database data-directory/listen settings before making schema changes. Run it only against a freshly created disposable socket-only cluster using `KYC_ISOLATED_TEST_SOCKET=<isolated socket>` and `node -r ./test/support/mission-25c-network-guard.cjs ./node_modules/jest/bin/jest.js --maxWorkers=2 --testRegex='[.]isolated-pg[.]test[.]ts$' --runTestsByPath -- test/kyc-foundation.isolated-pg.test.ts`. It will not use normal app DB settings.
- An initial incorrectly formed Jest command selected unrelated integration suites; their disposable-cluster guard rejected them before database access. The corrected command ran only the synthetic suite.
