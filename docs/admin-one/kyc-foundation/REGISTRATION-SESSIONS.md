# Pre-customer registration sessions — prior partial checkpoint

This historical report describes commit `d110de4`. For the subsequent synthetic application integration and current limitations, see [REGISTRATION-INTEGRATION.md](REGISTRATION-INTEGRATION.md).

This increment implements and tests an **unwired internal service**, not an end-to-end application feature. No endpoint, Nest provider, user-facing flow or pre-customer identity dispatch is enabled. It does not satisfy the requested completion standard and must not be treated as authorization to begin Batch 2 or enable live KYC.

## Implemented

`KycRegistrationSessionService` creates an opaque 256-bit pending credential for a normalized Nigerian phone, stores only its SHA-256 digest, and binds every challenge to the session. Its OTP uses the existing registration constants (six digits, salted PBKDF2-SHA256, five-minute challenge, five guesses and 60-second resend cooldown) and the existing notification provider interface. The new tables are independent of the legacy registration challenge and do not consume its one-time token. The session lasts at most 15 minutes; verifying a challenge once atomically consumes it, removes the pending token hash and issues a different 256-bit limited authorization credential (only the digest is stored). No customer, wallet or active customer session is created.

Challenges, counters, audit events and consent persist in PostgreSQL. Per-phone and per-IP fixed-hour session creation, OTP issuance and verification counters are committed separately, including denials. Phone-level issuance locking and cooldown apply across sessions using this new service; recent codes for the same phone are not reused while still valid. Session and challenge row locks serialize verification. A request ID makes repeated issuance a no-op and makes consent creation replayable only with the same payload. A lost verification response cannot retrieve the authorization: recovery is to start a new, rate-limited session and repeat phone verification, not to replay the OTP. Revocation and expiry fail closed.

Consent records are scoped to the verified session, kind, notice version and expiry and can be withdrawn. A helper checks the current authorization and consent transactionally. **It is not a dispatch authorization:** the transaction ends when the helper returns, so session or consent can change before a later provider call. It must not be used as a check-then-dispatch security boundary. The service contains no identity verification or provider dispatch; synthetic SMS is used in tests, not synthetic identity verification.

## Remaining work specific to this feature

- Wire and test the service through an appropriately guarded application API, with bearer-only transport, trusted source IP, generic responses, logging redaction, approved consent notice/version policy, configuration and operational limits. The present service trusts its caller's source IP and notice version. Confirm notification delivery behavior and observability without storing or logging OTPs.
- Integrate authorization and consent **atomically with an actual pre-customer identity-request reservation/dispatch design**, including withdrawal/revocation races, idempotency, no duplicate billable calls, ownership continuity with existing customer claims, and handling of an uncertain outcome. The existing orchestrator and claim schema require a customer ID. The helper alone cannot establish that any actual request is protected.
- Test the real HTTP path and its runtime guard, a synthetic identity provider, actual process restart/reconnection, concurrent independent processes and migration chain against the real application schema. Current tests reconstruct the service object against the same database, not a full process restart. Test integration with existing registration, including abuse budgets shared across the legacy and new flows: these limits are currently separate, so both paths can be used independently. Preserve compatibility and avoid generating active privileges.
- Review rate bucket retention/cleanup, recovery and throttling UX, availability and CPU impact of synchronous PBKDF2; define audit retention and privacy handling for stored phone numbers. Session creation is not idempotent, and delivery can be uncertain after a crash. OTP-issuance replay does not redeliver and consumes rate budget. A fresh request after cooldown is needed to recover. No claim is made about real SMS delivery.
