# Batch 2A — isolated synthetic draft completion

This is **not production registration or KYC**. It creates a persistent customer DRAFT only when NODE_ENV=test, an in-memory test notification provider is installed, and the database is a socket-only, PostgreSQL 16 disposable test cluster in the explicitly verified workspace namespace. The completion endpoint fails closed anywhere else, even if synthetic verification is available. The mobile simulation availability endpoint currently checks only the test runtime/SMS sink, so it can show the simulation in an environment where completion will return 503. A portable, explicitly provisioned isolated demo environment is still needed; never relax this guard to use a production or shared database.

For a BVN or NIN demo, verify a test phone via the in-memory sink, enter `Synthetic Person`, date of birth `2000-01-01`, accept synthetic consent, and use a fixture between `00000000000` and `00000000009`. These are fake fixture slots, not genuine identifier ownership. Each slot can be claimed once per kind in the disposable database; pick a new slot for another subject. Tap Create test draft after MATCH. The mobile app stores the session authorization and attempt ID securely, not the OTP or identifier; an interrupted completion can be retried while authorization and consent remain valid. If the verification response itself was lost, repeat the same verification request using the same test fixture. Expired/revoked sessions cannot recover.

A transaction locks the verified session, matches the exact attempt to a profile/phone HMAC binding and active consent, and atomically creates the existing customer, profile, verified phone and separate synthetic provenance link. The session lock, unique link constraints, and unique fixture claim serialize retries and competing claims; conflicts return a generic response. The fixture hash is deliberately a small synthetic lookup key and is **not** suitable for real identifiers. The synthetic link is not genuine KYC evidence and cannot be read as approval by the governed tier evaluator. No credentials, PIN, tier transition or wallet is created.

A permanent customer synthetic marker, customer status/KYC constraint, and database triggers for the known customer financial tables block synthetic activation and attachment of financial records; the customer service also rejects activation. These protections do not substitute for database role separation: a privileged database administrator can alter or disable constraints. The older wallet subsystem accepts opaque customer identifiers, so unrecognized aliases and any future financial surfaces require a separate cross-domain policy review. The existing general administrative activation path for **non-synthetic** customers is unchanged and remains a production-readiness blocker until genuine verification and all applicable regulatory requirements are enforced. Synthetic verification must never be promoted to genuine evidence.

This does not implement trusted provider integration, production consent, production identity ownership, credentials, transaction PIN, automatic tier transitions, wallet activation, Tier 2/3, or Classes of Service. No live provider or notification delivery is used. Audit and data retention, privilege separation, provider entitlement, applicable policy, and production activation controls require separate approval.
