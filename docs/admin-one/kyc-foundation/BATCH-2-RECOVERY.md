# Batch 2 recovery — partial synthetic journey, not complete

The mobile registration screen now runs a **test-only simulation**, not a real customer registration. It is shown only in a development build when the backend's simulation-availability endpoint confirms `NODE_ENV=test` and an in-memory test SMS provider. The backend independently enforces `NODE_ENV=test` on the synthetic profile and verification paths, and governance must route to SYNTHETIC. Outside that runtime the screen says registration is unavailable. Do not use real identity numbers or personal data in this simulation.

A Nigerian phone starts the existing registration session; OTP is bound to that session and uses the existing notification interface and cooldown. The user may enter a synthetic first name, last name, birth date and optional email, choose BVN or NIN, accept the synthetic-only consent and submit the sole allowed dummy identifier `00000000000`. The provider's test fixture matches `Synthetic Person`, date of birth `2000-01-01`; otherwise it returns REVIEW. The server takes the phone from the verified session, not from the request. A session row lock protects the saved profile; a profile cannot be changed once an attempt exists, and the profile is rechecked under that lock before dispatch. This remains synthetic registration-attempt data, not genuine provider evidence. The production evidence reader remains unavailable.

The app uses a purpose-limited registration bearer rather than a customer bearer and does not purge customer authentication on a registration 401. It stores the temporary session credential and request identifiers in the existing secure-storage abstraction for resumption; it does not persist the OTP or identifier. The service preserves existing session expiry and one-time OTP semantics: if the OTP verification response is lost after consumption, restarting and re-verifying is necessary. Retry uses the same verification request ID and ambiguous outcomes stay pending without redispatch. The simulation has not been subjected to device/browser penetration, secure storage failure, or accessibility testing. Data retention and cleanup for synthetic profile rows must be defined before any wider use.

## What is still missing

There is **no complete Tier 1 journey**: synthetic registration attempts are not linked to an authoritative customer, no applicable requirements are collected, no tier assessment is created by this flow, and no password, PIN, customer, wallet or account is created. The app explicitly says so after a simulated match. Real production evidence, legal consent, provider and regulatory controls remain external dependencies. Work still required includes a single customer lifecycle, a transactional bridge from session consent and provider result to identity-bound evidence, identity/duplicate ownership checks, approved-policy requirements, credentials and PIN, safe test-only account isolation, atomic activation and genuine production activation gating.

**Universal activation enforcement remains unimplemented.** Existing administrative customer activation and wallet-creation paths can still provide active statuses without this KYC boundary; imports, direct database access, other financial privileges and reactivation also need a complete transactional design and regression review. The previously disabled legacy self-service completion continues returning 503. Existing tests that expect legacy phone-only registration success remain incompatible; they have not been silently rewritten to assert the old behavior is safe. Do not deploy as completed onboarding.

## Validation

A real full AppModule with all migrations was booted on disposable PostgreSQL 16.14 with a synthetic notification provider. Both BVN and NIN followed session creation, OTP, synthetic profile, consent and simulated MATCH through HTTP; customer, credential and wallet counts did not change. This does not demonstrate complete registration. Isolated API tests additionally exercise missing consent, mismatch, timeout, concurrent duplicate dispatch, authorization, production-mode rejection and profile locking. Mobile tests mock the backend and check the two simulation paths and resume. No real notification, provider call, financial transaction, production data or secret was used.
