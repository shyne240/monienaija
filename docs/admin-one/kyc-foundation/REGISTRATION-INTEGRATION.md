# Registration-session application integration: synthetic verification only

This increment wires the existing pre-customer session into the application and exercises a **synthetic-only** identity request. It creates no customer or wallet and does not enable Monnify, real KYC or financial privileges. A synthetic `MATCH` is a simulation, not identity evidence; the response is explicitly marked `simulated: true`, and its history is stored separately from customer KYC evidence.

## API and demonstration

All paths below are POSTs beneath `/api/v1/customers/registration-sessions/`; responses include `Cache-Control: no-store`. After `start`, all calls use `Authorization: Bearer <session credential>` and include `sessionId` in the body. The pre-verification bearer is invalidated on OTP verification and replaced with a distinct short-lived authorization; neither is a customer login.

1. `start` accepts a Nigerian phone and returns `id` and pending `token`.
2. `otp` takes `sessionId` and a UUID `requestId`; it issues to the session's stored phone, not a client-supplied verification phone. The same request ID is a no-op on replay; a fresh ID requests a resend subject to cooldown and budgets.
3. `otp/verify` takes the six-digit `code`; one winner atomically consumes it and obtains `authorization`. Lost responses require a new rate-limited registration session and OTP; the old OTP cannot reissue authorization.
4. `consent` takes `kind` (`BVN`/`NIN`), `requestId`, `accepted: true`, `noticeVersion: "synthetic-test-v1"` and an ISO expiry no later than the session expiry. This synthetic-only notice marker is **not** an approved legal notice for real verification. `consent/withdraw` and `revoke` invalidate subsequent use.
5. `verification` takes `consentId`, `kind`, `requestId`, and the only accepted synthetic identifier `00000000000`. The sole route is the in-process `SYNTHETIC` provider. It runs through the existing `KycOrchestrator` using a pre-customer-specific store and provider guard; all supplied identity details are fixed synthetic values. The result is persisted in `kyc_registration_attempts`, never in customer evidence. `status` returns the authenticated session state and expiry without returning the phone or credentials.

These public route entries are authenticated by the controller's limited bearer checks rather than the customer/workforce guard. Source IP is taken from Fastify's `req.ip`, using the application's existing proxy-trust configuration. Secrets are not put in paths, query strings, database fields, audit details or this service's logs. SMS uses the existing direct notification provider abstraction and OTP policy; the tests substitute an in-memory synthetic provider. Full logging behavior of every possible external SMS adapter was not live-tested.

## Atomic verification boundary

The store locks the session and consent, checks the session is verified, unexpired and authorized, checks active consent and the synthetic purpose/route, enforces session/consent/provider limits, then persists a reservation containing a keyed MAC of the exact request. A replay with the same request returns the stored attempt without another dispatch; changed consent or request data conflicts. The guarded provider consumes that exact reservation at most once, under the same locks, rechecking authorization, expiry, consent and routing immediately before setting `DISPATCHING`. After consumption is committed, a final locked recheck occurs and the synthetic provider is invoked while the session and consent locks are held; it does not wait for the provider result under those locks. The application no longer exposes the earlier check-only helper.

`DISPATCHING` is the durable at-most-once consumption marker; the locked provider invocation is the dispatch boundary. Changes committed before that invocation prevent dispatch. A revocation or expiry after invocation cannot unsend an in-flight call; completion rechecks current state and does not persist a match if authorization or consent is no longer valid. Provider timeout or an ambiguous synthetic error is `UNKNOWN`, and an identical replay does not dispatch again. A crash with a `RESERVED` or `DISPATCHING` attempt leaves it blocked rather than automatically repeating it. No real paid provider may be substituted into this simulation path: ownership continuity, real provider governance, reconciliation, billing/idempotency guarantees and approved policy remain outside this increment.

Legacy OTP and the new service share the existing A2 per-IP/per-phone issuance and per-phone verification token buckets. A shared per-phone cooldown was added to both paths; legacy cooldown denial keeps its generic accepted response. The new path retains its additional durable session limits. Old registration endpoints, OTP challenge/token consumption, customer creation and wallet behavior are otherwise unchanged.

## Limitations and follow-up before real use

- The tests build a small Nest application from the real controller, route guard and production module factories; they do **not** boot the complete `AppModule` or validate the full production migration chain/schema. Legacy regression coverage is primarily unit-level; the shared-cooldown integration test uses the real legacy method with synthetic repository stubs in one direction. An end-to-end regression against a complete isolated app schema remains warranted.
- This is a simulation path only, not a production BVN/NIN verifier. Do not substitute a live provider or treat simulated consent as lawful real verification consent. Approved notice/purpose, real provider capability and billing contracts, durable ownership handoff and reconciliation are still needed for a later authorized stage.
- Counters and phone records need an approved retention/cleanup policy; abuse limits and trusted proxy configuration need operational review. Public session creation is not idempotent. OTP send failures are deliberately not disclosed to prevent sensitive provider details leaking; recovery is a later bounded resend or a new session. Provider acceptance does not prove SMS delivery.
- The overall KYC foundation and Batch 2 are not thereby complete or authorized. No Tier 1/2/3 or financial-policy work was undertaken here.
