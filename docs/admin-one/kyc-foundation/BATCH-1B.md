# Batch 1B — KYC foundation continuation

**Status: partial development checkpoint, not complete and not production-ready.** This is disconnected from HTTP, registration, customer activation, wallets, transaction authorization and mobile/Admin UI. No real provider, identity, credentials or existing database was used. Do not enable the isolated adapter or wire these services into a live system.

## Implemented

- `PostgresKycStore` now requires an active, unexpired `customer-api` session token, bound to the same ACTIVE, non-deleted customer, to grant or withdraw consent and to reserve/replay verification. Session lookup uses the existing session token's SHA-256 format; it stores the session ID on consent and does not put the raw token into SQL or audit. Session validation and reservation share a transaction. Previously unbound consents are historical and cannot authorize new attempts or count as current evidence. This supports authenticated **existing active customers only**, not pre-customer registration or assisted onboarding.
- `KycOrchestrator`, `PostgresKycStore` and migration `1785753600105` add a separate keyed, domain-separated BVN/NIN ownership MAC and a unique claim per kind/MAC, reserved atomically before dispatch and shared across customers/providers. A competing subject is blocked, a deduplicated private conflict recorded, and no provider call is sent. Identifiers are never stored in plaintext. Unknown, in-flight, and disputed claims remain held; a `REVIEW` is not proof of ownership. A singleton key proof rejects silently changed keys instead of permitting duplicate claims. This does not import/check old non-KYC identity records; existing histories and external systems need explicit reconciliation before rollout. Rotation and recovery of the dedicated high-entropy ownership key need a governed migration; never replace it casually. MACs and conflict metadata are sensitive.
- `KycExceptionReviewService` uses the existing `AuthorizationService` with `kyc.review`, MFA, a non-read-only workforce principal and an authenticated session ID to record a private audited **hold**. It assumes its principal has been authenticated by the existing runtime guard; it exposes no route. It cannot transfer/release a claim, mark evidence verified, or grant a tier. Independent authorization/maker-checker and approved ownership-dispute policy are required before adding any override.
- Fail-closed `selectKycProvider` selects a single explicitly enabled provider with the requested capability; missing/ambiguous/disabled routes fail and there is no automatic fallback. This is a routing primitive only, **not a persisted or governed provider configuration** and not a substitute for runtime authorization.
- Unknown/withdrawn in-flight outcomes open a durable private reconciliation case; a bounded scan can queue old `DISPATCHING` attempts and is idempotent. A late definitive completion closes an interruption-only case without another request. This does not provide a worker, manual outcome resolution, provider query, bill reconciliation or safe retry approval. Uncertain calls remain blocked.
- Evidence completion and consent withdrawal transactionally increment a durable per-customer eligibility-refresh revision. This is **invalidation/queueing only**: no worker, automatic reevaluation, policy decision or customer privilege change occurs. The prior on-demand evaluator stays advisory.

## Outstanding work and blockers

1. **Governed provider configuration and routing:** approved authorization matrix, maker-checker rules, persisted immutable policies, versioning, administration and audit, secret management, operational limits and a single authoritative runtime gateway. The router can be bypassed by direct internal construction and therefore must not be treated as enforcement.
2. **Reconciliation and exceptions:** authorized restricted review interface, independent approval, provider-supported evidence and charge reconciliation, case resolution, stale in-flight/late-result procedures, and safe controlled ownership reassignment. Current cases are hold-only. Monnify account access, BVN response schema, NIN endpoint, rate limits, reference and idempotency/billing behavior remain unverified; no duplicate billable retries may be made on speculation.
3. **Tier transitions:** no authorized tier-transition service was implemented. Existing `CustomerService.createKycAssessment` is unchanged and is not proven to enforce these new evidence requirements. Do not treat it as the requested new governed transition path. Approved mandatory requirements and a transactional evidence/profile/consent/ownership check, reviewer authorization, restricted audit, expiry/revocation and race handling are needed before any tier write.
4. **Automatic reevaluation:** consume refresh revisions with trusted authoritative customer/phone evidence and approved versioned policies, handle profile changes, consent/evidence expiry, revocation and concurrent mutations; ensure stale results cannot be used for tier changes. No default regulatory tier thresholds were invented.
5. **Authentication/privacy:** a securely verified pre-customer registration session, notice/purpose/charge binding, secure assisted-onboarding authorization, restricted access to history and private audit, retention/erasure policy, key custody and at-rest protection remain necessary. The internal services assume the trusted server and database boundary; they are not ready for direct use by untrusted callers.
6. **Rollout and regressions:** audit/migrate existing identifier data without exposing it or accidentally enabling existing identities. The singleton ownership key lock serializes reservations and needs throughput/load review. Full application migration-chain, PostgreSQL 16 production-equivalent, HTTP authorization, and financial transaction regression testing remain outstanding. Current legacy registration may activate before KYC; this batch does not change it.

## Tests

- TypeScript no-emit check and targeted ESLint passed.
- Five targeted unit/regression suites passed: **50 tests**, including existing Monnify, customer onboarding/eligibility and authorization suites. The full test suite was not run.
- **13 synthetic PostgreSQL 16.14 tests passed**, on a freshly initialized isolated Unix-socket-only cluster with a minimal synthetic customer/session schema and migrations 0104–0105. Covered session mismatch/revocation, consent, idempotency, concurrent cross-customer ownership, retry/cooldown and provider rate limits, outage and interruption queues, MFA/review authorization, failed audit rollback and key-rotation fail-closed behavior. Authorization service's audit dependency was mocked; the private KYC review audit was checked in PostgreSQL. This does not prove full-stack guard behavior or complete migration compatibility. The synthetic cluster was stopped and deleted.

No tier transition service exists yet, so unauthorized tier-transition integration tests cannot be claimed. No customer record, financial privilege or production configuration was changed.
