# KYC tier transitions — implementation and remaining release blockers

Migration `1785753600110` adds a disabled/unconfigured versioned policy, MFA maker/checker proposals, evaluation history, review holds, queue revisions, expiry markers and evidence/identity-change queue triggers. It does not change existing customer, wallet, transaction or policy data. The normal authorization catalogue seed and migration backfill grant dedicated `kyc.policy.view`, `.propose` and `.approve` functions. SUPER_ADMIN proposes; an independent COMPLIANCE principal approves or rejects. Configuration requires an explicit regulatory-review confirmation and is revalidated before use. The evaluator always retains the requested BVN-or-NIN Tier 1 and BVN-and-NIN Tier 2 floor and applies operator and reviewed regulatory requirements additively. Those floors are not a claim of comprehensive regulatory compliance.

`KycTierTransitionService` is the repository's KYC assessment mutation boundary. The legacy `CustomerService.createKycAssessment` now rejects direct calls; the workforce assessment endpoint delegates to the transition service and requires the existing status-specific permission plus MFA. An approval body cannot select or manufacture evidence: the service evaluates the effective policy and server-side evidence under transaction locks. Administrative PENDING/REJECTED actions set tier NONE, require a bounded reason code (`EVIDENCE_REVOKED`, `IDENTITY_CONFLICT`, or `MANUAL_REVIEW`), create a persistent review hold, and must be explicitly released by an evidence-gated authorized approval. This is an intentional change to the old unrestricted administrative assessment workflow; existing API clients must adapt. Level 3 is not modified by this service.

The worker uses the existing `kyc_evaluation_refresh` queue, monotonic revisions and database locks to serialize evaluations. The migration queues changes to verification attempts, consent, identity claims and relevant profile/contact fields; the worker also queues expiry and policy-effective changes. It writes the current customer KYC fields and assessment together with transition history and the existing transactional audit event. Missing policy, untrusted/unavailable source, ambiguous evidence, and legacy or Level 3 assessments are held rather than blindly approved. Managed approved assessments with identity conflicts are suspended pending review; expiration can suspend a managed approval even if its evidence reader is unavailable. Legacy approvals are not automatically migrated or downgraded. Review metadata can be read at `GET /api/v1/internal/kyc/tier-reviews` with `kyc.review` and MFA. Policy APIs are under `/api/v1/internal/kyc/tier-policies` (`GET`, `GET /proposals`, `POST /proposals`, and `POST /proposals/:id/approve` or `/reject`). History/review listings are limited to 100 without pagination.

## Important production blocker

**No production provider is trusted or wired as an evidence reader.** The production `KycTierEvidenceReader` returns unavailable, so it cannot issue a real automatic approval. The test-only adapter under `test/support` reads synthetic fixtures from the KYC verification tables, checks a fixture identity binding and consent, and imitates a trusted provider. It is not registered in the application and is not evidence of a real verified identity. Synthetic registration outcomes and `SYNTHETIC` provider records cannot produce real approvals. A production adapter still needs a confirmed provider contract and account entitlement, authenticated provenance, secure identity-binding key lifecycle, complete consent/claim/revocation handling, additional-evidence sources and isolated integration/security review. Monnify capabilities, credentials, billing and live verification remain unconfirmed; no provider was called.

The new functions, worker, triggers and schema are not a substitute for database privilege separation. The application direct-assessment method is closed; a database principal with unrestricted UPDATE/INSERT privileges can still bypass application controls. Deployment must review restricted database privileges, maker/checker role grants, audit retention, worker monitoring, expiry-sweep indexing and queue scale. The expiry sweeper and policy requeue use bounded batches, but have not been load-tested. The review endpoint is a bounded backend work list, not a complete case-management or review UI. The three administrative reason codes and added MFA change the previous assessment API contract.

## Validation scope

Isolated PostgreSQL 16 tests demonstrate transitions only with fabricated, test-only trusted-provider fixtures, not actual provider verification. They cover Tier 1 and Tier 2, duplicate/concurrent processing, policy publication races, expiry, consent withdrawal, identity mismatch, review holds, synthetic rejection, manual authorization, transactional audit rollback and the existing Cash-to-Cash assessment predicate. The Cash-to-Cash test checks the existing KYC gate only; it does not execute a transfer, payout or any financial transaction. A clean full migration chain and AppModule boot were checked against an independently initialized socket-only PostgreSQL 16 cluster with synthetic configuration and network blocking. Full financial workflows, real provider authorization, deployment configuration, production data migration and operational readiness have not been proven.
