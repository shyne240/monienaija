# Batch 2B — partial synthetic credential setup

This is **not the requested complete mobile onboarding or account-claiming flow**. Only a test-only, isolated synthetic DRAFT can set a six-digit login passcode and a different six-digit transaction PIN here. Both values must be confirmed. The setup transaction authenticates and locks the verified, unexpired registration session, checks the linked synthetic MATCH and live consent, locks the DRAFT, and atomically inserts separately salted PBKDF2 hashes into the existing customer authentication credential, password history and transaction PIN tables. It creates no customer, wallet, customer session, KYC evidence or financial privilege. A concurrent/replayed setup is rejected; status can be checked with the same unexpired session after a lost response. The mobile screen does not store either secret and explicitly says that the DRAFT cannot sign in.

The endpoint inherits Batch 2A's independently checked disposable test PostgreSQL 16 boundary and requires the test SMS sink. It is unavailable in production or ordinary databases. It is not a production password/PIN rollout. PIN length is fixed at six in this test-only path; the existing authenticated PIN system has its own limits and semantics.

## Remaining blockers

* There is no unified entry/account-claiming implementation. An admin-entered `customer_identity_documents` row has no verified state or provenance binding a particular document number to a genuine KYC result. The genuine `kyc_identity_claims` store uses a keyed identifier MAC, but there is no configured trusted key or production evidence reader. A plain document, aggregate tier, or synthetic result is not evidence that a specific identifier was verified. Matching these would permit account takeover.
* Normal customer authentication intentionally refuses DRAFT customers and normal sessions carry financial-capable permissions. A properly scoped onboarding-only authentication/session, with independent concurrency-safe passcode throttling, cooldown and replay handling, has not been implemented. The hashes can be checked by the existing verifier, but that is **not a successful customer login**.
* Transaction PIN setup is stored in the existing infrastructure, but full onboarding PIN verification, configurable four/six-digit policy, robust concurrent lockout and account-claiming setup still require work. Do not infer production readiness from this test-only record.
* After verified phone OTP, the app still follows the synthetic new-customer path rather than distinguishing existing customers from new ones. Admin claims with either BVN or NIN, existing-credential routing, and session recovery across those paths remain unimplemented.
* The two earlier admin-suite setup timeouts occurred during a run contending with other heavy test/lint work. The isolated suite passed with an explicit 30-second setup allowance; this points to load sensitivity but does not prove an environmental-only cause. Its old direct-KYC-creation assertions were corrected to require 409, preserving the evaluator boundary.

No live provider calls, real notifications, wallet activation or transactions are part of this work. Synthetic evidence remains ineligible for production KYC. Genuine verified provenance and key management, account recovery, biometric authentication, regulatory policy, production activation controls, and database role separation remain separate work.
