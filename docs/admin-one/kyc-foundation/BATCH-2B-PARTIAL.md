# Batch 2B — synthetic onboarding progress (incomplete)

This is **not the requested complete mobile onboarding or account-claiming flow**. The existing test-only synthetic completion creates a DRAFT with no KYC tier, wallet or financial privileges. Its verified registration session can atomically set separate, confirmed six-digit passcode and PIN hashes in the existing credential tables. Synthetic data is not genuine KYC evidence.

## Scoped synthetic sign-in

In the independently checked disposable PostgreSQL 16/test-SMS environment only, a verified phone session can now route to new registration, synthetic DRAFT login, or a pending state. It cannot disclose the route to a pending/unverified bearer. The login verifies the six-digit passcode under a credential row lock, locks after five failures for 15 minutes, consumes the verified registration authorization once, and issues a 15-minute `customer-onboarding` bearer. It is bound to the credential password version and is separately checked for customer/credential status, expiration and revocation. It is accepted only by its own status/logout endpoints, not customer-api/financial routes. Normal customer login explicitly rejects synthetic customers. The mobile development simulation stores the onboarding bearer separately from the customer-api token, presents a scoped sign-in and logout, and does not store the passcode or PIN. A lost login response requires a fresh phone verification.

These endpoints call the same disposable-environment guard as synthetic completion; they do not implement a production onboarding login. Simulation availability still only checks the runtime and SMS provider and can be advertised when the database guard will reject actual completion/login. Migration `0114` adds a credential-version binding for the new audience and refuses rollback while such sessions exist.

Transaction PIN verification now locks the PIN row for atomic verification, failure counts and audit. Customer-facing first PIN creation uses create-only semantics under a customer lock so concurrent setup cannot rotate an existing PIN. These changes do not execute a transaction or grant privileges.

## Remaining blockers

* There is no genuine account claiming, identifier evidence-status extension, trusted ownership reader/key integration, or verified BVN/NIN matching. Admin-entered `customer_identity_documents` lack verified provenance and are never promoted. A plain document, aggregate tier, or synthetic result is not evidence that a specific identifier was verified. Matching these would permit account takeover.
* The post-OTP routing above is **simulation-only**, not the requested unified production flow. Existing non-synthetic accounts are pending, not claimable or loggable through this route; new sessions cannot resume an incomplete synthetic credential setup unless the original registration session is retained. There is no production mobile claim, mismatch, provider-backed pending, locked, or authenticated flow.
* The separate onboarding session implements only its own status and logout, not production onboarding operations or production financial authorization. Normal customer-api authentication still requires ACTIVE; ordinary non-synthetic customer behavior is not redefined by this test implementation.
* Genuine provider capabilities and credentials, approved regulatory policy, ownership-key custody/rotation, real evidence ingestion, recovery, activation controls and database privilege separation remain unresolved. No live provider calls, real notifications, wallet activation or transactions were introduced.
* Prior admin-suite setup timeouts happened while other heavy work ran. The isolated rerun passed with a 30-second setup allowance; that does not prove an environmental-only cause. The older direct-KYC creation assertions require 409 to preserve the evaluator boundary.

## Verification of this increment

The disposable PostgreSQL 16 full-AppModule test covers synthetic BVN and NIN setup, simultaneous PIN failures, repeat PIN setup rejection, onboarding login lockout/cooldown and one-use exchange, scoped session expiry, credential-version invalidation and logout, rejection at a wallet route, and non-synthetic pending routing. It does not test genuine claims. The seven isolated PostgreSQL suites and the backend and mobile unit suites were run. The first full backend run exposed a stale production migration-head marker and a missing tier-service mock in the HTTP authorization matrix; both were corrected and the full unit suite then passed. This does not replace production security or integration review.
