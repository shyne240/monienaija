# MonieNaija One — console inventory and restructuring foundation

**Review proposal, not an implementation authorization.** Source baseline `6596545b04603886e56e165e9aef566228640de5`; the approved reference images in `docs/admin-one/reference/` remain visual authority. Do not use the earlier historical IA document as a statement of current behavior. This work changes documentation only. The [interactive review](review.html) contains the full 28-row route matrix, component/backlog register, trees, source-index search and the seed role/function matrix; `source-inventory.json` and `extract-source.cjs` provide a reproducible source-discovery appendix.

## 1. Executive decisions and boundaries

1. Organize around nine sections: Overview; Customers; Agents; Transactions; Finance; Products & pricing; Risk & compliance; Support; Administration. Keep one canonical implementation of each object; contextual links are not duplicate applications. The nine headings are a proposal, not a permission expansion.
2. Separate customer directory/registration and agent directory/enrollment; move Support out of the combined servicing group. Preserve the recent dashboard, sticky shell, current access checks, guarded navigation, PII masking, state-loss warnings and approved forest-green/cream/white/gold direction.
3. Collapse Transfers/Deposits/Withdrawals into one Transactions investigation workspace with type tabs, retaining all three legacy view identifiers and their initial type. Collapse five commercial registry links into one Products & pricing area with protected tabs and preserve their individual gates. Retain cash-to-cash operations as its own subworkspace and keep limit assignments and diagnostics accessible. Do not combine authorization checks just because pages share presentation.
4. Show a customer or agent profile's verification, eligibility, limits and financial records as linked facts from their authoritative domains. **A customer class editor is not established in current admin source**; customer KYC tier, eligibility policy and legacy customer limit profile are not an existing configurable customer class. Treat a unified customer-class editor as a proposed capability requiring business and backend review.
5. Financial rules are not visually merged: agent class service eligibility denies malformed/missing service lists; the separate limit resolver can return **no limit** for missing/disabled assignment/profile or no matching rules. A design that equates “not configured” with “blocked”, or says all scopes stack, is unsafe. Highlight this difference without modifying policy.
6. The legacy source contains many entity, controller, DTO and policy artifacts outside the Admin UI. Their existence is indexed for discovery, **not represented as an Admin feature or proof of runtime enforcement**. Documented features are not automatically reachable: runtime depends on current principal, scope, tenant/configuration, API policy, workflow state and backend.

## 2. Evidence and status model

`source-inventory.json` indexes all 69 admin-web TS/TSX files, 88 backend `*.controller.ts`, 156 `*.entity.ts`, 142 DTO files and 182 `*.service.ts` file paths at the baseline. It records JSX controls and labels, selected static API call syntax, component imports/states, controller decorators and action checks, DTO properties/decorators, entity attributes/relations and default role-function seed assignments with source line numbers. The index covers code surfaces, not every path through them: dynamic dispatch, wrappers, inherited DTOs, module wiring, cross-file validations, raw SQL and guards outside captured methods require following the cited source. Long extracted expressions are truncated; inspect source for exact semantics. Some helper calls are candidates, not APIs. It is a discovery index, **not an exhaustive semantic proof**, and a controller entry is not a verified active route. Files under other apps and non-admin APIs are not presented as admin pages.

- **Source-wired / partial:** code contains a UI, handler and/or API; functionality is not declared proven merely because it renders or a test passes. Matrix marks these partial until action-specific synthetic end-to-end verification.
- **Observed (narrow):** prior synthetic browser run in `docs/admin-one/evidence/ui-correction/README.md` selected all 28 desktop destinations across roles, exercised rail, dashboard period selection, customer preview and synthetic logout; does not demonstrate every action or populated data. It is historical evidence for this baseline, not a new complete workflow test.
- **Policy-blocked / unavailable:** explicit disabled/inoperative class-reclassification and agent PIN remediation controls in `AgentClassAssignmentPanel.tsx` and `AgentTransactionPinSupportPanel.tsx`. Do not turn into enabled promises.
- **Backend-only / unreachable from current UI:** source endpoint/model exists but no corresponding Admin control is established (for example aggregator hierarchy or commercial writes). Other clients may use it; not automatically a defect.
- **Planned / missing:** desired global transaction search, generalized customer class editor, shared registration framework, universal approval queue or settlement/break resolution are not established by these UI sources. Maintain these as explicit decisions/dependencies, not apparently functioning screens.
- **Broken:** no new end-to-end break was established during this documentation-only pass. A static mismatch or historical report is a *candidate for verification*, not a confirmed live defect. Uncertainty is not silently treated as working.

The matrix in `review.html` records each in-memory view ID, current/proposed placement, purpose, role gate, primary/secondary jobs, known gaps, backend domains and batch. Clicking a row opens its page brief: proposed structure, actions, missing support, dependencies and reusable patterns. The source index is the detailed backstop for labels, fields, forms, dynamic calls and panels; a search can include a screen name, endpoint or field. All 28 IDs and nine legacy aliases in `navigation-access.ts` remain accounted for; these are **SPA state identifiers, not 28 distinct URL routes** (`App.tsx`, `Layout.tsx`). Customer and agent IDs are passed as context. Local/remote session behavior and current session permissions, not the proposed menu, decide what is actually available.

## 3. Existing and proposed IA

The exact existing tree and route-by-route comparison are in the HTML. Proposed tree:

```text
Overview
  Operations dashboard → alerts, personal work and contextual approval links (existing data only)
Customers
  Directory → customer preview → Customer 360 (overview, personal, proof of address, readiness,
    wallet/history and linked KYC/cases/support/limits); Register customer (existing wizard)
  Service tiers & eligibility — proposed composed view, not a new customer-class engine
Agents
  Directory → Agent 360 (status, outlets/terminals, history, credentials, limits, support)
  Applications → new/draft, submission, review/decision; Service classes
  Network/hierarchy — backend-only candidate, not enabled until scope and workflow proven
Transactions
  Investigate → Transfers | Deposits | Withdrawals (one existing trace screen)
  Cash-to-cash operations; customer-context transaction history (same canonical data)
Finance
  Ledger & reversals; Reconciliation & internal reports; Agent funding (contextual approval handoff)
Products & pricing
  Products; Pricing (Fees | Commissions); Rewards; Limit policies (definitions | assignments | diagnostics)
Risk & compliance
  Customer KYC; Compliance cases; Fraud cases (current customer-ID lookups, not universal queues)
Support
  Tickets (customer or agent context, same canonical ticket workspace)
Administration
  Workforce; Roles & access; Approvals; Audit; Notifications; Operational health; Recovery;
  Experience / Dashboard assignments
```

Cross-links must invoke the same guarded destination, preserve customer/agent context, return navigation and unsaved-change handling. Account controls remain in the sticky top bar. A role with no authorized children must not see an empty group. Workload badges are shown only from authorized, validated, fresh counts; a generic “my work” queue is proposed, not evidenced. Approvals in Overview are deep links into the same checker workspace, not a second approval state machine.

**Design:** share one accessible WizardFrame: start/resume, progress/visited (not “completed” unless persisted), heading focus, field/section labels and required indicator, inline+summary validation, Back/Continue, explicit save state, review and result. Customer retains per-step DRAFT writes, optional address/identity, OTP and separate activation. Agent retains active class selection, versioned draft, dynamic evidence and explicit submit/review/approve/activation. The framework must label what is saved vs locally edited, exact side effects, and indeterminate outcomes; it must preserve conflict and retry/idempotency safeguards. Do not unify payloads, rules or approvals. For uploads, use only an existing authorized backend contract; no upload claim for an evidence-reference-only form. Future direct wizard resume would need a reliable server projection/contract; do not store sensitive credentials or OTP in browser draft storage.

**Potential overlap to review, not delete:** customer display/legal name is derived from business/personal names; agent registration number vs KYC reference vs class evidence may overlap semantically but are stored as distinct payload keys. Product owner and compliance must decide whether any are redundant after examining real policy, data consumers and migrations. No mandatory field/rule is removed here.

## 6. Unified inner-page standards

- **Directory:** one primary task, explicit scope/source and freshness; bounded server filters and stable paging where APIs support them, label local-only filters; no fake sort or bulk actions. Responsive table with a single labeled, keyboard-scrollable horizontal region only when required. Mask PII and preserve granular reveal authorization. Empty, loading, restricted, unconfigured, failed and stale are distinct.
- **Profile/detail:** identity/status header, concise summary and actions; tabs for related evidence, not duplicate entities. Deep link/back context; side drawer for quick inspection, full workspace for long or stateful edits. Links enforce destination permissions independently.
- **Form:** label, help, units, validation and requiredness follow source/backend; field errors linked by `aria-describedby`, focus error summary, no inferred defaults for money. Explicit save/cancel, optimistic version and post-save receipt verification; show partial success and uncertain outcome without retrying blindly.
- **Wizard:** standard frame above; progress does not imply save. Explicit dangerous-action confirmations, separate review from submission and from activation; focus, Escape, cancel, and exit guard.
- **Policies/settings:** separate read/configure/propose/approve/execute, show exact actor and scope, effective interval, version, provenance, impact, audit. No assumed universal approval or live enforcement.
- **Approvals:** canonical queues when available; exact object/evidence, maker/checker separation, status pending/approved/executed/rejected/unknown, scoped links to origin. Do not imply approved equals executed. Retain idempotency and recovery.
- **Modal/drawer:** use existing `WorkspaceDrawer`, dialog focus utilities and shared primitives where suitable; labeled modal, initial focus, Escape if safe, trapped focus and restoration, busy/unsaved guard. Do not hide a pending side effect on close.
- **Dashboard/navigation:** retain approved shell, responsive collapse, top account/logout, permission-gated contextual links, no invented figures. Detail work stays in the canonical workspace. Screen-reader semantics and active states must match interactions; avoid multiple independently scrolling regions unless a bounded table requires it.
- **Visual language:** forest green, cream, white, restrained gold, existing tokens and approved images; coherent typography and density. Avoid introducing a new visual direction. References are mockups, not operational evidence.

## 8. Owner decisions before implementation

1. Approve nine-section IA and canonical/contextual links; decide whether proposed customer tiers and agent hierarchy should be visible as unavailable vs omitted until supported.
2. Confirm governance for limit-definition and assignment changes, and whether permissive no-profile behavior is acceptable. A change to enforcement is **not** a visual redesign and needs independent risk/financial review.
3. Define authoritative effective-policy preview, overlap explanation, customer-class data model and per-flow enforcement evidence before promising a single combined editor.
4. Decide scope for global transaction/case/approval search, settlement and reconciliation-break handling; classify missing APIs and authorizations separately from visual work.
5. Confirm exact enrollment requiredness, evidence references vs uploads, customer draft resumption and any approval separation. Preserve all current fields until decisions and migrations are separately approved.

For the current pass, all policy, status, permission and workflow claims are source-derived and bounded as above. The review stops at architecture approval; it does not approve implementation, deployment, migrations or a business-rule change.
