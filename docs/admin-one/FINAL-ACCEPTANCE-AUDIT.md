## Method and coverage

The visual authority was the approved [login, dashboard and directory references](reference/) and [implementation brief](reference/IMPLEMENTATION-BRIEF.md), not the illustrative data in those images. The existing [phase-one comparisons](evidence/comparisons/) and per-workspace captures documented in [README](README.md) were reviewed alongside a new real-browser sweep. The structural green shell, navigation, cards, tables, forms and responsive patterns follow that direction; this is not a pixel-perfect comparison of every state. Some specialized forms still use inline styles and technical copy rather than identical shared primitives. No wholesale return to the old shell was observed in the exercised views.

The new [manifest and screenshots](evidence/final-acceptance/manifest.json) cover **28 navigation destinations × 3 widths = 84 viewport captures**, at 1440, 768 and 375 pixels. They use Vite, the real Nest AppModule, and a fresh disposable migrated PostgreSQL database with synthetic accounts and one customer. Seven seeded roles were exercised to cover destinations: SUPER_ADMIN, FINANCE_CONTROLLER, ADMINISTRATOR, OPERATIONS, CUSTOMER_SERVICE, COMPLIANCE and RISK_FRAUD. Screenshots show the initial viewport, not every lower section or every state. Earlier per-batch evidence covers additional drawers, tables, filters and drafts, and is identified by source SHA in [README](README.md). The harness checked document width for page-level overflow: 84/84 matched viewport width. Horizontal table/filter scrolling is intentional; the customer table was scrolled in the 768 and 375 checks.

The repeatable sweep is [`evidence/tools/one-final-acceptance.cjs`](evidence/tools/one-final-acceptance.cjs). Browser traffic was limited to the local UI, GET requests and the local-development login POST; other mutations were blocked by the proxy. The notification and cash-to-cash workers were disabled and the Node outbound-network guard was active. Browser monitoring recorded **zero console errors, uncaught page errors, API HTTP failures or API request failures** during the sweep; no external browser requests were blocked. This does not cover unvisited interactions or staging API behavior.

## Backend dependencies and policy boundaries

These are documented product/contract limitations, not newly discovered P0/P1 regressions. They should not be represented as implemented. Each is **P3 / nonblocking for the current read-only acceptance**, unless a separate product requirement makes it mandatory:

- **Dashboard / global search:** Search a non-customer agent, ticket or non-exact transaction: general cross-domain text-search contracts are not available. Supply scoped backend search before advertising it. Evidence: [README: connected behavior](README.md#connected-behavior-and-remaining-dependencies), transaction trace's exact-UUID notice.
- **Dashboard action items:** Open the dashboard action panel: a unified action count, flagged-transaction queue and reliably scoped approvals count are not available. Add authorized aggregation endpoints before displaying those values; current UI avoids inventing them. Evidence: [dashboard capture](evidence/final-acceptance/dashboard-1440.jpg) and README.
- **Support assignment:** Open a ticket assignment form: it accepts a workforce principal ID, not a searchable assignee directory. A scoped directory API is needed for a picker. Evidence: [support batch](evidence/support-batch/manifest.json) and [progress ledger](PROGRESS.md).
- **Production policy blocks:** A00 production sign-in, E05 Tier 3, E08 agent reclassification and E09 PIN support remain blocked as documented in [PROGRESS](PROGRESS.md). They require policy/owner decisions, not UI bypasses. These boundaries are not a defect to work around in staging.

Browser checks here sampled seven roles and four denied reads, not the entire authorization matrix.

This audit deliberately blocked all such browser mutations. Do not use real financial operations, send external SMS/email, activate providers or bypass policy controls.
3. Validate supported browsers and real desktop/tablet/mobile devices, keyboard-only use, screen readers, magnification/actual zoom and long translations. The sweep was headless Chromium at three widths; it did not test assistive technology, real devices or all modal/scroll states.
4. Check staging-specific API failures, availability and production-build performance, and obtain product-owner visual and operational acceptance. Existing screenshots are synthetic and do not substitute for that sign-off.
5. Proof-of-address upload and real provider interactions were not browser-exercised here; the test environment lacks their production integrations. Validate only with approved safe fixtures and no external delivery.

No merge, deployment, production-data change, financial transaction, external notification, provider activation, or approval decision was performed during this audit. The staging decision authorizes **testing readiness only**, not deployment or production release.
