# Customer lifecycle and financial readiness — technical investigation

**Source baseline:** `5a7c14896dbb3ef8a2534a00b6f7415dbbad4da5` on `arena/44f00580-monienaija`. Investigation date: 2026-11-06. Documentation only. This is a static source investigation, not a production configuration audit, live deployment inspection, regulatory determination, or proof of end-to-end operation. No user database, credentials, environment files, financial operations or notifications were accessed. Endpoints below use the `/api/v1` prefix. Source paths refer to this repository at the baseline commit; a path and line reference identifies the implementation, not evidence that a deployed instance has that configuration.

## Executive findings

1. Admin wizard **finishes a DRAFT**, not an activated customer; it neither creates a financial wallet nor starts/completes the separate onboarding workflow. Manual activation is a later, function-gated status change requiring a verified primary phone, not KYC approval or onboarding completion. A separate public self-registration flow with a verified phone **and password** creates an ACTIVE individual, password credential and NGN financial wallet atomically; without a password it creates a verified-phone DRAFT, without those assets. [S1](../../../src/customer/customer.service.ts#L80), [S2](../../../src/customer-registration/customer-registration.service.ts#L466), [S3](../../../apps/admin-web/src/screens/authenticated/CustomerRegistrationWizard.tsx#L1671).
2. The customer has independent **status**, **KYC level/status**, **onboarding status**, **eligibility/restrictions**, and financial **wallet** states. Their sequencing and coupling differ by path. In particular, separate onboarding completion requires customer ACTIVE, not the other way round. Neither a KYC decision nor activation implies the other. [S4](../../../src/customer-onboarding/customer-onboarding.service.ts#L497).
3. There is no single universal decision invoked by all transaction paths. `CustomerEligibilityService.getOperatingStatus` is an eligibility projection; source searches show the financial flows below do not call it directly. Transfer, Cash-In, Cash-Out and Cash-to-Cash have distinct boundary checks. A separate sophisticated `InternalTransferGateService` exists, but a source search finds its declaration/module registration, not a call from `CustomerAppController.createTransfer` or `TransferService`. Do **not** assert that it governs those paths. [S5](../../../src/customer-eligibility/customer-eligibility.service.ts#L491), [S6](../../../src/transfer/internal-transfer-gate.service.ts#L82), [S7](../../../src/customer-app/customer-app.controller.ts#L676).
4. KYC levels `NONE`, `LEVEL_1`, `LEVEL_2`, `LEVEL_3` are enum/database-constrained labels, not a configurable level-requirements system. Compliance can record an assessment/level in the Admin Console. **There is no working KYC-level requirements configuration interface identified.** No general rule mapping documents to each level or automatic approval-driven level advancement was found in the assessment implementation. [S8](../../../src/customer/customer.enums.ts#L13), [S9](../../../src/customer/customer.service.ts#L1005), [S10](../../../apps/admin-web/src/screens/authenticated/ComplianceScreen.tsx#L45).
5. Limit resolution is **potentially permissive** when no assignment, an invalid/disabled selected profile, or no matching rules exists. It selects one assignment by stored precedence; it does not infer KYC hierarchy. This is current code behavior, not a recommendation. [S11](../../../src/limit-catalog/limit-profile-resolver.service.ts#L20), [S12](../../../src/limit-catalog/limit-enforcement.service.ts#L65).
6. Fee and commission decisions are wired into several posting flows; actual accounting is a separate, disabled-by-default, explicitly configured boundary. Reward resolution exists, but no transaction calls `RewardEngine`; snapshots use NONE. Configured rule, calculated decision, posted fee, commission accrual/settlement and credited reward are different claims. [S13](../../../src/transfer/transfer.service.ts#L650), [S14](../../../src/commercial-accounting/commercial-accounting.service.ts#L119), [S15](../../../src/reward/reward.module.ts#L24).

## 1. Registration: actors, stages and persistence

### Administrator workflow

`CustomerDirectoryScreen` opens `CustomerRegistrationWizard`. With `customer.create`, profile save posts `POST /customers` with type, then `POST /customers/:id/registration-profile` (later edits use PATCH profile). Creation is separately committed: if profile save fails, a customer may already exist. The service creates UUID plus optional normalized unique reference, otherwise `mn-cus-` plus 12 cryptographically random bytes in hex; DRAFT, KYC NONE/NOT_STARTED, audit row. The controller overrides requested status to DRAFT. [S1](../../../src/customer/customer.service.ts#L80), [S16](../../../src/customer/customer.controller.ts#L83), [S17](../../../apps/admin-web/src/screens/authenticated/CustomerRegistrationWizard.tsx#L290).

| Wizard stage | Required at this stage | Optional / behavior |
|---|---|---|
| Profile | Type; individual first and last name, or business name; valid derived display/legal name | Individual middle name, date of birth, nationality. DOB must be a real non-future date. Business cannot use individual-only fields. Type becomes locked after record creation. |
| Contact | A valid primary phone must be saved to advance | Email optional; valid format when supplied. Phone verified separately; only Nigerian numbers supported by current OTP flow, although other valid numbers can be saved unverified. No activation here. |
| Address | Can skip | When saving: type, line 1, city, state/province, ISO country; line 2 and postal code optional, with country validation. |
| Identity | Can skip; access requires `customer.view_identity_documents` AND `kyc.review` | For an item saved: applicable type, document number and issuing country. Individual: BVN, NIN, passport, driver's licence, voter's card; business: business registration. BVN/NIN: 11 digits, Nigeria, no issue/expiry dates; other date constraints apply. Metadata only; not file upload or official identity verification. |
| Summary | No completion transition | Shows DRAFT; saved data only; open Customer 360 or exit. |

Each explicit save persists its own step. Navigation alone does not save. Exit prompts for unsaved changes. Resume means locate the DRAFT in directory and continue/edit the persisted record in Customer 360, **not** a guaranteed restoration of the original wizard step, unsaved state, OTP, or uncertain-outcome lock. Ambiguous response may mean a write already committed: inspect record and audit before retrying. [S17](../../../apps/admin-web/src/screens/authenticated/CustomerRegistrationWizard.tsx#L263), [S18](../../../src/customer/customer-validation.ts#L310), [S19](../../../apps/admin-web/src/screens/authenticated/Customer360Workspace.tsx#L200).

`POST /customers/registration/otp`, `/otp/verify`, then PATCH contact with one-time verification token prove the saved Nigerian primary phone. Token is phone-bound, hashed, time-limited, one-use; changing verified contact clears proof. OTP service uses rate limiting, resend cooldown and bounded attempts; already-verified bound phone yields enumeration-safe response. Actual delivery depends on notification provider configuration; fallback is a console provider, not evidence of SMS delivery. [S20](../../../src/customer-registration/customer-registration.service.ts#L130), [S21](../../../src/customer/customer.service.ts#L734).

### Self-registration and agent registration

Customer mobile contains `RegistrationScreen` using the public phone OTP endpoints then `POST /customers/registration`: phone and verification token required; optional password (8–128 characters), display name and idempotency key. With valid password, code creates ACTIVE INDIVIDUAL, verified primary contact, active password credential and primary NGN ledger-backed `wallet_accounts` plus liability ledger account in one transaction; optional display name creates profile. Without password, verified phone DRAFT, no credential/wallet. Initial reference is `mn-` plus normalized Nigerian phone, not the admin random reference. A login session is not returned by registration. Compare actual service with stale route-policy comments saying public registration only creates drafts; code wins. [S2](../../../src/customer-registration/customer-registration.service.ts#L466), [S22](../../../src/customer-registration/dto/complete-registration.dto.ts), [S23](../../../apps/customer-mobile/src/screens/unauthenticated/RegistrationScreen.tsx#L15), [S24](../../../src/authorization/route-policy-registry.ts#L49).

Agents are denied the workforce customer-create and lifecycle routes (`route-policy-registry.ts` and `CustomerController`); no dedicated agent-assisted customer-registration endpoint was found in searched agent controllers/mobile source. An agent may participate in financial services, not thereby acquire a registration/activation grant. Self-service is not evidence of an agent-managed enrollment process. [S25](../../../src/authorization/route-policy-registry.ts#L355), [S26](../../../src/customer/customer.controller.ts#L355).

### Duplicates and progression

`customers.reference` is unique; live contact `(type, normalizedValue)` has a global unique index for phone and email, and self-registration checks existing bound phone. Duplicate identity document check is **within the same customer and document type**, not a demonstrated cross-customer identity deduplication system; duplicate addresses are checked within the customer. No broad fuzzy/name/person matching was established. Input validators reject malformed names, dates, phones, countries and document fields. OTP expiration/lockout, missing permission, unsaved or invalid form fields, duplicate contacts and uncertain writes can prevent progression; the wizard permits skipped address and identity and does not guarantee readiness. [S27](../../../src/customer/customer-contact-method.entity.ts#L11), [S28](../../../src/customer/customer.service.ts#L1314), [S18](../../../src/customer/customer-validation.ts).

## 2. Activation and status lifecycle

| Current | Allowed targets | Gate |
|---|---|---|
| DRAFT | ACTIVE, SUSPENDED, CLOSED | entering ACTIVE requires live verified primary PHONE |
| ACTIVE | SUSPENDED, CLOSED | appropriate lifecycle function |
| SUSPENDED | ACTIVE, CLOSED | reactivation again requires verified primary PHONE |
| CLOSED | none | soft-deleted (`deletedAt`) on close |

Same-status request returns unchanged. Invalid transitions conflict. `PATCH /customers/:id` is workforce-session-only and maps target ACTIVE to `customer.activate`, SUSPENDED to `customer.suspend`, CLOSED to `customer.close`; actor derived from authenticated principal and change audited. No maker-checker call in this route/service. Same activation permission covers reactivate. An agent or customer cannot use this PATCH. Self-service initial activation is a **different creation path**, not permission to self-reactivate. Verified phone is the sole stated manual ACTIVE gate; KYC, email, onboarding, financial wallet and approval are not checked here. If a phone changes after activation verification is cleared, but no automatic customer suspension was established. [S29](../../../src/customer/customer.service.ts#L147), [S30](../../../src/customer/customer.service.ts#L1242), [S25](../../../src/authorization/route-policy-registry.ts#L355).

Customer 360 has Activate/Suspend/Reactivate and Close buttons conditional on status/function, confirmation and verified-phone warning. Availability to a principal is not proof an action succeeds: backend rechecks. [S31](../../../apps/admin-web/src/screens/authenticated/Customer360Workspace.tsx#L335).

## 3. KYC vs onboarding vs eligibility

`customers` holds `kyc_level` and `kyc_status`; `customer_kyc_assessments` records current and superseded assessments. Every `POST /customers/:id/kyc-assessment` supplies level and status, with reason/expiry optional. Backend replaces `assessedBy` with authenticated actor. Allowed status transitions: NOT_STARTED→PENDING; PENDING→APPROVED or REJECTED; APPROVED→PENDING; REJECTED→PENDING. Same status is rejected. On **every** assessment, including PENDING, service copies the caller-selected level and status to customer; approval is not itself an automatic upgrade, and there is no demonstrated minimum evidence/level-document validation or maker-checker in this path. `kyc.review`, `kyc.approve`, `kyc.reject` are separately authorized based on target status. Admin Compliance KYC screen reads/submits assessment and selected level; this is a per-customer manual assignment/change, not configurable global level requirements. Individual/business document-type validation differs, but no comprehensive tier-by-tier requirements matrix exists in this assessment service. [S32](../../../src/customer/customer.controller.ts#L55), [S9](../../../src/customer/customer.service.ts#L1005), [S10](../../../apps/admin-web/src/screens/authenticated/ComplianceScreen.tsx#L45).

Separate onboarding entity: NOT_STARTED→IN_PROGRESS→AWAITING_REVIEW→APPROVED→COMPLETED, with REJECTED possible from IN_PROGRESS or AWAITING_REVIEW and no exit from REJECTED/COMPLETED. Approval status is separate from onboarding status. Prohibited onboarding risk prevents an approved decision or approved workflow status. Completion requires ACTIVE customer; active profile; a nondeleted address and identity-document record; at least one required agreement and all required agreements accepted; at least one required task and all completed; risk not PROHIBITED; onboarding APPROVED. Missing risk profile passes `riskAllowed` because only PROHIBITED is excluded. Presence is not verification. Workflow APPROVED transition itself does not establish every completion criterion. [S33](../../../src/customer-onboarding/customer-onboarding.service.ts#L140), [S4](../../../src/customer-onboarding/customer-onboarding.service.ts#L497), [S34](../../../src/customer-onboarding/customer-onboarding.service.ts#L663).

Separate eligibility record can become ELIGIBLE only after COMPLETED onboarding and absent active BLACKLISTED restriction; active product enrollment requires ELIGIBLE and not FROZEN. Operating projection prioritizes BLACKLISTED, FROZEN, CLOSED, LIMITED/MANUAL_REVIEW, revoked/suspended eligibility and then ELIGIBLE. Enabled permissions and active enrollments are reported but their presence is not required for `OPERABLE` in that projection; customer SUSPENDED is not explicitly checked there (only CLOSED). Neither this projection nor these enrollment/permission records should be represented as universally enforced at financial posting. [S5](../../../src/customer-eligibility/customer-eligibility.service.ts#L491), [S35](../../../src/customer-eligibility/customer-eligibility.service.ts#L583).

These backend workflow write handlers mostly lack explicit per-function checks within their controllers; the global `RuntimeAccessGuard` and route registry still apply. Generic `/customers/:id/*` accepts customer SELF or allowed workforce principal types; do not infer unauthenticated access, but do not infer robust action-specific role/maker-checker protection either. Actor fields in several legacy DTOs are caller-supplied. Investigate the exact authorization of these mutations, SELF ownership and audit provenance in isolated adversarial HTTP tests before relying on them. [S36](../../../src/customer-onboarding/customer-onboarding.controller.ts), [S37](../../../src/customer-eligibility/customer-eligibility.controller.ts), [S38](../../../src/authorization/route-policy-registry.ts#L473), [S39](../../../src/app.module.ts#L192).

Proof-of-address has its own protected storage/review workflow and Tier 3 readiness panel; it is not a demonstrated global `LEVEL_3` auto-upgrade. Compliance cases and risk profiles have independent models/guards. [S40](../../../src/customer-proof-of-address/customer-proof-of-address.controller.ts), [S41](../../../apps/admin-web/src/screens/authenticated/CustomerTier3ReadinessPanel.tsx), [S42](../../../src/customer-compliance/customer-compliance.controller.ts).

## 4. Financial transaction boundaries and worked example

**No universal readiness verdict.** Each path's handler and posting service are authoritative for that operation, in combination with route authorization and ledger rules. Below describes source path, not a promise of deployed transaction success. Product enrollment, generic operating permission, separate eligibility, generic restrictions, email verification, KYC level and onboarding completion were not found directly checked in these specific Cash-In/Cash-Out/Transfer call chains; do not extrapolate to all products or separate policy engines.

| Operation and entry | Customer checks and factors | Other necessary conditions / uncertainty |
|---|---|---|
| Cash-In `POST /agents/cash-in` | resolves receiving identity to CUSTOMER, customer ACTIVE/not deleted; no customer PIN in this path | authenticated agent, agent PIN, CASH_IN capability/class, positive NGN, idempotency, agent float/ledger, customer and agent wallets ensured if absent, customer `CASH_TO_WALLET` INCOMING limit. |
| Cash-Out `POST /agents/cash-out` | customer ACTIVE/not deleted, customer transaction PIN, customer-bound desk OTP/MFA | authenticated agent, agent PIN, CASH_OUT capability/class, positive NGN, idempotency, sufficient customer funds; wallets ensured; customer `WALLET_TO_CASH` OUTGOING limit. |
| Transfer `POST /customers/me/transfers` | authenticated CUSTOMER session, source wallet SELF ownership, customer PIN, active wallets and matching currency; service checks existing customer rows for both legs ACTIVE/not deleted | positive amount, destination wallet, sufficient balance, idempotency, source-customer `WALLET_TRANSFER` OUTGOING limit. Missing UUID-shaped customer row is explicitly skipped as possibly system wallet: investigate identity/binding assumptions. Recipient's incoming customer limit is not demonstrated in this call. |
| Cash-to-Cash `POST /agents/cash-to-cash`, claim routes `/agents/cash-to-cash/claim` or `/claim-by-number` | claim binds beneficiary to their verified primary phone, customer ACTIVE and KYC APPROVED, transfer code, desk OTP; wallet claim checks current assessment expiry when applicable; cash claim requires current approved unexpired assessment with assessor | agent session/capability/PIN for applicable operation, transfer unclaimed/unexpired and settlement; initiation applies agent OUTGOING limit; claim applies CUSTOMER INCOMING for wallet or AGENT INCOMING for cash. See exact mode checks in service. |
| Customer funding | `CUSTOMER_FUNDING` customer INCOMING limit at the specific funding boundary | Different operational workflow and authorization; do not equate with an agent Cash-In. Generic `/deposits`, `/withdrawals`, `/transfers` command handlers deliberately reject. |

[S43](../../../src/agent/agent-cash-in.service.ts#L60), [S44](../../../src/agent/agent-cash-out.service.ts#L96), [S45](../../../src/customer-app/customer-app.controller.ts#L676), [S46](../../../src/transfer/transfer.service.ts#L370), [S47](../../../src/agent/agent-cash-to-cash-claim.service.ts#L331), [S48](../../../src/customer-funding/customer-funding.service.ts#L430), [S49](../../../src/transfer/transfer.controller.ts#L31).

**Worked example:** An operator creates an individual draft with first/last name, saves a primary Nigerian phone and completes phone OTP; address/document may be skipped but are needed for the separate onboarding readiness. Operator with `customer.activate` activates via Customer 360. This does **not** create password, customer session, PIN, KYC approval, onboarding completion, eligibility, or wallet. For Cash-In, an eligible authenticated agent with capability/PIN resolves the customer receiving identity and has float; the flow can ensure wallet and then checks applicable customer incoming limits and posts ledger entries. A verified receiving-number binding and availability must be established; successful activation alone is insufficient. For Cash-Out, additionally arrange valid customer credential/session-backed desk OTP and transaction PIN, agent capability/PIN, and sufficient wallet funds; wallet creation alone supplies no funds. For a customer-initiated Transfer, establish an authorized customer credential/session, set transaction PIN using `POST /customers/me/transaction-pin`, ensure an ACTIVE funded source wallet, an active compatible destination wallet, and pass source limit and ledger checks. Initial credentials for admin-created ACTIVE customers have a separate workforce issuance/rotation path (`POST /internal/admin/customers/:id/credentials`, `POST /customers/credentials/rotate`); confirm delivery and access operationally. The wizard does not perform it. No real operations were attempted. [S50](../../../src/admin/admin-customer-credentials.controller.ts#L64), [S51](../../../src/customer-app/customer-app.controller.ts#L1200), [S52](../../../src/agent/agent-desk-otp.service.ts#L113).

## 6. Limits: configuration, resolution and enforcement

Profiles/rules/assignments are stored in `limit_profiles`, `limit_rules`, `limit_assignments`; usage/reservations tracked separately. `/internal/limit-profiles`, `/:code/rules`, `/internal/limit-rules/:id` and `/internal/limit-assignments` expose create/read/patch, with `limit.modify` for non-agent assignments and `agent.assign_limit` for agent assignments; diagnostics require `limit.view`. Catalogue screen is read-only; assignment UI supports agent and agent-class creation/toggles and customer-scoped inspection, **not a customer assignment creation form**. API supports direct CUSTOMER assignment, subject to effective authorization; no verified one-off bypass of limit checks was identified. [S57](../../../src/limit-catalog/limit-catalog.controller.ts), [S58](../../../src/limit-catalog/limit-assignment.controller.ts#L35), [S59](../../../apps/admin-web/src/screens/authenticated/LimitAssignmentScreen.tsx#L632), [S60](../../../apps/admin-web/src/screens/authenticated/CommercialRulesScreen.tsx).

Select live active effective assignments matching GLOBAL, individual CUSTOMER/AGENT, supplied AGENT_CLASS or supplied SEGMENT. Order `precedence DESC, effective_from DESC, created_at DESC`, limit 1; no implicit specific-over-global precedence or final unique tie-break shown. Disabled assignment is excluded, allowing another matching assignment to win. If the selected assignment references missing, deleted, disabled or non-ACTIVE profile, resolver returns no profile **without falling back** to the next assignment. Missing profile or no applicable rules → allowed, not zero limit. Rule matching: selected profile, exact product/currency, effective, active, nondeleted; direction null/BOTH/exact and channel null/exact. All matching rules are evaluated; priority orders but does not choose a single rule. `MIN_AMOUNT_PER_TX`, `MAX_AMOUNT_PER_TX`, DAILY/WEEKLY/MONTHLY/YEARLY amount/count and `WALLET_BALANCE_MAX` are supported; balance max checks incoming projected ledger balance, not outgoing. Windowed use includes reserved plus used, and reservations/commits are tied to the transaction where wired. Calendar windows use Africa/Lagos; weekly starts Monday. [S11](../../../src/limit-catalog/limit-profile-resolver.service.ts#L68), [S12](../../../src/limit-catalog/limit-enforcement.service.ts#L78), [S61](../../../src/limit-catalog/limit-window.util.ts#L60).

Limit modifications currently use function checks but **not the commercial maker-checker service**; `governed-action.registry.ts` explicitly excludes limit.modify pending future work. Seed gives FINANCE_PREPARER INITIATE and FINANCE_CONTROLLER APPROVE, but the runtime catalogue deliberately flattens access types into function codes: `requireFunction('limit.modify')` alone does not distinguish INITIATE from APPROVE. Consequently both seeded roles can satisfy that function check when their effective session and principal type permit the route; there is no independent approval consumption in the shown limit endpoints. Verify real session grants and configuration separately. The older per-customer `customer_limit_profiles` and `CustomerLimitType` exist independently; no use by the quoted `LimitEnforcementService` financial paths was found. [S62](../../../src/authorization/governed-action.registry.ts#L104), [S63](../../../src/customer-eligibility/customer-limit-profile.entity.ts), [S78](../../../src/authorization-catalogue/authorization-catalogue-runtime.service.ts#L37).

## 7. Fees, commissions and rewards

Fee rules (`fee_rules`) resolve by product, currency, active effective window and highest priority; top-priority tie yields AMBIGUOUS, no silent winner. Amount drives calculation (flat, percentage, min/max and VAT parameters), not a direct customer/KYC/segment target in this resolver. No customer-specific fee targeting was identified in this registry. NOT_CONFIGURED is not an explicitly configured zero. [S64](../../../src/fee-rules/fee-rule-resolver.service.ts#L87), [S65](../../../src/fee-rules/fee-rule-calculator.service.ts).

Commission rules (`commission_rules`) resolve by product/currency, recipient type, optional agent/class/aggregator targeting and priority; same highest-priority tie fails closed. Principal, fee or net basis may require actual fee evidence. Agent transaction flows supply agent context; customer-only Transfer/funding do not supply agent/class, so no blanket claim of agent-specific commission. Rewards (`reward_rules`) support customer, KYC level, agent/class or campaign targeting (at most one), per beneficiary, priority and ambiguity checks. Resolver is read-only and no RewardEngine flow consumer was found. [S66](../../../src/commission/commission-rule-resolver.service.ts#L13), [S67](../../../src/reward/reward-rule-resolver.service.ts#L15), [S68](../../../src/agent/agent-financial-execution.service.ts#L517).

Fee/commission engines are called and snapshots recorded in several flows including Transfer, Cash-In/Cash-Out through agent financial execution, Cash-to-Cash initiation and funding. Some historical comments in resolvers say not wired; later call sites supersede those comments. Accounting is explicitly gated by `COMMERCIAL_ACCOUNTING_ENABLED` and applicable product, required account mappings, VAT and commission treatment/timing; configuration missing can fail closed when enabled. `EXPENSE_PAYABLE` accrual is not proof of paid agent wallet; `AGENT_WALLET_NETTING` can post credit only under its configured conditions. Customer/agent funding fee scope differs. Snapshot calculation alone is not ledger posting or settlement. No deployed flag, rules, account mappings or ledger was inspected. [S13](../../../src/transfer/transfer.service.ts#L679), [S69](../../../src/commercial-accounting/commercial-accounting-config.service.ts), [S14](../../../src/commercial-accounting/commercial-accounting.service.ts#L160), [S70](../../../src/customer-funding/customer-funding.service.ts#L801).

Fee, commission and reward registries have create/modify APIs with governed request→independent FINANCE_CONTROLLER approval→execute matching change, FINANCE_PREPARER maker, MFA and no self-approval. Commercial screen provides read-only catalogue views, not a complete create/approve/execute UI. Product governance and approval features have their own boundaries. [S71](../../../src/authorization/commercial-rule-governance.service.ts#L18), [S72](../../../src/authorization/governed-action.registry.ts#L75), [S60](../../../apps/admin-web/src/screens/authenticated/CommercialRulesScreen.tsx).

## 8. Actual roles, functions and approvals

The following are **seed grants**, not a live-user entitlement inventory; runtime role definitions may change, sessions must contain authorized functions and route principal-type restrictions still apply. `SUPER_ADMIN` is not a bypass. `AuthorizationService.requireFunction` evaluates required functions against the effective principal. [S73](../../../src/authorization-catalogue/authorization-catalogue.seed.ts#L1235), [S74](../../../src/authorization/authorization.service.ts#L61).

| Responsibility | Relevant source checks and seeded roles |
|---|---|
| Register, activate, suspend, close | `customer.create`, `.activate`, `.suspend`, `.close`: SUPER_ADMIN and OPERATIONS EXECUTE. AGENT/CUSTOMER excluded from workforce creation/lifecycle. |
| Identity metadata and KYC | Identity write requires `customer.view_identity_documents` plus `kyc.review` for workforce; both seeded to SUPER_ADMIN and COMPLIANCE, not OPERATIONS. KYC review/approve/reject SUPER_ADMIN and COMPLIANCE EXECUTE. Per-customer own-data writes have separate SELF handling. |
| KYC level | same assessment function determined by status, no separate upgrade permission or independent checker found. |
