Product ownerIntroduction+

What this is: a source-code investigation of baseline 5a7c14896dbb3ef8a2534a00b6f7415dbbad4da5, not a live-system audit or a recommendation already approved for implementation. No real customer, payment, notification or database was used. For precise code references, endpoints and limitations, see the technical report and configuration inventory.

Product ownerThe short answer+

An administrator registering someone does not activate them. The Admin Console saves a customer as a draft. An authorized operator can later activate or reactivate the customer after the primary phone is verified. That activation does not itself approve KYC, complete the separate onboarding workflow, create a financial wallet, or authorize every transaction.

Customers have another route: the customer mobile registration flow can verify a Nigerian phone and, when a password is supplied, create an active individual, credential and NGN wallet together. That still does not automatically create an approved KYC assessment or transaction PIN. Actual phone-message delivery depends on deployment configuration, which was not checked.

There is no one universal “ready to transact” switch shown to govern every transaction. The Cash-In, Cash-Out, Transfer and Cash-to-Cash flows make different checks. Some separate eligibility and onboarding records exist but were not found directly used by those individual posting paths. This does not establish that these records are never used elsewhere.

Product ownerHow an administrator creates a customer+
  1. In Customer Directory, the operator starts registration. Individual first and last names are required; middle name, date of birth and nationality are optional. A business needs a business name. The system creates a reference and a DRAFT record.
  2. A valid primary phone is saved; an email is optional. The phone can be verified with the existing Nigerian-phone one-time-code flow. Saving a phone is not the same as verifying it.
  3. Address and identity metadata can be saved or skipped. Identity actions have extra permissions. Saving a number or document record is not proof that a document was uploaded or verified with an official source.
  4. The summary says DRAFT. The wizard does not activate the customer or create a financial wallet. Previously saved data can be continued from Customer 360, but unsaved edits and the exact wizard position are not guaranteed to return.

Each save is separate. If a response is lost, the operation may already have succeeded: check the record and audit before retrying. The system detects a duplicate normalized live phone/email and reference, and checks duplicate identity entries within a customer; this is not proof of a complete cross-customer identity-matching system.

Product ownerWhat activation means+

Activation is the customer account status ACTIVE. In Customer 360, authorized staff can activate, suspend, reactivate or close a customer. A verified primary phone is required when entering ACTIVE, including reactivation. There is no maker-checker step in the inspected activation route. An agent cannot use that workforce activation route, and a customer cannot use it to reactivate themselves. The separate initial self-registration flow can create an ACTIVE customer after phone verification and password setup.

Customer status and KYC are distinct: a customer can be ACTIVE while KYC is NOT_STARTED. Completing a separate onboarding workflow actually requires an already ACTIVE customer, plus profile, address, identity record, required accepted agreements, completed tasks and an allowed risk state. A record of identity is not the same as verified identity.

Product ownerKYC levels and customer classes+

The code recognizes NONE and Levels 1, 2 and 3. The Compliance screen can record a customer's KYC assessment and the selected level, with appropriate permissions. Assessments must follow the backend status sequence: NOT_STARTED → PENDING → APPROVED or REJECTED; an approved or rejected assessment goes back to PENDING for a new decision. The level is manually supplied on each assessment, including PENDING; approval does not automatically calculate the next level.

There is no identified working Admin Console screen to configure what each KYC level requires, and no general level-to-documents rule was found in the assessment service. The individual/business forms allow different identity types, but that is not a complete policy for levels 1–3. Proof-of-address has its own workflow; it is not proof that Level 3 is automatically granted.

No operational Customer Class of Service system with customer class definitions, assignment and approval was identified. Agent Classes are real but apply to agents. Other concepts — product enrollment, restrictions, permissions, direct limits, and a separate commercial tier architecture — should not be presented as a finished customer-class system without further integration evidence.

Product ownerBefore a first transaction: an example+

Assume an administrator creates an individual and verifies the primary phone. An operator activates the customer. From there:

  • Cash-In: an authenticated, authorized agent with the right service capability and agent PIN resolves the customer's receiving identity. The customer must be ACTIVE; the flow can create the financial wallet if needed. Agent float, transaction rules and applicable customer incoming limits must also permit the transaction. The customer's transaction PIN is not required by this path.
  • Cash-Out: the ACTIVE customer needs a transaction PIN, a customer-bound one-time-code/MFA challenge, and sufficient wallet funds. The agent needs the appropriate capability and agent PIN. The transaction also passes applicable customer outgoing limits.
  • Transfer: the customer needs an issued/usable credential and customer session, their own active funded financial wallet and transaction PIN; the recipient needs a compatible active wallet. Source ownership, active customer states, currency, applicable outgoing limit and ledger checks apply.
  • Cash-to-Cash claim: the claimant must control the beneficiary's verified phone, be ACTIVE and meet the claim's approved KYC and evidence checks; transfer code, OTP and agent-side checks also apply. This is stricter in a different way than the above paths.

These are code-path conditions, not an assurance that a deployed service or message provider works. The administrator's wizard does not itself issue the customer's credential, complete KYC, enroll a PIN or supply wallet funds. Separate credential issuance and rotation code exists; its actual delivery and hand-off need operational validation.

Product ownerLimits, fees, commissions and rewards+
  • Limits: profiles can be assigned directly or by other supported scopes. The highest stored precedence wins; a customer-specific rule does not automatically beat a global one. If there is no matching assignment, the selected profile is unusable, or no rule matches, the examined enforcement allows the transaction without a limit from this catalogue. Decide whether this is acceptable. The Admin Console can inspect customer assignments but the current assignment form is for agents and agent classes, not creating customer assignments.
  • Fees: a matching product/currency rule can be calculated; the main resolver does not target customers or KYC tiers. Calculation and a decision snapshot do not prove a fee was charged. Actual accounting requires explicit enabled configuration and valid treatments/accounts.
  • Commissions: rules can target agent or agent class and some agent flows calculate a decision. A decision is not necessarily paid: configured accounting may accrue a payable or post wallet netting under different conditions.
  • Rewards: a backend rules and calculation foundation exists, including targeting by customer or KYC level. The inspected transaction flows do not call the reward engine to award rewards. Do not describe reward points or credits as live.

Commercial rule changes use a finance maker/checker process in the backend. Limit changes use separate function checks, and the inspected limit mutations do not consume that commercial approval workflow. The Admin commercial catalogue is primarily a viewing interface, not a full policy-management workflow.

Product ownerHighest-priority decisions for the owner+
  1. Should ACTIVE be allowed before approved KYC, and should each transaction type have a uniform or intentionally different KYC requirement?
  2. Should the separate onboarding/eligibility, enrollment, restrictions and permissions be mandatory for each transaction, and what should happen when they are missing?
  3. What are the precise KYC requirements and valid evidence for individuals versus businesses at each level, including review, expiry, upgrade and downgrade authority?
  4. Is a Customer Class of Service needed, or do existing products, eligibility and direct/segment limits meet the business need? How would it relate to the separate commercial tier model?
  5. What precedence, fallback and default-deny/default-allow policy should apply to limits, and which product/direction/channel combinations must be covered?
  6. Which fees, taxes, commissions and rewards are approved, when should they be posted or settled, and who must approve changes?
  7. Who owns credential hand-off, PIN recovery, monitoring, suspension and customer support? What separation of duties is required?
Product ownerWhat to improve after approval+

Prioritize a clear Customer 360 readiness explanation and safe navigation; separate KYC assessment from a future requirements configuration facility; expose evidence and blocked reasons; provide appropriate customer limit-management controls; connect or deliberately retire disconnected models only after a backend/control review; and make commercial calculation versus posting versus settlement visible. These are investigation recommendations, not an authorized implementation plan. Stop for owner decisions before changing policy or code.

Technical investigationExecutive findings+
  1. Admin wizard finishes a DRAFT, not an activated customer; it neither creates a financial wallet nor starts/completes the separate onboarding workflow. Manual activation is a later, function-gated status change requiring a verified primary phone, not KYC approval or onboarding completion. A separate public self-registration flow with a verified phone and password creates an ACTIVE individual, password credential and NGN financial wallet atomically; without a password it creates a verified-phone DRAFT, without those assets. S1, S2, S3.
  2. The customer has independent status, KYC level/status, onboarding status, eligibility/restrictions, and financial wallet states. Their sequencing and coupling differ by path. In particular, separate onboarding completion requires customer ACTIVE, not the other way round. Neither a KYC decision nor activation implies the other. S4.
  3. There is no single universal decision invoked by all transaction paths. CustomerEligibilityService.getOperatingStatus is an eligibility projection; source searches show the financial flows below do not call it directly. Transfer, Cash-In, Cash-Out and Cash-to-Cash have distinct boundary checks. A separate sophisticated InternalTransferGateService exists, but a source search finds its declaration/module registration, not a call from CustomerAppController.createTransfer or TransferService. Do not assert that it governs those paths. S5, S6, S7.
  4. KYC levels NONE, LEVEL_1, LEVEL_2, LEVEL_3 are enum/database-constrained labels, not a configurable level-requirements system. Compliance can record an assessment/level in the Admin Console. There is no working KYC-level requirements configuration interface identified. No general rule mapping documents to each level or automatic approval-driven level advancement was found in the assessment implementation. S8, S9, S10.
  5. Limit resolution is potentially permissive when no assignment, an invalid/disabled selected profile, or no matching rules exists. It selects one assignment by stored precedence; it does not infer KYC hierarchy. This is current code behavior, not a recommendation. S11, S12.
  6. Fee and commission decisions are wired into several posting flows; actual accounting is a separate, disabled-by-default, explicitly configured boundary. Reward resolution exists, but no transaction calls RewardEngine; snapshots use NONE. Configured rule, calculated decision, posted fee, commission accrual/settlement and credited reward are different claims. S13, S14, S15.
Technical investigation1. Registration: actors, stages and persistence+

Administrator workflow

CustomerDirectoryScreen opens CustomerRegistrationWizard. With customer.create, profile save posts POST /customers with type, then POST /customers/:id/registration-profile (later edits use PATCH profile). Creation is separately committed: if profile save fails, a customer may already exist. The service creates UUID plus optional normalized unique reference, otherwise mn-cus- plus 12 cryptographically random bytes in hex; DRAFT, KYC NONE/NOT_STARTED, audit row. The controller overrides requested status to DRAFT. S1, S16, S17.

Self-registration and agent registration

Customer mobile contains RegistrationScreen using the public phone OTP endpoints then POST /customers/registration: phone and verification token required; optional password (8–128 characters), display name and idempotency key. With valid password, code creates ACTIVE INDIVIDUAL, verified primary contact, active password credential and primary NGN ledger-backed wallet_accounts plus liability ledger account in one transaction; optional display name creates profile. Without password, verified phone DRAFT, no credential/wallet. Initial reference is mn- plus normalized Nigerian phone, not the admin random reference. A login session is not returned by registration. Compare actual service with stale route-policy comments saying public registration only creates drafts; code wins. S2, S22, S23, S24.

Agents are denied the workforce customer-create and lifecycle routes (route-policy-registry.ts and CustomerController); no dedicated agent-assisted customer-registration endpoint was found in searched agent controllers/mobile source. An agent may participate in financial services, not thereby acquire a registration/activation grant. Self-service is not evidence of an agent-managed enrollment process. S25, S26.

Duplicates and progression

customers.reference is unique; live contact (type, normalizedValue) has a global unique index for phone and email, and self-registration checks existing bound phone. Duplicate identity document check is within the same customer and document type, not a demonstrated cross-customer identity deduplication system; duplicate addresses are checked within the customer. No broad fuzzy/name/person matching was established. Input validators reject malformed names, dates, phones, countries and document fields. OTP expiration/lockout, missing permission, unsaved or invalid form fields, duplicate contacts and uncertain writes can prevent progression; the wizard permits skipped address and identity and does not guarantee readiness. Technical investigation3. KYC vs onboarding vs eligibility+

customers holds kyc_level and kyc_status; customer_kyc_assessments records current and superseded assessments. Every POST /customers/:id/kyc-assessment supplies level and status, with reason/expiry optional. Backend replaces assessedBy with authenticated actor. Allowed status transitions: NOT_STARTED→PENDING; PENDING→APPROVED or REJECTED; APPROVED→PENDING; REJECTED→PENDING. Same status is rejected. On every assessment, including PENDING, service copies the caller-selected level and status to customer; approval is not itself an automatic upgrade, and there is no demonstrated minimum evidence/level-document validation or maker-checker in this path. kyc.review, kyc.approve, kyc.reject are separately authorized based on target status. Admin Compliance KYC screen reads/submits assessment and selected level; this is a per-customer manual assignment/change, not configurable global level requirements. Individual/business document-type validation differs, but no comprehensive tier-by-tier requirements matrix exists in this assessment service. S32, S9, S10.

Separate onboarding entity: NOT_STARTED→IN_PROGRESS→AWAITING_REVIEW→APPROVED→COMPLETED, with REJECTED possible from IN_PROGRESS or AWAITING_REVIEW and no exit from REJECTED/COMPLETED. Approval status is separate from onboarding status. Prohibited onboarding risk prevents an approved decision or approved workflow status. Completion requires ACTIVE customer; active profile; a nondeleted address and identity-document record; at least one required agreement and all required agreements accepted; at least one required task and all completed; risk not PROHIBITED; onboarding APPROVED. Missing risk profile passes riskAllowed because only PROHIBITED is excluded. Presence is not verification. Workflow APPROVED transition itself does not establish every completion criterion. S33, S4, S34.

Separate eligibility record can become ELIGIBLE only after COMPLETED onboarding and absent active BLACKLISTED restriction; active product enrollment requires ELIGIBLE and not FROZEN. Operating projection prioritizes BLACKLISTED, FROZEN, CLOSED, LIMITED/MANUAL_REVIEW, revoked/suspended eligibility and then ELIGIBLE. Enabled permissions and active enrollments are reported but their presence is not required for OPERABLE in that projection; customer SUSPENDED is not explicitly checked there (only CLOSED). Neither this projection nor these enrollment/permission records should be represented as universally enforced at financial posting. S5, S35.

These backend workflow write handlers mostly lack explicit per-function checks within their controllers; the global RuntimeAccessGuard and route registry still apply. Generic /customers/:id/* accepts customer SELF or allowed workforce principal types; do not infer unauthenticated access, but do not infer robust action-specific role/maker-checker protection either. Actor fields in several legacy DTOs are caller-supplied. Investigate the exact authorization of these mutations, SELF ownership and audit provenance in isolated adversarial HTTP tests before relying on them. S36, S37, S38, S39.

Proof-of-address has its own protected storage/review workflow and Tier 3 readiness panel; it is not a demonstrated global LEVEL_3 auto-upgrade. Compliance cases and risk profiles have independent models/guards. S40, S41, S42.

Technical investigation6. Limits: configuration, resolution and enforcement+

Profiles/rules/assignments are stored in limit_profiles, limit_rules, limit_assignments; usage/reservations tracked separately. /internal/limit-profiles, /:code/rules, /internal/limit-rules/:id and /internal/limit-assignments expose create/read/patch, with limit.modify for non-agent assignments and agent.assign_limit for agent assignments; diagnostics require limit.view. Catalogue screen is read-only; assignment UI supports agent and agent-class creation/toggles and customer-scoped inspection, not a customer assignment creation form. API supports direct CUSTOMER assignment, subject to effective authorization; no verified one-off bypass of limit checks was identified. S57, S58, S59, S60.

Select live active effective assignments matching GLOBAL, individual CUSTOMER/AGENT, supplied AGENT_CLASS or supplied SEGMENT. Order precedence DESC, effective_from DESC, created_at DESC, limit 1; no implicit specific-over-global precedence or final unique tie-break shown. Disabled assignment is excluded, allowing another matching assignment to win. If the selected assignment references missing, deleted, disabled or non-ACTIVE profile, resolver returns no profile without falling back to the next assignment. Missing profile or no applicable rules → allowed, not zero limit. Rule matching: selected profile, exact product/currency, effective, active, nondeleted; direction null/BOTH/exact and channel null/exact. All matching rules are evaluated; priority orders but does not choose a single rule. MIN_AMOUNT_PER_TX, MAX_AMOUNT_PER_TX, DAILY/WEEKLY/MONTHLY/YEARLY amount/count and WALLET_BALANCE_MAX are supported; balance max checks incoming projected ledger balance, not outgoing. Windowed use includes reserved plus used, and reservations/commits are tied to the transaction where wired. Calendar windows use Africa/Lagos; weekly starts Monday. S11, S12, S61.

Limit modifications currently use function checks but not the commercial maker-checker service; governed-action.registry.ts explicitly excludes limit.modify pending future work. Seed gives FINANCE_PREPARER INITIATE and FINANCE_CONTROLLER APPROVE, but the runtime catalogue deliberately flattens access types into function codes: requireFunction('limit.modify') alone does not distinguish INITIATE from APPROVE. Consequently both seeded roles can satisfy that function check when their effective session and principal type permit the route; there is no independent approval consumption in the shown limit endpoints. Verify real session grants and configuration separately. The older per-customer customer_limit_profiles and CustomerLimitType exist independently; no use by the quoted LimitEnforcementService financial paths was found. S62, S63, S78.

Technical investigation7. Fees, commissions and rewards+

Fee rules (fee_rules) resolve by product, currency, active effective window and highest priority; top-priority tie yields AMBIGUOUS, no silent winner. Amount drives calculation (flat, percentage, min/max and VAT parameters), not a direct customer/KYC/segment target in this resolver. No customer-specific fee targeting was identified in this registry. NOT_CONFIGURED is not an explicitly configured zero. S64, S65.

Commission rules (commission_rules) resolve by product/currency, recipient type, optional agent/class/aggregator targeting and priority; same highest-priority tie fails closed. Principal, fee or net basis may require actual fee evidence. Agent transaction flows supply agent context; customer-only Transfer/funding do not supply agent/class, so no blanket claim of agent-specific commission. Rewards (reward_rules) support customer, KYC level, agent/class or campaign targeting (at most one), per beneficiary, priority and ambiguity checks. Resolver is read-only and no RewardEngine flow consumer was found. S66, S67, S68.

Fee/commission engines are called and snapshots recorded in several flows including Transfer, Cash-In/Cash-Out through agent financial execution, Cash-to-Cash initiation and funding. Some historical comments in resolvers say not wired; later call sites supersede those comments. Accounting is explicitly gated by COMMERCIAL_ACCOUNTING_ENABLED and applicable product, required account mappings, VAT and commission treatment/timing; configuration missing can fail closed when enabled. EXPENSE_PAYABLE accrual is not proof of paid agent wallet; AGENT_WALLET_NETTING can post credit only under its configured conditions. Customer/agent funding fee scope differs. Snapshot calculation alone is not ledger posting or settlement. No deployed flag, rules, account mappings or ledger was inspected. S13, S69, S14, S70.

Fee, commission and reward registries have create/modify APIs with governed request→independent FINANCE_CONTROLLER approval→execute matching change, FINANCE_PREPARER maker, MFA and no self-approval. Commercial screen provides read-only catalogue views, not a complete create/approve/execute UI. Product governance and approval features have their own boundaries. S71, S72, S60.
