# Batch 1 — Monnify identity adapter and access report

Status: isolated code and synthetic unit tests only; **not integrated, not live-verified, not approved for use**. Assessed 2026-11-06. No customer or financial state, UI, database, real environment file, provider account, or live endpoint was touched. The adapter is not registered in a Nest module or reachable through an endpoint, scheduler, or customer flow.

## Provider contract observed

| Capability | Official documentation | Adapter behavior and confidence |
| --- | --- | --- |
| Authentication | [API reference](https://developers.monnify.com/api) specifies POST `/api/v1/auth/login` with Basic base64 of `apiKey:secretKey`; [quickstart](https://developers.monnify.com/docs/collections/quickstart) says use its Bearer access token. | One login per operation; credentials injected by trusted caller, never logged; no token persistence. Mock-tested only. |
| BVN details match | [Verification guide](https://developers.monnify.com/docs/verification-api/verifying-your-customers) uses POST `/api/v1/vas/bvn-details-match` with BVN, name, date of birth (`DD-Mon-YYYY`), and mobile number; illustrative boolean `bvnInformationMatch`. Guide lists ₦10 per successful request. | Sends only these fields. Accepts that documented boolean; unknown or other shapes fail closed. |
| BVN/account name | Same guide uses POST `/api/v1/vas/bvn-account-match` with BVN, bank code, account number and name; illustrative boolean `bvnAccountNameMatch`. | Supports this illustrative contract; does not infer customer ownership from the match. |
| NIN | The [API reference](https://developers.monnify.com/api) and [official MCP implementation](https://github.com/Monnify/mcp-server/blob/main/src/tools/verification/verifyNin.ts) use POST `/api/v1/vas/nin-details` with `nin`; the guide instead uses `/api/v1/vas/nin-verification`. The guide lists ₦60 per successful request and sample fields including names, date of birth and `ninInformationMatch`. | Uses `nin-details` as the reference and official client agree, **but this discrepancy must be resolved with Monnify before use**. The returned sensitive details are for a future authorized comparison, not proof of ownership; the provider boolean alone is not a customer match. |

The guide explicitly says BVN/account, BVN details and NIN are **live only**, despite its sandbox example URLs. Name enquiry is separate and described as sandbox/live; this batch does not implement it. The [API reference](https://developers.monnify.com/api) also calls its verification category live only. The guide says checks fail when wallet funds are insufficient. Prices are documentation snapshots, not an approved budget or account-specific tariff.

A further response discrepancy matters: an older [Monnify BVN information reference](https://teamapt.atlassian.net/wiki/spaces/MON/pages/454459393/BVN+Information+Verification) shows `FULL_MATCH` / `PARTIAL_MATCH` / `NO_MATCH` fields rather than the current guide's boolean; an [older BVN account reference](https://teamapt.atlassian.net/wiki/spaces/MON/pages/454557732/BVN+and+Account+Name+Match) shows `matchStatus` / `matchPercentage`. The adapter deliberately reports unknown outcome on these shapes, rather than inventing match policy. Confirm current request and response formats for the actual account before integration. False means the provider returned a documented negative, not identity fraud.

## Safety and limitations

- Default construction is disabled. `monnifyOptionsFromEnvironment` accepts an explicitly supplied trusted environment/secret-manager snapshot, and only exact `MONNIFY_VERIFICATION_ENABLED=true` enables it. It never reads a file or environment on import. Secrets are `MONNIFY_API_KEY` and `MONNIFY_SECRET_KEY`; never place real values in source, tests, logs, or chat. **Do not enable or wire this provider until all approvals and safeguards below are complete.**
- HTTPS transport is fixed to `api.monnify.com`, exact paths only, checks all resolved IPs for non-public ranges and pins a validated address while retaining TLS hostname verification. No redirects, URL overrides or response bodies in errors; bounded response size and deadline including DNS. Failures after a verification dispatch, including provider rejection, malformed response, throttling, 5xx, or timeout, are conservatively `OUTCOME_UNKNOWN` because billing/replay semantics are unconfirmed. Authentication errors are `AUTH_FAILED`. Messages contain fixed codes only. No retry is performed, including login: maximum zero retries, avoiding duplicate charges.
- No official verification-specific rate limit or idempotency/requery contract was established. No claimed provider idempotency header. This adapter **does not implement durable idempotency, deduplication, reconciliation, customer consent, secure evidence storage, ownership matching, audit persistence or caller authorization**. In-memory/no-retry alone does not prevent duplicate calls, process crashes, concurrent requests or repeat charges. The existing generic idempotency record expires and can be removed, so it must not be assumed sufficient for ambiguous paid operations. A future caller must durably reserve an operation before dispatch, prevent concurrent/repeated execution, preserve unknown outcomes for governed review, handle crashes, and define reconciliation with Monnify before a retry or enabling any traffic.
- Adapter returns only match booleans for BVN and limited NIN identity fields in memory. NIN data is sensitive; callers must not log, expose in generic audit, or persist it without an approved access, encryption, retention and minimization design. No audit is written in Batch 1; an authorized, durable, access-controlled audit with safe metadata only is required before use. Provider results do not constitute identity ownership, KYC tier, eligibility, financial readiness or entitlement.
- Known provider failures described by the guide include invalid BVN/NIN/bank/account, account-validation failure and service unavailability; message text may contain identity data and is not propagated. No reliable verification-specific code mapping was established. Provider-side entitlement, wallet funding, network/IP allowlisting, operational limits, actual billing, current payloads, error shapes, retry and reconciliation procedures must be confirmed with the account owner/Monnify. The [go-live guidance](https://developers.monnify.com/docs/live) mentions whitelisting and live keys; no account configuration was inspected.
- Before any live lookup: obtain separate explicit user/business authorization, provider/account confirmation, consent and privacy/legal approval, funds/budget controls, durable charge/replay safeguards, safe audit, egress and secret-management review, and a reviewed integration plus isolated tests. Do not run production calls or interpret mock success as provider access.

## Tests

`npm test -- test/monnify-verification.unit.spec.ts` uses synthetic identifiers and mocked network, plus test-only DNS/HTTPS doubles under the repository network guard. It covers disabled/config/input cases, both BVN operations and NIN contract fixtures, auth, negative and malformed responses, fixed error messages, no automatic retries, timeout/abort, disallowed IPs/paths, DNS-rebinding defense and redirect handling. This is not a live or provider sandbox test; no DB is involved.
