## 5. Concurrency-control mechanism per service (before this task)

- **CommissionRuleRegistryService.updateRule()**: manual compare-and-swap — `this.repo.update({ id, version }, { ...changes, version: () => 'version + 1' })`, then checks `result.affected !== 1` and throws `ConflictException` if so. This *is* a real DB-level CAS: the `WHERE id = ? AND version = ?` predicate is generated by TypeORM's `update(criteria, partial)` overload, so a losing concurrent writer's `UPDATE` matches zero rows and `affected === 0`.
- **RewardRuleRegistryService.updateRule()**: byte-identical pattern to commission (same `repo.update({id, version}, {...})` + `affected !== 1` → 409).
- **LimitCatalogService.updateProfile() / updateRule()** (before fix): `this.profileRepo.findOne({ where: { code } })` / `this.ruleRepo.findOne({ where: { id } })` to read the row into memory, synchronous in-process `assertVersion(current, incoming)` check, then `this.profileRepo.save(profile)` / `this.ruleRepo.save(r)`. TypeORM's `save()` on an entity with a `@VersionColumn` does append `SET version = version + 1`, but it does **not** add a `WHERE version = :old` predicate — `save()`'s optimistic-locking behavior in TypeORM only throws `OptimisticLockVersionMismatchError` when you explicitly pass `{ version: expectedVersion }` through `manager.save(Entity, entity, { version })`/QueryBuilder `.setLock('optimistic', version)`, which this code never does. The in-process `assertVersion` check only protects against *sequential* stale requests (an old version read earlier, submitted later); it provides no protection at all when two requests both read the current version concurrently before either writes.

## 6. Exact SQL/transaction evidence

- Commission/Reward: `UPDATE commission_rule_definitions SET ..., version = version + 1 WHERE id = $1 AND version = $2` (and the reward equivalent) — confirmed by reading the `repo.update({id, version}, {...})` call sites; this is the actual CAS predicate TypeORM's `update(criteria, partial)` overload compiles.
- LimitCatalogService (before fix): `SELECT * FROM limit_profiles WHERE code = $1` / `SELECT * FROM limit_rules WHERE id = $1` (plain, no lock clause, no transaction) followed later — after in-process field mutation — by `UPDATE limit_profiles SET ..., version = version + 1, updated_at = now() WHERE code = $1` / equivalent for `limit_rules`, with **no `version` in the WHERE clause**. Two concurrent requests reading the same row both see the same starting version, both pass `assertVersion` in-process, and both issue an unconditional `UPDATE ... WHERE code = $1`, with the later commit winning — a classic lost update, not merely a theoretical one.
- LimitCatalogService (after fix): both methods now run inside `this.dataSource.transaction(async (manager) => { ... })` and read the row via `manager.getRepository(Entity).createQueryBuilder(...).where(...).setLock('pessimistic_write').getOne()`, which compiles to `SELECT ... FROM limit_profiles WHERE code = $1 FOR UPDATE` (Postgres row lock). A second concurrent transaction's `SELECT ... FOR UPDATE` on the same row blocks until the first transaction commits, then returns the **post-commit** row with the incremented version, so `assertVersion` correctly rejects the stale submitted version with a clean `409`.

## 7. Concurrent test methodology

PostgreSQL-backed, HTTP-layer, `Promise.all`-fired, un-awaited-until-fired pairs of requests against the same starting resource version, run with `--runInBand` (single Jest worker, so the only source of interleaving is the app's own request handling and the DB, not Jest parallelism):

- Commission: existing test #11 in `test/v1-commission-01-commission-engine.integration.spec.ts` ("concurrent creates race to one identity winner; concurrent updates race optimistic versions").
- Reward: existing test #11 in `test/v1-reward-01-reward-engine.integration.spec.ts` (same pattern).
- Limit catalog: two **new** tests added this task, `test/v1-limit-01-limit-catalogue.integration.spec.ts` #14 ("concurrent PROFILE updates from the same version: exactly one must be rejected, not both applied") and #15 (identical shape for `LimitRule`). Both create a resource, then fire two concurrent `PATCH` requests carrying the *same* starting `version` via `Promise.all`, and assert: exactly one response is `200`, exactly one is `409`, the `409` body contains no raw DB error signature (`QueryFailedError|duplicate key value|SQLSTATE|at \w+\.\w+ \(`), and the final DB row (read directly via a fresh `SELECT`) matches exactly the winner's submitted values with `version = 2`.

Each service's test was run repeatedly (not once) because a two-request HTTP race's outcome depends on Node event-loop / connection-pool timing; a single isolated pass is not sufficient evidence of safety (see §8).

## 9. Which services are vulnerable

**`LimitCatalogService`** — both `updateProfile()` and `updateRule()` — confirmed vulnerable to the lost-update race (silent overwrite under genuine concurrent requests).

## 10. Which services are already safe

- **`CommissionRuleRegistryService.updateRule()`** — safe. Uses `repo.update({id, version}, {...})` which compiles to an atomic `UPDATE ... WHERE id = $1 AND version = $2`; a losing writer's `affected` count is `0`, mapped to a clean `409`. Confirmed live (10/10 passes, §8); no code change made.
- **`RewardRuleRegistryService.updateRule()`** — safe, identical reasoning and identical confirmed-live result. No code change made.

Both are structurally identical in business model to `FeeRuleRegistryService` (mutable, administratively-controlled rule rows) but were **not** vulnerable because they already used the correct CAS pattern at the point V1-TEST-01 found and fixed the bug in `fee-rule-registry.service.ts`. Code-shape resemblance to a vulnerable sibling is not itself evidence of vulnerability — per task instruction, each was independently proven safe by live concurrent test rather than assumed safe or unsafe from inspection.

## 11. Exact fixes

`src/limit-catalog/limit-catalog.service.ts`:

- **`updateProfile(code, input, actor)`**: row-independent input validation (code pattern, enum checks, name non-empty) now runs first, outside any transaction. The read, `assertVersion` check, field mutation, and `save()` are now wrapped in `this.dataSource.transaction(async (manager) => { ... })`, reading the row via `manager.getRepository(LimitProfile).createQueryBuilder('profile').where('profile.code = :code', {...}).setLock('pessimistic_write').getOne()`. The existing best-effort audit-record write (wrapped in its own try/catch, unchanged in behavior) now runs after the main transaction has committed, so it only fires for the confirmed winner. The pre-existing (previously unreachable — profile `code` cannot be changed via update, so no real unique-index collision was possible) `isUniqueViolation` → `ConflictException('Profile version conflict')` catch was preserved around the transaction for defense in depth.
- **`updateRule(id, input, actor)`**: same approach — row-independent validation (product/currency pattern, dimension enum, date parsing) runs first; the row read, `assertVersion` check, field mutation, amount/count-exclusivity re-validation, and `save()` are wrapped in `this.dataSource.transaction(...)` with `setLock('pessimistic_write')` on the `LimitRule` row. The existing `isUniqueViolation` → `ConflictException('Limit rule unique constraint violation')` catch (genuinely reachable here, since `product`/`direction`/`channel`/`currency`/`dimension`/`effectiveFrom` combinations are uniquely constrained and *are* mutable via update) was preserved around the transaction.

No changes were made to `commission-rule-registry.service.ts` or `reward-rule-registry.service.ts` (proven safe, left untouched per task instruction).

## 16. Remaining concurrency risks (not fixed, out of this task's scope)

- `LimitCatalogService` has no `isCheckViolation` helper (only `isUniqueViolation` exists in the file's private-helpers section). `limit_rules` has a real DB-level `CHECK` constraint (`chk_limit_rules_amount_count_exclusive`) that mirrors the application-level `validateDimensionValue()` check. If application validation and the DB constraint ever drift apart (e.g. a future code change to `validateDimensionValue` that stops matching the migration's constraint), a `CHECK` violation could reach the client as a raw `QueryFailedError`/SQLSTATE rather than a clean 4xx. This is a **pre-existing, unrelated error-handling gap**, not a concurrency defect, and was not introduced or worsened by this fix — it was deliberately left unmodified to respect this task's scope control (fix only the proven lost-update race; no speculative or unrelated hardening). Recommended as a follow-up, not addressed here.
- No other mutators were found in any of the three services that read-modify-write a versioned row outside a transaction; `createProfile`/`createRule` in all three services are pure inserts (no lost-update surface), and list/get paths are read-only.
