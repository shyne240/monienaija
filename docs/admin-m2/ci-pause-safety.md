# M2 CI and notification pause — investigation

## Current behavior (no workflow changes)

- `.github/workflows/ci.yml` runs on pushes and pull requests. It retains the mandatory PostgreSQL job, sets `NOTIFICATION_WORKER_ENABLED=false` and `CASH_TO_CASH_EXPIRY_WORKER_ENABLED=false`, and applies `test/support/mission-25c-network-guard.cjs` to backend tests. The guard restricts Node network connections/DNS to loopback, but is not an independent network firewall.
- `npm run test:pg` discovers **all** `*.integration.spec.ts` suites. The job-level worker flag is not an absolute prohibition: `test/v1-notification-provider-configuration-01.integration.spec.ts` and `test/mission-25o-credential-binding.integration.spec.ts` set the flag to true in their own disposable test processes. The former injects `mockTransport`; the latter also injects a mock transport and explicitly calls `worker.tick()`. These are simulated notification/worker tests, not deployed workers, but they really do start or invoke test worker code in the CI test process. A blanket claim that no worker code runs in full CI would be inaccurate.
- A simulated send using disposable data and a verified injected fake transport is different from sending to an actual provider, but its safety depends on the mocks, environment and egress controls. The cited tests are examples, not an audit of every notification test or a guarantee that all paths are mocked. Enabling a worker against an actual database/provider, supplying real credentials, making a real test-send, or bypassing the mock/egress guard can create real side effects and remains prohibited.
- At this checkpoint the latest completed full CI on `0070eaf` passed all four jobs. The older PostgreSQL failure `42631452865` still has no diagnosis: repeated retrieval of job `129208654784` failed with EOF. The prior `785dffd` commit was marked skip-CI under the previous broader pause interpretation; there is no full CI result for it. The owner approved a normal push and the existing isolated simulated test-worker execution while keeping real SMS and deployed workers paused. This continuation does not skip CI or change its workflow or test restrictions; monitor the automatically triggered run.

## Pause-safe gate proposal — owner decision needed, not implemented

1. Keep deployed notification workers disabled, no real SMS test-send, no real provider credentials and no actual customer data. Separate and disposable CI database, test secrets and test-only principals are mandatory.
2. Have Security/CI owners audit the full notification-test inventory, verify every provider transport is fake and fail-closed, and enforce infrastructure-level deny-by-default egress after dependencies are installed (allow only required loopback/test database traffic). The existing Node guard is useful defense in depth, not a substitute for this independent boundary. Verify CI cannot reach production databases/providers; record a deliberately blocked-egress check without sending a message.
3. The owner has permitted **isolated simulated worker tests** while deployed workers remain paused. Preserve full coverage and have CI/Security verify mocks, disposable databases and infrastructure egress isolation for every relevant path. Approval of simulated tests is not approval for real sends or deployed workers. Simply forcing the flag false breaks tests that intentionally exercise worker code, and silently excluding them would weaken the mandatory gate.
4. Do not remove, skip or mark the PostgreSQL job optional. Agree how missing diagnostics from the earlier failed run will be investigated and how to retain accessible logs. Do not interpret a later green run as a diagnosis of the earlier failure.

No real SMS send, deployed worker, vendor call, workflow change or new testing restriction was introduced during this investigation. The current environment's manually selected authorization suites also ran with workers disabled and the loopback guard; see the acceptance report.
