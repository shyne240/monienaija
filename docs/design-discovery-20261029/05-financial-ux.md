# Financial UX: evidenced journeys and safety boundaries

**Discovery and design guidance only.** The following describes source evidence, not end-to-end or production verification. No APIs, security rules, providers, money flows, accounting, logs or migrations were changed. Where a contract or policy is absent or uncertain, the interface must say so and the decision goes to its owner—not to a designer or a frontend calculation.

## Money and status display contract

1. **Amount:** preserve exact minor-unit value from the existing contract; format locally only with safe precision, explicit NGN/currency, decimal places and sign. Never reimplement ledger calculation, fee, tax, commission or settlement rules in a visual component.
2. **Recipient:** display only a verified backend-returned name when the relevant resolver actually supplies one. Otherwise label the supplied ID/phone accurately; do not call it verified. Preserve masking/authorization for contact and identity data.
3. **Fee, VAT, total:** use authoritative values with clear labels and timing (simulation, pre-submit quote, or post-result). If absent, show “not available” rather than `₦0.00`; any policy to block, delay, or estimate a fee is a decision, not an inferred default.
4. **Review/authorization:** present exact entity, amount, currency, action and consequential effect before the already-supported irreversible action; retain current maker/checker and MFA/role/function checks. Confirmations do not imply execution or settlement.
5. **Results:** map only server-supported statuses; include a safe reference/time when supplied, and differentiate confirmed posting, replay and any non-ledger operational action. Do not call a locally submitted request “completed.”
6. **Sensitive data:** no passwords, PINs, OTPs, bearer tokens or transfer secrets in logs, analytics, ordinary notification templates, support context, share payloads or screenshots. The public claim locator is not the secret. Existing secret lifecycle and direct OTP paths remain authoritative and require Security review before any visual restructuring.

## Outcome vocabulary and retry safety

| UI state | What can be said | What must not be inferred |
|---|---|---|
| Loading / submitting | “Processing” or “Checking status”; disable duplicate activation while preserving the existing implementation's synchronous guard. | That the operation failed, succeeded or was cancelled. |
| Confirmed result | Describe the specific server-returned status and financial effect; show safe reference. | Physical handover, verified identity, provider delivery or approval not proven by the response. |
| Replay / already recorded | Explain the result refers to the same previously recorded instruction where the response indicates replay. | That every new request is safe or a fresh transaction occurred. |
| Definitive rejection | Show the known rejection and allowed correction/support path, using existing contract semantics. | That every 4xx globally has no effect; rely on each flow's documented error contract. |
| Unknown / ambiguous | “Outcome not confirmed. Check the existing status/history or recovery path before another attempt.” Preserve the same logical intent and key according to the existing flow. | Automatic failure, reversal, refund, a new operation, or guaranteed success. |
| Restricted / inaccessible | Explain access is restricted without exposing protected data; offer only existing permitted assistance. | That a workforce role implicitly grants compliance access. |
| Empty / not found | Use only when a successful authoritative response establishes absence; preserve not-found semantics. | That a network error, stale response or lack of authorization means no records. |
| Cash-to-Cash unclaimed / claimed / expired | Display the status and known timestamps from the server, distinguish reserved vs claimed. | Any unapproved expired-funds refund, release, redistribution or physical payout. |

## Required owners and tests before implementation

- **Product + Finance:** decide verified-recipient and fee/total preview requirements and what happens when unavailable; any backend work is separately scoped. Resolve Wallet→Cash receipt wording with Operations.
- **Security + Product:** reconcile Cash→Cash secret instruction with the standing no-credential-distribution rule; preserve OTP/PIN secrecy, MFA, authorization and provider governance.
- **Engineering + QA:** contract-test confirmed, pending, replay, definitive rejection, timeout/unknown, restart/recovery and duplicate interaction for every touched existing money flow. Test the same request/intent behavior already implemented; do not change keys or financial semantics to fit a design.
- **Compliance + Security:** confirm wording for KYC evidence vs reviewed assessment and human vs SERVICE decisions; no authorization policy changes are implied.
