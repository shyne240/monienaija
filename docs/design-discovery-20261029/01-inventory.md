## Counting rules and portfolio

* **Admin Web:** 28 canonical in-memory authenticated views + conditional Login = **29 view entries**, backed by **22 distinct routed screen components** (21 in the switch + Login). Nine legacy aliases canonicalize to existing views and are not extra views. App-level session loading and access-denied states are not separate routes.
* **Customer Mobile:** **12 registered native-stack route names**, 12 unique components, including conditional Splash. `Profile` has no incoming navigation found; `TransactionPin` is linked only from `Profile`. Two sandbox screen files are unregistered, not in route types and excluded from the 12.
* **Agent Mobile:** **28 registered native-stack route names**, including conditional Splash and `History` as a second name for the `Transactions` component, **27 unique components**. One generic `PlaceholderScreen` is unregistered and excluded.
* Thus **69 view/route entries** = 29 + 12 + 28 and **61 distinct routed screen implementations** = 22 + 12 + 27. These are different concepts: Admin uses React state, not URL routes; native stacks are conditional on session/credential state. No route is assumed simultaneously accessible to every role. The audit also covers 13 embedded Admin workspaces/panels and three unregistered mobile screens, giving **85 assessment rows**; 69 + 13 + 3, with aliases repeated intentionally. Embedded panels and conditional states do not increase the routed-screen count.
* The repository scan found **three frontend application projects** with manifests/entry points below; this count does not imply each builds or runs successfully. The root [package.json](../../package.json) is the NestJS backend/tooling package, not a fourth frontend. No separate merchant or aggregator portal is present; [V1 UAT](../uat/V1-UAT-FINAL-01.md) marks aggregator self-service decision-pending and QR/card/PoS/marketplace never built. Planned capabilities are not present UI.

## Aliases, nested surfaces and component reuse

* Admin has exactly nine *internal view aliases*: `ledger → ledgerExplorer`, `transactions → transfers`, `commercial → feeRules`, `compliance → kycQueue`, `riskfraud → fraudCases`, `roles → roleGovernance`, `approvals → approvalsInbox`, `workforce → workforceAccess`, `system → systemHealth`. See [navigation-access.ts](../../apps/admin-web/src/screens/authenticated/navigation-access.ts). They are not nine additional URL routes; current navigation is local component state. Customer-context return navigation is separately guarded and must be retained.
* Admin dashboard has reusable [KpiTile](../../apps/admin-web/src/components/dashboard/KpiTile.tsx), [WidgetCard](../../apps/admin-web/src/components/dashboard/WidgetCard.tsx), [PeriodControls](../../apps/admin-web/src/components/dashboard/PeriodControls.tsx), [widget renderers/SVG chart](../../apps/admin-web/src/components/dashboard/widgets.tsx), a widget data hook and dashboard-specific [tokens](../../apps/admin-web/src/components/dashboard/tokens.ts). The common [StructuredData](../../apps/admin-web/src/components/StructuredData.tsx) renders record tables/values; Customer registration/servicing also use [CountrySelect](../../apps/admin-web/src/screens/authenticated/CountrySelect.tsx), [CustomerFormFields](../../apps/admin-web/src/screens/authenticated/CustomerFormFields.tsx), [masking](../../apps/admin-web/src/screens/authenticated/customer-masking.ts) and [customer-management.css](../../apps/admin-web/src/screens/authenticated/customer-management.css). These are component-level inventory, evaluated within their parent screens, not additional route counts.
* Both native apps have separate copies of `theme/{colors,spacing,typography,index}` and `Button`, `Card`, `Input`, `ErrorBoundary`, `ErrorState`, `LoadingState`, `TransactionRow`; compare [Customer components](../../apps/customer-mobile/src/components) and [Agent components](../../apps/agent-mobile/src/components). A byte comparison at this baseline found all four theme files and `Button`, `Card`, `Input`, `ErrorBoundary`, `ErrorState` identical; `LoadingState` and `TransactionRow` differ. Customer uniquely has `AmountInput`, `StatusBadge`, `ConfirmationDialog`; Agent adds `AgentReceipt`, `CapabilitiesList`, `MfaChallengeCard`. Similar names do not guarantee identical props, accessibility or financial behavior.
* Notifications/activity: Admin Notifications is a nine-tab operations console (not a customer inbox); Admin System Health includes outbox and deliveries, Audit has security events; customer/agent have transaction history and support activity, but no dedicated push/in-app notification inbox found. SMS/email provider labels in source do not establish live readiness.
* Authentication/onboarding: Admin login has workforce email/password and dev-only engineering controls; customer has welcome, phone OTP registration and separate login; agent has login plus mandatory credential rotation. User data, OTP and PIN behavior stays in existing contracts.
