# Phased roadmap, ownership and decision register

**This is a proposal, not authorization to implement.** The current assignment permits documentation only. The standing restrictions on editing Admin/Agent application files, modifying security or backend behavior, creating a separate branch, merging, deploying and changing financial logic remain in force. Any future implementation requires explicit Product Owner approval **and** explicit release of the applicable file/scope restrictions; it must use the session-pinned branch unless the platform changes that constraint. Backend/Admin completion precedes mobile. Arena 4's independent security acceptance is ongoing and is not replaced by this UX work.

### Sizing assumptions

One person-day = one person working one day. Estimates include incremental UI implementation **only after all relevant permissions are granted**, review and tests for existing functionality; they exclude backend/API feature expansion, vendor work, production deployment, major design research, and time waiting for independent security acceptance. Cross-role effort includes Product, Finance, Security and accessibility review; it is not a promise of their availability.

|---|---:|---:|---:|---:|---:|
| M0 | 1–2 | 3–5 | 2–3 | 2–4 | **8–14** |

The **12–18 week** rough calendar assumes roughly 2 frontend engineers for M1, 3 for M2, and two dedicated engineers on each mobile stream in parallel after the backend/Admin gate, with shared design, QA and independent reviewers available as budgeted. M0 → M1 → M2 → max(M3,M4) → M5 is the critical sequence. These ranges are planning hypotheses; contract expansion, device defects, security findings, lack of parallel staffing or owner delays change the schedule materially.

## Risks, handoffs and controls

- **Safety / concurrent ownership:** Arena 2 exclusively owns F-01/F-05 provider behavior; Arena 3 owns authorization catalogue, funding controllers and product-catalogue modules as well as its producer work. Arena 4 performs independent security acceptance. UI work does not change those files or duplicate producers; coordinate documented handoffs before touching their surfaces. Existing notification reliability handoff is [here](../ARENA1-NOTIFICATION-RELIABILITY-HANDOFF-20261028.md).
- **Financial invariants:** preserve `CUSTOMER_WALLET` vs `AGENT_CASH`, ledger journals, transfer settlement, exact money semantics, unknown/replay handling and migration 100. No change to database migrations or backend logic merely to make a UI test pass.
- **Availability and truth:** error must not become no data; any dashboard metrics have an owner and definition; simulated values cannot look like authoritative transaction fees.
- **Accessibility:** current source uses mixed semantics; one owner maintains automated checks plus manual web/native assistive-tech evidence. Scorecard numbers are triage, not a WCAG certification.
- **Operational continuity:** 28 Admin views, legacy aliases, actions, contextual guards and both native stacks remain represented. Pilot changes are incremental, with tests and rollback by ordinary revert of an approved future commit—not reset, rebase or force-push.
- **Baseline quality:** Customer `npm ci` needed `--legacy-peer-deps` and its typecheck currently fails; mobile suites emitted React `act` warnings. Address only in approved follow-up scope. Admin build's chunk warning warrants measurement before performance optimization; no new dependency is assumed.
- **No production inference:** current screenshots are synthetic, no real credentials or vendor calls were used, and passing frontend unit tests do not certify security, ledger correctness, end-to-end behavior or provider readiness.

## Recommended first milestone

Approve **M0**, then authorize **M1: Admin light-token foundations, accessible shell and read-only Customer Directory presentation pilot**. This confines initial work to the best-evidenced app and minimizes financial or security risk while establishing the system for the remainder. Preserve New Customer and all other existing actions/guards. Start no implementation until the Product Owner approves the phase and explicitly permits the affected files to be edited; await the parallel security team's own acceptance where required.
