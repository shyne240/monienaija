## 1. Product decision this inventory is written against (binding, 2026-11-19)

Agents may transfer from their authorized operating wallet to **any valid external bank
beneficiary**: their own bank account, another individual's bank account, or any eligible bank
beneficiary. **Not** restricted to own account. **Not** a workforce treasury action. The agent
uses the **existing operating wallet**; there is no separate personal agent wallet and there must
never be a second financial engine. Institutional governance, agent class of service, applicable
product capability, directional limits, PIN authorization and commercial configuration all apply,
exactly as they do to other agent financial operations.

## 2. Route families serving the agent banking journey today

(`src/authorization/route-policy-registry.ts`): identity comes from the session; a path parameter
is never an authorization; no agentId from a request is trusted.

## 3. What the agent app exposes today (mobile truth)

`apps/agent-mobile/src/services/agent-banking.ts`: funding-account view/request/deposits only —
an agent can see the account float should be sent to and verified arrivals. The client explicitly
cannot move money out. No bank directory, no name enquiry, no beneficiary management for bank
accounts, no outbound transfer, no confirmation, no receipt. `FundingAccountScreen.tsx` implements
A1–A3 UX.

## 4. Gaps that block the complete agent journey (ordered by dependency)

1. **Service vocabulary + governance**: add an agent service capability for external bank transfer
   (e.g. `EXTERNAL_BANK_TRANSFER`) with class-of-service, limit and capability evaluation — decided
   with the same A10/A11 mechanism, not a side door.
2. **Shared authority (Group 9)**: extend the A6 financial-commitment architecture so an
   **agent-self** initiation binds: authenticated agent principal; operating-wallet ownership
   re-checked inside the commitment transaction; agent-class/service capability; directional
   limits; PIN; destination binding to an agent-owned BANK_ACCOUNT (or wallet) beneficiary;
   provider routing via the governed registry; immutable evidence; settlement/rejection effects.
   Customer and agent paths must share one commitment engine — not two engines.
3. **Agent bank-beneficiary self-service**: list/create/nickname/suspend/delete for BANK_ACCOUNT
   destinations, enforced under the agent's ownership; name-enquiry-confirmed creation only;
   immutable destination binding after creation.
4. **Agent confirmation surface**: principal/fee/VAT/total-debit preview bound at authorization
   time; refusal if drift exceeds the confirmed intent. Agent commission handling must be explicit
   (agent party to an operation earns via commission engine, never by taking a cut invisibly).
5. **Mobile experience**: bank selection, beneficiary management, confirmation, PIN, durable
   interrupted-operation recovery (reuse `pending-operation.ts` with a new operation type), tracking,
   history, receipts — the full loop, matching the customer journey in capability (minus workforce/treasury framing).
6. **Outcome handling**: RESERVED never shown as settled; unknown → confirming; definitive rejection
   compensates (reservation release) via the existing settlement bridge; notifications on definitive outcomes.

## 5. What must NOT be built

- No separate personal agent wallet, no second financial engine, no agent-side treasury framing.
- No own-account-only restriction; no requirement that the beneficiary be the agent's own account.
- No agent capability that bypasses class-of-service/limits/PIN/operating-wallet authority.
- No caller-supplied `agentId` treated as authorization anywhere.
- No workforce principal initiating "agent" bank transfers on an agent's behalf (that is the admin
  console, a different mission surface with its own governance).
- No fabricated provider references; RESERVED is never presented as settled.
