## 1. Events, channels, recipients, and variables

`GET /api/v1/internal/notifications/events` returns `{items: [...]}`, **not** the older proposed `{data: [...]}` DTO. Each item is `{eventType, deliveryClass, editable, variables, channels}`; each `channels.SMS` / `channels.EMAIL` is `{enabled, locked, configurationVersion, activeTemplateVersion}`. These are current database configuration values, not proof that a producer, recipient resolver, worker, or external vendor is operational. The table below describes the frozen seed and code mapping; real databases can have governed versions and enablement changes.

| Exact event type | Class | Mapped recipient and channel | Allowlisted template variables |
|---|---|---|---|
| `customer.funding.requested` | INFORMATIONAL | Customer SMS; optional customer EMAIL | `reference`, `amount_clause` |
| `customer.funding.approved`, `customer.funding.rejected` | TRANSACTIONAL | Customer SMS; optional customer EMAIL | `reference`, `amount_clause` |
| `transfer.completed` | TRANSACTIONAL | Both source and destination CUSTOMERs, deduplicated for self-transfer; SMS and optional customer EMAIL | `reference`, `amount_clause` |
| `transfer.failed` | TRANSACTIONAL | Source CUSTOMER; SMS and optional customer EMAIL | `reference`, `amount_clause` |
| `support.ticket.created`, `.assigned`, `.resolved`, `.closed`, `.message_added` | TRANSACTIONAL | Ticket-bound CUSTOMER and/or AGENT SMS; optional EMAIL for CUSTOMER only | `reference` |
| `support.ticket.status_changed` | TRANSACTIONAL | Ticket-bound CUSTOMER and/or AGENT SMS; optional EMAIL for CUSTOMER only | `reference`, `status` |
| `cash_to_cash.created` | INFORMATIONAL | Beneficiary PHONE, SMS only; registration not required under the existing code contract | `sender_name`, `amount`, `locator_clause` |
| `cash_to_cash.claimed`, `cash_to_cash.expired` | INFORMATIONAL | Mapped claimant/beneficiary CUSTOMER and/or AGENT, SMS only when a suitable fact exists | `reference`, `amount_clause` |
| `agent.application.approved`, `agent.application.rejected`, `agent.activated`, `agent.suspended`, `agent.terminated`, `agent.reactivated` | INFORMATIONAL | Mapped AGENT SMS only; authoritative Agent phone resolver is missing, so Agent legs are skipped | `reference` |
| `customer.registration.phone_verification`, `customer.credentials.temporary_credential`, `agent.desk.customer_otp` | SECURITY | Code-owned direct SMS; not ordinary outbox/template delivery | None exposed to editable templates |

The shorthand support names in the table all retain the full `support.ticket.` prefix. `transfer.unknown` maps to the `transfer.failed` template/configuration; `cash-to-cash.claimed` and `cash-to-cash.expired` map to the corresponding underscore names. Aliases do not add catalogue rows. `cash_to_cash.*` and Agent events are **not** augmented with customer EMAIL by the existing email-intent helper. The previous proposed UI variable `agent_locator_url` is not the active template variable: use `locator_clause`. Never add transfer codes, sender/beneficiary phone, journal or ledger IDs, or arbitrary message bodies to previews or customer content.

For a clean seed, every ordinary event has SMS enabled, EMAIL disabled, and `locked=false`; the three SECURITY events have SMS enabled, EMAIL disabled, `locked=true`, `editable=false` and no editable templates. The registry enforces SECURITY locks server-side. `required` in historical prose or the old static frontend catalogue is **not** a server lock. A D-N8 owner decision is still required for additional transactional locks: existing Admin Web marks `customer.funding.approved`, `customer.funding.rejected`, and `transfer.completed` locked while this backend seeds them unlocked. Do not present either interpretation as newly approved policy, silently disable mandatory protections, or treat a UI lock as authorization.

Customer EMAIL intents are created only for the funding/transfer/support allowlist when an effective email provider is selected. Event/channel enablement, verified contacts and customer channel preferences still gate delivery. SMS/email opt-out here is not marketing consent. There is no functioning PUSH token/provider path, and Agent phone/email authority is unresolved. A customer inbox item is projected from each non-skipped CUSTOMER delivery, not an independently deduplicated in-app notification; SMS+EMAIL may therefore produce two inbox items. The `notification_in_app_enabled` preference is not an independent delivery gate in this projection.

`deposit.completed`, `deposit.failed`, `withdrawal.completed`, and `withdrawal.failed` are existing **business facts**, not notification catalogue entries. They have no approved generic customer notification mapping, variables or channels here; unsupported facts are quarantined, not silently sent. Do not add UI toggles or imply these notifications exist until product/security approve the actual recipient, content, preference and channel policy. Ordinary Agent D8/D9, the cash-to-cash locator/release gate, and other blocked product decisions remain separate open decisions.

## 2. Support-message producer/consumer contract

A new public message emits `support.ticket.message_added` with aggregate `SUPPORT_TICKET`, aggregate ID/ticketId, messageId, authorType, authorId, explicit `isInternal:false`, and event key `support.ticket.message_added:<messageId>`. No message body is emitted in the notification fact. Internal notes emit no such producer fact. In the transaction the notification consumer verifies the committed message and ticket, public visibility and author binding under share locks and derives recipients from the ticket; supplied recipient IDs must match. Direct dispatch applies the same verification. Message identity, rather than a caller-supplied alternative key, is used for delivery idempotency.

An explicit `true` marker is suppressed as `INTERNAL_SUPPORT_MESSAGE`; a missing/non-boolean marker, forged author/recipient, mismatched ticket, invalid message ID or missing/private message is `QUARANTINED` with `SUPPORT_VISIBILITY_UNKNOWN`. Unsupported schema is quarantined separately. Do not weaken this check or infer visibility from missing fields. Existing historical message events without the marker remain quarantined: any recovery or replay requires an owner-approved, audited procedure that re-verifies the source message, and must preserve unique delivery identity. This mission does not backfill or automatically release them.

For the existing status producer `{ticketId, from, to, actor}`, `to` is now recognized as an allowlisted status and the safe ticket reference is rendered. Neither `actor` nor the message body becomes notification text.

## 3. Registry and governance HTTP contract

All paths below have prefix `/api/v1`. Authorization is server-side and remains authoritative. `notification.view_deliveries` is the ordinary catalogue read function; an independent FINANCE_CONTROLLER reviewer follows the existing review policy. Template and trigger changes use the existing interim SUPER_ADMIN maker / independent FINANCE_CONTROLLER checker, MFA, version and approval-consumption checks; do not substitute the old proposed `PATCH` or invent additional backend role grants.

| Endpoint | Actual request / response |
|---|---|
| `GET /internal/notifications/events` | `{items: [{eventType, deliveryClass, editable, variables, channels: {SMS, EMAIL}}]}`; each channel exposes `enabled`, `locked`, `configurationVersion`, `activeTemplateVersion`. Missing/corrupt catalogue data fails closed. |
| `GET /internal/notifications/templates?eventType=...&channel=SMS|EMAIL&locale=en-NG&limit=...&beforeVersion=...` | Event and channel required; `{eventType, channel, locale, items: [{id,eventType,channel,locale,version,active,subject,body,createdBy,createdAt}], nextBeforeVersion}`. No security templates. |
| `POST /internal/notifications/templates/preview` | Body `{eventType,channel,locale?,subject?,body?}`; uses active content if `body` omitted, fixed synthetic samples only. Returns `{eventType,channel,locale,subject,body,variablesUsed}`. Read-only unsafe-method restrictions still apply: a preview POST is not a general exemption. |
| `GET /internal/notifications/changes` and `GET /internal/notifications/changes/:approvalId` | List returns `{page,limit,hasMore,items}`; detail returns stored change, requester/checker and approval status. List statuses: `REQUESTED`, `APPROVED`, `REJECTED`, `CANCELLED`, `CONSUMED`, `EXPIRED`. |
| `POST /internal/notifications/changes` | `type` is `CONFIGURATION`, `TEMPLATE`, or `TEMPLATE_ROLLBACK`; requires exact event/channel, `expectedVersion`, `reason`, and respectively `enabled`, `subject`/`body`, or `sourceVersion` (template locale is `en-NG`). Returns `{approvalId,status,actionType,actionFingerprint,requestedAt,expiresAt}`. Requesting is not application. |
| Existing workforce approval routes, then `POST /internal/notifications/changes/:approvalId/execute` | Independent checker approves; the same approving checker executes the stored proposal with an empty body. Returns the changed configuration/version or the new template version. 403 for denied/locked, 409 for stale version or conflicting state. |

Do not reinterpret maker-checker, MFA, read-only methods, audit, role separation, or Mission 19A's exact authenticated current-session revocation exception. Security events are direct-only, cannot be edited and cannot be sent through the ordinary outbox dispatcher.

## 4. Provider status, test send, and errors

- `GET /internal/notifications/provider-status` returns `channels:['SMS','PUSH','EMAIL']` and `projectionScope`. A `notification.provider.view` principal receives `FULL` non-secret SMS/email configuration and worker tuning; a delivery-only principal receives `MINIMAL` with just `sms.available`, `push.available`, `email.available`. Do not infer provider identity from the minimal projection.
- `GET /internal/notifications/provider-config` is provider-view scoped and returns `{sms,email,encryption,worker,contracts}`. Per-channel `source` is `DATABASE` or `ENVIRONMENT`; `ENVIRONMENT` is **not** external activation. Choices are SMS `console|robase`, EMAIL `none|console|brevo|resend`; credential sources are `NONE|ENCRYPTED_DB|ENV_SECRET`. `ENV_SECRET` is usable only when an enabled governed row selects it. Resolved environment or decrypted keys that fail provider-format validation yield the safe generic `PROVIDER_FAILURE`, never the credential or validator details. Missing pinned endpoints and malformed sender/reply-to fields fail closed. Non-production console simulation is the only environment-only exception.
- `lifecycleState` is `NOT_CONFIGURED|CONSOLE_ONLY|MISCONFIGURED|CONFIGURED|VERIFIED|ENABLED|DELIVERY_TESTED|PRODUCTION_READY`. `gates` contains booleans `configured`, `verified`, `enabled`, `deliveryTested`, `productionReady`; display them as reported, not as proof of production acceptance or customer receipt. Top-level `enabled` may reflect the stored switch even when effective readiness is false; use the gates and misconfiguration together. Domain SPF/DKIM/DMARC fields are stored assertions, not live DNS verification. An absent governed row cannot enable an external vendor, even if legacy keys exist.
- **Unresolved H-07:** an approved `ENV_SECRET` proposal currently has only a four-character display fingerprint; activation and sends reread mutable environment material, so the UI must not claim the exact secret is cryptographically bound to the checker approval. Arena 2/security must resolve secret rotation and binding before live use.
- Unreadable/corrupt governance produces a sanitized **503**, and dispatch is dark; missing/incomplete configuration on controlled test-send gives **400 `PROVIDER_NOT_CONFIGURED`**, disabled governed channels give **400 `SMS_PROVIDER_DISABLED` / `EMAIL_PROVIDER_DISABLED`**, and declared misconfiguration gives a safe code. UI must not fall back to stale environment values or present unavailable as enabled. A disable cannot recall a request already in flight.
- `POST /internal/notifications/test-send` takes exactly `{channel:'SMS'|'EMAIL',destination:string}`, uses fixed safe content, authorization, a durable five-per-principal rolling-hour quota, and audit. It returns `201 {status:'SENT'|'FAILED',channel,correlationId,destination,provider,providerRef,errorCode}`; destination is masked and provider reference is boundary-sanitized. `SENT` means accepted by the selected adapter, **not** customer receipt. For `provider:'console'`, the `SENT` response is a simulation; provider `lastTest.status` is `CONSOLE_SIMULATED` and must not be presented as live delivery. Quota exhaustion is 429. This mission did not invoke a live test-send.
- Provider proposals (`/internal/notifications/provider-config/proposals`, `/:id/approve`, `/:id/reject`, `/:id/activate`) and channel verification (`/:channel/verify`) retain their existing audited role, MFA and maker-checker controls. Verification/test-send can reach vendors when legitimately configured; never run automatically during UI rendering or this handoff. Do not log API keys, destinations, credential bodies or upstream response text.

## 5. Delivery and receipt diagnostics

`GET /internal/notifications/deliveries` requires `notification.view_deliveries`; supports page/limit (1–100), status, recipientType, channel, eventType and UUID recipientId filters. It returns `{data,total,page,limit,totalPages,hasNextPage}`. Rows expose `{id,eventType,eventKey,aggregateType,aggregateId,recipientType,recipientId,channel,status,attempts,providerRef,correlationId,causationId,errorCode,createdAt,updatedAt,sentAt,failedAt}`. Destination, message, subject/HTML and payload are excluded. Sensitive or malformed identifiers may be `[REDACTED]`/null; do not use redacted values as authority, unique identity, or a reversible lookup. Only stable safe identifiers are expected to survive unchanged.

| Delivery status | Meaning |
|---|---|
| `PENDING` | Materialized and eligible for worker processing, subject to current gates. |
| `SENT` | Adapter/provider accepted or a local console simulated the send; not end-user receipt. |
| `FAILED` | Definite retryable failure or pre-send failure; bounded retry policy applies. |
| `SKIPPED` | Disabled/opted-out/missing dependency or other intentional suppression. |
| `UNKNOWN` | Outcome may have reached the provider; no blind retry. |
| `DEAD` | Permanent failure or attempts exhausted; no automatic retry. |

Admin Web currently lacks `UNKNOWN`/`DEAD` filtering and KPI treatment. Treat these as explicit states, not `FAILED` or success. `GET /internal/notifications/outbox-receipts` returns the same pagination envelope with notification-only `{outboxEventId,status,reason,attempts,nextAttemptAt,createdAt,updatedAt}`. Accepted statuses: `MATERIALIZED|SUPPRESSED|UNSUPPORTED|QUARANTINED|FAILED`. Safe reasons include `EVENT_TYPE_UNSUPPORTED`, `UNSUPPORTED_SCHEMA_VERSION`, `SECURITY_DIRECT_ONLY`, `INTERNAL_SUPPORT_MESSAGE`, `SUPPORT_VISIBILITY_UNKNOWN`, `NO_NOTIFICATION_INTENTS`, `MATERIALIZATION_FAILED`, `MATERIALIZATION_EXHAUSTED`, `LEGACY_PUBLISHED_UNVERIFIED`; an unsafe historical reason projects as `UNCLASSIFIED`. Materialization is not external delivery. Shared `GET /internal/outbox` requires separate `outbox.view`; its diagnostic identifier fields and identifier-shaped payload fields are re-masked at read time, without changing the stored business fact.

## 6. Temporary customer credentials

The existing workforce `POST /internal/admin/customers/:id/credentials` and `.../credentials/reissue` response keeps the legacy `delivery:{channel,delivered,destination,provider}` and adds top-level `deliveryStatus:'NOT_CONFIRMED'|'SIMULATED'|'PROVIDER_ACCEPTED'` plus `deliveryNotice`. `delivered=true` historically meant adapter acceptance, not handset receipt. `NOT_CONFIRMED` includes failure/no verified phone; `SIMULATED` means local/test mode; `PROVIDER_ACCEPTED` is not proof of receipt. A console result carries an internal simulation marker so a stale cached provider name cannot turn it into an acceptance claim. Audit retains the historic action name for compatibility but now also records the truthful `deliveryStatus`. Never expose plaintext temporary passwords or log message bodies. Recovery/reissue must follow its existing authorization and audit flow.
