### Common queue, preference, status and failure semantics

For a mapped ordinary event, the source producer enqueues inside its transaction; the independent notification subscriber checks the known template/schema/security/privacy contract, resolves intents, checks event enablement and contacts/preferences, renders redacted content, and inserts delivery rows idempotently. EMAIL intents are added only for CUSTOMER SMS intents on the explicit funding/transfer/support allowlist when the cached email provider is not `none`; C2C and Agent events are excluded. Email event switches and verified email/preference must also pass. The worker rechecks the switch, destination and preference before sending. Failure to resolve an eligible destination becomes `SKIPPED`; provider errors and pre-send failures use bounded retry; ambiguous started/expired attempts become `UNKNOWN` without blind automatic resend; exhausted attempts become `DEAD`. Receipt `MATERIALIZED` means rows exist, **not** that a message was sent. `SENT` means provider acceptance (or console simulation outside production), not confirmed end-user delivery. Receipt states include `MATERIALIZED`, `SUPPRESSED`, `UNSUPPORTED`, `QUARANTINED`, `FAILED`; most current unknown event types are quarantined with a safe reason. See S1–S3 and the test evidence.

Direct security flows instead use fixed code text and direct SMS-provider calls. Their secret-bearing message is not put into outbox/delivery/template persistence; normal queue retries/status are not available, and provider failure behavior is flow-specific. They must remain secret-safe and non-enumerating.

### Security classification, template and authorization boundary

- The three named SECURITY events are code-owned, locked, direct-only and excluded from ordinary editable templates/outbox dispatch. Transactional/informational events use event-specific allowlisted variables, bounded plain text and header-safe email subjects; arbitrary expressions, nested paths and sensitive literals are rejected. Classification names do not prove that every future security event or alert policy is covered. The [template-engine tests](../../../test/notification-template-engine.spec.ts) passed offline.
- Customer inbox uses the authenticated CUSTOMER principal's own ID. Delivery/receipt diagnostics require `notification.view_deliveries`; provider status has a limited projection for delivery-only viewers and a fuller projection for `notification.provider.view`. Provider proposals require `notification.provider.configure` plus service-level role/MFA/independent-approval controls; verify/test-send requires `notification.test_send`. See [provider controller](../../../src/notification/notification-provider-config.controller.ts) and [test-send authorization](../../../src/admin/admin-notification-provider.controller.ts#L564-L585).
- Registry read is available to an authorized `notification.view_deliveries` workforce principal or an MFA FINANCE_CONTROLLER reviewer. Under the current interim policy, a SUPER_ADMIN with that read function and MFA proposes a frozen change; a separate FINANCE_CONTROLLER with `privileged:approve` and MFA must approve/execute it, with version and audit checks. This does not override H-06's UI/server trigger-lock disagreement. The separate backend/Admin D-10 policy ratification remains open.
- Read-only principals cannot use unsafe methods, except the exact authenticated current-session revocation allowed by the existing runtime guard. Do not use the preview limitation as a reason to permit unrelated POST/DELETE calls. These are source and unit/synthetic observations; Mission 25A did not run real PostgreSQL-backed HTTP/session authorization tests.

Connection verification may call `/v3/account` and `/v3/senders`; stored booleans are assertions, not independent DNS verification. | Mocked unit tests for API contract/verification and F-05 passed. Real provider enablement, separately authorized after remediation, would need documented product/security approval; account and credential provisioning without exposure; valid encryption keyring for managed secrets; verified sender identity/domain and permitted egress; worker deployment/health and event/recipient preference configuration; controlled test destinations and explicit authorization; provider acceptance **and separate end-user receipt** evidence; monitoring, rollback and reconciliation of `UNKNOWN`/`DEAD`. This is a future checklist, **not** authorization to activate a provider now.

Provider readiness snapshots expose configured/verified/tested gates and role-limited data, but a local key-shape/decryption check does not verify the vendor account or actual delivery. Brevo verification can make live calls; Robase/Resend checks described by the code are local contract/credential-shape checks until a separately authorized test-send. A `deliveryTested` field must not be presented as proof of final receipt without corroborating evidence.

## D. Ranked defects and risks

Severity is relative to the audited scope and stated conditions. "No Critical proven" does not mean safe to deploy.

### Critical

**None proven** by this read-only, offline audit. No production data exposure, external sends or financial losses were established.

### High

**H-01 — Governed provider can fail open on configuration read failure.** [`loadDbRow`/`loadAllDbRows`](../../../src/notification/notification-provider-config.service.ts#L2607-L2640) catch database read failures and return the same null/empty result used for an absent row. [`sendSms`/`sendEmail`](../../../src/notification/notification-provider-config.service.ts#L509-L730) then fall back to direct environment providers, and the runtime cache can advertise environment email. With valid direct environment credentials and a disabled governed DB row, the synthetic healthy-row case made zero fake requests; changing only the fake DB read to throw made **two successful fake transport requests**. Managed-environment mode's own fallback fails closed. This is a conditional bypass of a disabled/changed governed row, not proof of a real send or that deployed credentials exist. Distinguish absent configuration from read failure and preserve maker/checker, egress and audit; coordinate with the provider owner/Arena 2. [Probe](./20261031-MISSION-25A-TEST-EVIDENCE.md#synthetic-probes-not-database-or-provider-integration).

**H-02 — Diagnostic identifier redaction does not cover the admin delivery path, and causation is passed through.** [`AdminNotificationController.listDeliveries`](../../../src/admin/admin-notification.controller.ts#L142-L156) directly projects stored `correlation_id` and `causation_id`; the synthetic legacy row returned a fake credential-shaped sentinel unmasked to a fake-authorized caller. Current [`OutboxService.enqueue`](../../../src/operations/outbox.service.ts#L19-L35) sanitizes correlation but leaves causation unchanged; [`mapEventToIntents`](../../../src/notification/notification-event-map.ts#L18-L30) and [dispatcher insertion](../../../src/notification/notification-dispatcher.service.ts#L195-L206) preserve it. The fake enqueue/map probe demonstrated this behavior. Exposure requires unsafe legacy correlation values or a reachable producer supplying unsafe causation, and a principal allowed to read the surface; neither real data nor real HTTP reachability was tested. The [earlier Report 26](../../audit/20261029/sprint1-security-acceptance/27-REPORT26-NOTFOUND-AND-BUSINESS-CORRELATION-REMEDIATION-2e364cd-20261029.md) covers `NotificationDispatcherService.listDeliveriesForEventKey`, but its blanket claim that every delivery listing is masked does not cover this separate admin projection. Coordinate shared outbox/diagnostics owners; preserve idempotency equality and authorization.

**H-03 — Public support updates are quarantined.** The [producer](../../../src/support/support.service.ts#L860-L868) emits only public messages but omits `isInternal`; the [subscriber](../../../src/notification/notification-dispatcher.service.ts#L149-L153) requires an explicit false marker and correctly quarantines unknown visibility. The producer-shaped fake event produced `SUPPORT_VISIBILITY_UNKNOWN`, zero delivery rows. Correct the contract, not the privacy gate; test public, internal, missing and malformed markers, including existing quarantined events under an approved recovery plan.

**H-04 — Financial-event coverage is materially incomplete.** Deposit and withdrawal services contain producer code for `deposit.completed/failed` and `withdrawal.completed/failed`, but these facts are absent from defaults and notification mapping; synthetic mappings returned no intents. Agent cash-in/out and C2C claimed/expired producers were not found for their intended notification paths. Required audiences/channels and financial disclosure are not yet policy-approved in all cases. Resolve contract/ownership and D8 before implementation; never alter ledger or financial settlement to make a notification test pass.

**H-05 — Temporary credential response overstates delivery.** [`issuanceView`](../../../src/admin/admin-customer-credentials.controller.ts) returns a notice saying the temporary credential was delivered even when the supplied delivery result says `delivered=false`; the synthetic method probe reproduced this. Even a provider success only establishes acceptance. This can mislead an operator and customer about access recovery. Preserve non-enumeration, no plaintext response/persistence, expiry/rotation and direct secret delivery.

**H-06 — Required-trigger lock is stricter in Admin Web than the backend registry.** The [UI catalogue](../../../apps/admin-web/src/services/notification-domain.ts#L1084-L1111) labels `customer.funding.approved/rejected` required and locked, and the [API mapping](../../../apps/admin-web/src/services/notification-management-api.ts#L358-L367) unions those static locks with registry locks. The [frozen seed](../../../src/notification/notification-defaults-v1.ts#L145-L179) sets ordinary configurations `is_locked=false`; [registry change/execution](../../../src/notification/notification-registry.service.ts#L299-L313) checks that field and still requires maker/checker. A fake-authorized, fake-DB `requestChange` accepted a proposal to disable funding-approved SMS; it remained `REQUESTED` and was **not** executed. The existing [unrun PostgreSQL registry test](../../../test/notification-registry.integration.spec.ts#L420-L441) explicitly expects a governed disable of `customer.funding.approved` to execute. This is not an unauthorized bypass or a SECURITY lock bypass; it is a product-policy/API/UI contradiction. Obtain an authoritative policy decision and enforce the same contract on the server without weakening roles or conflating mandatory alerts with marketing consent.

### Medium

**M-01 — Support status and reference fields do not line up.** The producer's `{ticketId, from, to}` [shape](../../../src/support/support.service.ts#L646-L652) is not the template's `status`/`newStatus` and public-reference input. Synthetic `IN_PROGRESS` rendered `Your support ticket your request status changed to updated.` Some resolution/closure cases choose their specialized template, but reference can still be generic. Align safe, allowlisted contract fields; do not include support message bodies/internal notes.

**M-02 — In-app inbox is dependent on other channels and not preference-aware.** [`listForCustomer`](../../../src/notification/notification-inbox.service.ts#L60-L127) reads each non-`SKIPPED` CUSTOMER delivery independently without `notification_in_app_enabled` or event-level deduplication, and projects `AVAILABLE` regardless of `PENDING`, `FAILED`, `UNKNOWN` or `DEAD`. Two fake channel rows yielded two items. With all rows skipped, none appears. Whether mandatory items should be visible despite an in-app opt-out is a **policy decision**, not a conclusion to hide them; the current preference/API semantics are nevertheless inconsistent and the projection is not independent in-app delivery.

**M-03 — Agent and push capability is advertised more broadly than it can deliver.** AGENT lifecycle/support/C2C mappings lack a usable Agent phone resolver; PUSH lacks tokens/provider and ordinary intents. Resolver returns explicit dependency reasons. Treat these as unavailable, not as successful implementation; implement only against approved Agent contact and device lifecycle/privacy policy.

**M-04 — Existing preview is safe but its access and samples are not fully aligned.** `POST /internal/notifications/templates/preview` uses code-owned synthetic samples and does not send, but the read-only runtime guard blocks unsafe POST methods; a direct guard-method probe denied POST and allowed GET. Thus a read-only auditor may have list access but not preview, absent a separately approved safe design. The Admin Web's locally assembled sample/`resolvedVariables` can disagree with backend fixed sample output. Do not broadly exempt read-only POST or change the Mission 19A logout exception. [Controller](../../../src/notification/notification-registry.controller.ts), [guard](../../../src/authorization/runtime-access.guard.ts), [UI workspace](../../../apps/admin-web/src/components/NotificationTemplateWorkspace.tsx).

**M-05 — Admin UI omits terminal delivery states from useful filters/counters.** Backend accepts `UNKNOWN` and `DEAD` filters, while the [Admin Web delivery filter and page counters](../../../apps/admin-web/src/screens/authenticated/NotificationManagementScreen.tsx#L359-L382) only enumerate `SENT`, `FAILED`, `PENDING`, `SKIPPED`; terminal rows can still appear when viewing all statuses. This hinders reconciliation, particularly because ambiguous sends must not be blindly retried. UI tests passed using mocks, not the terminal-state cases. [Filter](../../../apps/admin-web/src/screens/authenticated/NotificationManagementScreen.tsx#L2020-L2037), [backend states](../../../src/admin/admin-notification.controller.ts#L23-L24).

**M-06 — Security alerts and stored preferences are disconnected.** Login/device/transaction alert flags are stored, but no customer notification wiring was found for the corresponding authentication/PIN/device lifecycle. Existing three locked direct flows are not evidence that all mandatory security notifications exist. Decide event, audience, exception, rate, anti-enumeration and channel policy first.

**M-07 — Provider outcome and delivery observability are incomplete.** No provider receipt/webhook or bounce/complaint integration was found in the traced SMS/email adapters. Provider acceptance is not handset/mailbox receipt. Retry, `UNKNOWN`, `DEAD`, opt-outs, disabled worker/email and direct-security send failures need explicit operating procedures and alerts; do not add blind retries or infer actual delivery.

### Low / documentation and follow-up risk

**L-01 — Historical contracts and branch artifacts can be stale.** Earlier notification documents differ from the current transfer/C2C producer code; `transfer.completed` identities and `cash_to_cash.created` are now wired. The Ordinary Agent D8 register's description predates that created event; the current message does not establish that the six-digit locator is delivered or that SMS is a release gate. Do not replace the pin's source with old audit statements. D8/D9 remain open despite older documents suggesting an answer.

## G. Final completeness statement

**The notification backend is not complete and is not proven production-ready.** It has sound building blocks—provider abstractions, fixed direct-security sends, independently checkpointed outbox materialization, allowlisted templates, encrypted provider proposals, fenced attempts and fail-closed handling of ambiguous sends—but the event matrix, SMS/email channel enablement, provider governance, diagnostics redaction, support integration, in-app semantics, Agent/PUSH dependencies, security-alert coverage and administrative workflow do not meet end-to-end completeness.

What remains is not merely "turn on a provider": resolve the listed security/contract defects and product-policy decisions; implement only approved event coverage while preserving financial and security controls; validate isolated PostgreSQL integration/upgrade behavior; and obtain separately authorized sandbox/real-provider **and recipient-receipt** evidence. The 177 passing tests and synthetic probes establish the narrow offline behavior recorded here, not real delivery, actual database state, live configuration, deployment safety, or compliance approval.
