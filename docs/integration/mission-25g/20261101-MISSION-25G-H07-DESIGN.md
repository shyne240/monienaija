# Mission 25G — H-07 exact-secret binding and rotation design

**Status: recommendation only; not implemented or approved.** External provider use with `ENV_SECRET` remains a production blocker. This proposal does not authorize activation, real credentials, outbound sends, or a deployment. Security/product, the provider-governance owner, Arena 1 and Arena 2 must review the design and the overlapping provider-security surfaces before a separate implementation is authorized.

## Observed gap at the 25E baseline

Mission 25F found that a maker/checker approval does not bind the exact `ENV_SECRET` credential. In `notification-provider-config.service.ts`, `USE_ENV_SECRET` proposal creation resolves the value, validates its format, derives `computeKeyFingerprint()`, and includes that display fingerprint in `actionFingerprint`. `computeKeyFingerprint()` in `notification-secret-encryption.service.ts` retains only four sanitized trailing characters. At activation the service re-reads the secret and computes a new display fingerprint but consumes the stored proposal fingerprint without comparing the approved secret. `resolveRowSecret()` later re-reads and format-validates the environment value without comparing it with the approved value. A changed valid-shaped secret, including one sharing the same final four characters, can therefore be activated or used without an approval of those exact bytes. Current `coreIdentityUnchanged` readiness logic also compares the display fingerprint, so a same-tail rotation can appear unchanged. This is a conditional integrity/approval bypass, not evidence of disclosure or actual external delivery.

The current schema in migration `1785753600100-CreateNotificationProviderConfiguration.ts` deliberately constrains the existing fingerprint to `****xxxx`; it is a **display hint**, not a cryptographic commitment. Do not redefine it or alter migration 100. Proposal history, maker/checker separation, existing encrypted-envelope behavior, pinned provider origins and fail-closed external routing must remain intact.

## Proposed binding

1. Prefer a secret-manager reference to a **provably immutable, version-specific** secret, controlled by an independent security boundary. If that guarantee cannot be established for every deployment, use a versioned keyed HMAC over the exact effective credential as well. An environment-variable name or mutable `latest` alias is not an immutable version.
2. Define a canonical, length-delimited encoding and domain-separated `HMAC-SHA-256`: e.g. `HMAC(K_binding_vN, encode("monienaija.notification.env-secret.binding.v1", channel, provider, effective_secret_bytes))`. The effective bytes must be exactly those returned by the same provider validation/canonicalization that the adapter will use; the current validator trims surrounding whitespace and rejects internal whitespace. Version this normalization rule. Include the algorithm/normalization version and HMAC key identifier; bind channel and provider so one provider's commitment cannot be copied to another. Use an independent, access-controlled KMS/HSM-backed or separately provisioned HMAC key, never an unkeyed hash, the provider credential, or a publicly exposed display tail as the binding key.
3. At proposal time, resolve and validate one secret snapshot, compute its binding and store only the binding metadata and existing display hint. Include the binding version, key ID, MAC and immutable secret-version reference (if used), together with the existing proposal ID, expected configuration version and governed settings, in the action fingerprint reviewed by an independent checker. Do not expose the secret or full MAC in logs, API bodies, error text or ordinary audit projections; display only the existing masked hint and non-sensitive version information as separately approved. Maintain maker/checker and MFA requirements.
4. At activation, lock the proposal and active channel row, verify expected configuration version, resolve and validate one current secret snapshot, recompute the proposal binding using its recorded key version, and compare fixed-length MACs in constant time. Consume the exact approved action fingerprint only as part of the same successful transaction. Missing/invalid keys, secret, version, malformed binding or mismatch must fail closed, roll back and leave approval unconsumed. `KEEP_EXISTING` for an `ENV_SECRET` must prove that the existing bound credential is still the exact one being retained; it must not turn provider switches, an unbound legacy row or a changed secret into an implicit approval.
5. Persist the approved binding on the active row. On **every** real send, connection verification and test-send, resolve the actual credential snapshot once, validate and compare its binding in constant time, and pass that same snapshot directly to the adapter; do not check one read and send a later read. Never fall back to another environment credential, previous provider, console, or stale cached key after a mismatch. Readiness/status must show a safe failure and no secret; caches must be keyed/invalidate on the binding and config generation. Cover all SMS and email provider paths.
6. Compare the full binding, not the four-character display tail, when deciding whether verification and delivery-test readiness survive a configuration update. A new binding, provider, endpoint or sender identity must clear readiness and require the existing authorized re-verification/test process. Use an explicit stable failure code without leaking credential material or a comparison oracle.

This protects against a mutable credential changing behind an approval, not a fully compromised process able to bypass checks and access the HMAC key. Bindings are sensitive governance metadata even though they do not contain plaintext secrets; restrict their DB/API exposure and separate key-management duties.

## Rotation and mixed-version rollout

- Provider-secret rotation is a **new** maker proposal for the new immutable version or binding, independently checker-approved and activated with optimistic version checking. Verification/test readiness resets. A secret changed in the environment before activation must not be used; workers should fail closed until the approved bound version is available. Coordinate rollout across every application instance and worker.
- Rotate HMAC binding keys separately under a documented, audited key-governance process. Retain explicitly permitted old verification keys while active bindings reference them; a controlled, independently approved rebind or new proposal must establish the new key ID. Never silently recompute a legacy approval or retire a key while live rows depend on it. Missing/unknown/retired keys fail closed.
- A future **additive** migration should introduce nullable, versioned proposal and active binding fields and appropriate consistency constraints without altering migration 100 or rewriting historic records. New-code runtime must treat null/unrecognized bindings for `ENV_SECRET` as unbound and unusable. Existing unbound active configurations must not be silently backfilled from the current environment; disable/fail closed and require a fresh governed proposal and checker approval. Existing unbound pending/approved proposals must be canceled/expired or rejected at activation and reproposed. The exact operations procedure and owner approval are separate release gates.
- For mixed versions, deploy schema compatibility first, then ensure **every** node that can verify, test or send enforces the new checks before any bound `ENV_SECRET` is enabled. Fence or drain old workers, jobs and rollback images that ignore binding fields. Do not allow a rollback to an old binary to resume external delivery; enforce a deployment/egress gate until a compatible version is restored. Test the actual staged rollout and rollback with no real provider calls.

## Required future tests

Use synthetic values, fake transports and disposable PostgreSQL; prohibit network egress. Include:

- same secret succeeds at proposal/approval/activation/runtime; changed secret between proposal and activation and after activation fails, including a different secret with the **same final four characters**; mismatch produces **zero** outbound requests;
- missing, empty, invalid-shaped, unknown-key-version, malformed/tampered binding, wrong channel/provider and immutable-version substitution all fail closed without fallback, secret or MAC disclosure;
- the credential verified is the exact in-memory snapshot passed to the adapter, including a simulated concurrent environment/secret-manager change; cover delivery, verify, test-send, status/readiness, and every SMS/email provider;
- `KEEP_EXISTING`, stale expected version, replay, unauthorized maker, self-approval, checker independence, transaction rollback and approval non-consumption on mismatch; successful independently approved rotation resets readiness;
- mixed old/new workers, restart, cache invalidation, concurrent sends/rotation, HMAC-key rotation, missing old verifier key and downgrade fencing;
- clean-install and upgrade migrations, legacy active/pending rows, no auto-binding, failure cleanup, unchanged migration 100 and preservation of encrypted-DB credentials, historical audits and unrelated provider controls.

## Decisions still required

Security must choose the immutable-secret service or binding-key custody and canonical encoding, reviewer-visible identity, failure codes, migration/rollback sequencing, rotation/incident runbook and which operators may view governance metadata. Product/security must approve the readiness and outage behavior. No code in Mission 25G implements or asserts acceptance of this design.
