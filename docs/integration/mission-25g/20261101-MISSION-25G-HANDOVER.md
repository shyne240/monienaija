## Root cause and independent reproduction

At the 25E pin, all four `CustomerPreferenceController` handlers delegated to the service without an action-level identity or function check. The generic `/customers/:id/*` policy allowed `CUSTOMER`, `OPERATOR`, `SERVICE` and `PRIVILEGED` and declared no required function. For non-CUSTOMER principals, `AuthorizationService` deliberately treats `customerAccess: SELF` as nonrestrictive after the principal-type gate; it does not turn a workforce session into an owner. The existing read-only guard denied unsafe methods for read-only roles, but did not make reads safe or protect writes from non-read-only roles. `customer.view` is a profile/KYC-tier permission, not approval to see security-alert or biometric preferences. The DTO's required body `actor` flowed unmodified into preference history and business audit.

Two new real-guard/disposable-PostgreSQL tests were run against the unchanged 25E code before the fix: a genuine persisted CUSTOMER_SERVICE session received **200** where a preference GET should deny, and a customer's spoofed create actor was returned as the stored history actor rather than the session identity. Both expected-denial/attribution tests failed as intended. The first reproduces 25F's direct API observation; source inspection also establishes why the generic policy could reach roles without `customer.view`.

A further 25G investigation found a separate indirect disclosure: generic `GET /internal/audit` and the audit dashboard widget projected `CUSTOMER_PREFERENCE` and `PREFERENCE_HISTORY` audit rows containing old/new notification and security values. A real SUPPORT session returned these records via the audit endpoint before the projection fix; a real SUPER_ADMIN session did as well. This is additional 25G evidence, not attributed to the 25F assessment. Generic `audit.view` and the SUPPORT audit exception do not establish an approved customer-preference/history policy.

## Before and after

| Surface | Before | After |
| --- | --- | --- |
| `GET` / `HEAD` preferences, `GET` / `HEAD` history | Generic customer policy admitted allowed workforce principal types without a preference function; route-bound customers were scoped to self. | A validated CUSTOMER may address only its own bound route ID. All workforce roles and AGENT/SUPPORT are denied; no preference payload or target existence is disclosed. |
| `POST` and `PATCH` | Non-read-only workforce in allowed types could reach arbitrary customers; body chose the actor. | Only the same validated CUSTOMER self may create/update. Read-only unsafe-method protection remains unchanged; workforce, cross-customer and anonymous writes fail. |
| `actor` | Required caller-supplied value persisted in history and audit. | Optional legacy field is accepted for compatibility but ignored; the validated session's consistent `principalId`/`customerId` is used. Historical rows are not rewritten. |
| Alternate paths | Generic `/me` catch-all and raw encoded path handling could be broader than the intended preference rule. | All methods and descendants use the preference rule, including percent-encoded static segments; missing/empty/mismatched Fastify route parameters deny everyone. `/customers/me/preferences` remains unsupported and denies. |
| Generic audit projections | Preference business/history rows and preference-route decision metadata could be returned through generic audit reads and widgets. | Preference records and current/legacy preference-route decisions are excluded from generic audit projections and filtered queries for all roles, including provider-oversight readers. Underlying records remain intact. A trusted in-process health opt-in preserves the existing limit-one event-presence indicator; HTTP query parameters cannot select it. Unrelated audit rows remain visible under their existing gates. |

The controller independently requires a CUSTOMER principal with a session, `customerAccess: SELF`, matching route `id`, and `principalId === customerId` for reads, history and writes; this protects the handlers if the registry is misconfigured. The underlying service remains a trusted in-process boundary: any future write caller must independently establish approved authorization and actor attribution rather than forwarding a body-supplied actor. For a valid own ID, existing service behavior such as 404 for no preference, optimistic version handling and notification settings is retained. Unauthenticated calls return 401; authenticated non-owner/wrong-type calls return 403. Cross-customer requests receive the same denial for existing and nonexistent IDs. The normal authorization-decision audit remains in the database; read-only unsafe requests retain the guard's pre-existing behavior.

**Audit oversight trade-off:** generic workforce audit views temporarily do not show preference records or their route decisions. Existing business/history audit records and their actors/values remain in PostgreSQL. The separate operational audit summary still reports aggregate counts by action/entity type, not per-customer preference values; the health dashboard retains its prior 0/1 audit-event presence indicator. Security/product must decide any separately authorized and audited preference-history/oversight access; the health-only in-process exception is not a workforce preference grant.

### Isolation and limitations

Tests used an isolated local PostgreSQL 18.4 instance, UTF-8, bound to loopback only, unique test-run/database namespaces, test-only synthetic credentials and local process environment. No `.env` file was written. Dependencies were installed from the existing lockfile with lifecycle scripts disabled; only the embedded PostgreSQL package's local symlinks were hydrated in ignored `node_modules`. The Node test processes loaded `test/support/mission-25c-network-guard.cjs`, which blocks non-loopback socket/DNS/fetch egress, and notification sends used in-memory/fake adapters. This is not evidence of vendor connectivity or real delivery. No real provider credential, production database, SMS/email delivery, deployment or provider activation was used.
