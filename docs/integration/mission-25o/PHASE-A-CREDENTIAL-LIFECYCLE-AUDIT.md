## Findings and reviewed evidence

- Reviewed the complete archived Mission 25F assessment, the recommendation-only Mission 25G H-07 design, the Mission 25H integration findings and the later 25K integration report. 25H verified customer-only preferences and carried H-07 as an unresolved blocker; 25K aligned the frontend without changing notification backend code.
- The full Mission 25N report could not be found in available Git refs/history, integration/evidence branches, attachments, matching GitHub issues/PRs or the connected Drive. **It was not reviewed.** Per the mission owner, 25N's authoritative conclusion is `PASS — ASSESSED SECURITY AND INTEGRATION SCOPE TECHNICALLY ACCEPTED` for candidate `587c376…`; customer-preference security and frontend corrections were resolved, while H-07 remained high severity and external-provider activation prohibited. This is the supplied conclusion, not a claim to have reviewed the missing report.
- `ENV_SECRET` proposal creation validated the configured value but committed only a masked four-character display hint. Approval did not compare the actual value, activation reread the environment without matching the approved credential, and runtime reread it without matching the active configuration. A different valid credential, including one with the same suffix, could be substituted without fresh approval.
- `KEEP_EXISTING` copied the current credential source and display hint without a binding; a provider change could also redirect an environment-source lookup. Readiness reset compared the hint, so same-tail rotation could be mistaken for no change. Stored proposal fingerprints were consumed rather than reconstructed from the proposal's current fields.
- The maker and checker have independent role/capability/MFA requirements and self-approval is rejected. Activation uses a scoped, expiring, consumable approval and locks proposal/configuration rows with optimistic version checks. Those controls did not bind the exact environment credential.
- SMS, Brevo and Resend delivery load an active row, refuse disabled/unconfigured external providers, verify pinned provider origins and resolve the selected source. Brevo verification and status/readiness also resolve the credential. Provider-name caching does not cache secret bytes. Environment variables alone do not authorize an external provider when its governed row is missing. Local console simulation is non-production only.
- Verification and test-send readiness writes were keyed by channel, not the configuration version used for the action. A concurrent activation could associate an old result with a newer configuration. This is a source-level race observation, not evidence of a live incident.
- Provider audit projections, error sanitizers and masked display hints are intended to prevent disclosure; a binding value must not appear in API responses, audit payloads, diagnostics or logs. The durable notification processor already uses claims, attempt/lease fencing and conservative handling of ambiguous provider outcomes; these semantics must remain intact.

## Storage, key custody and revocation decisions

The existing migration 100 `ENCRYPTED_DB` workflow stores AES-256-GCM envelopes in active configuration and historical proposal rows. Those envelopes are reversible by a holder of the separately managed encryption key. The mission owner explicitly approved **preserving this existing encrypted-at-rest workflow**, including new encrypted proposal/configuration rows, as an exception to the no-reversible-database-material requirement; plaintext, additional reversible copies, API exposure and logging remain prohibited. No historical rows are automatically deleted.

The owner selected a **separately provisioned, independently managed, versioned HMAC keyring**. It is not the vendor credential, a public suffix, an unkeyed secret hash, the existing encryption key, or a source-code constant. Missing/revoked verification-key versions and governed provider disable must fail closed. Production key custody, distribution, rotation, retirement and deployment are operational release dependencies; this mission provisions no production keys.

A plain environment value cannot itself reveal that a vendor revoked a credential before an outbound attempt. Authorized operators must propagate credential revocation through the governed provider-disable mechanism and/or remove the relevant binding-key version from every sender; upstream revocation is not independently observable without an authorized external revocation service. Deployments must fence old workers and rollback images that do not enforce the binding before using an external provider.

A defensible design binds the validated effective bytes, channel, provider and source with a domain-separated keyed commitment. New proposal identity and expected version, all governed settings and binding metadata must be included in the independently approved action fingerprint. Approval, activation, verification, test-send and each real dispatch must check the binding; the in-memory credential that was checked must be the one passed to the adapter. Null/unknown legacy bindings cannot authorize external delivery and require a new proposal and independent approval. An additive migration, readiness version fencing, no-fallback error paths, secret-safe diagnostics and synthetic-only tests are necessary. This architecture remains subject to the implementation and test evidence in the handover; the audit alone does not establish remediation.
