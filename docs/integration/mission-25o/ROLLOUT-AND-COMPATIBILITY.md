# Mission 25O — compatibility and operational fencing

**Implementation/integration review is not authorization to provision production keys, deploy, activate any external provider, or send live messages.** All tests for this mission use disposable databases and synthetic credentials/fake provider transports.

## Contract and migration

- Migration `1785753600102-AddNotificationCredentialBinding` adds nullable versioned binding metadata to migration-100 provider rows/proposals and a v2 proposal-fingerprint marker. It does not rewrite migration 100, create provider credentials, backfill an approval, change financial data, or erase audit history. `ProductionReadinessService` now expects migration 102.
- An existing external configuration or old proposal has null binding metadata. Its old status, encrypted envelope, approval and audit evidence remain intact, but it cannot authorize an external send, new checker approval, activation, verification or configured/readiness gate. Operators must submit and independently approve a new proposal. A failed check does not consume the approval. Existing non-production console simulation and disabled/unconfigured provider **delivery** remain non-live.
- Preserved existing behavior: an authorized operator may verify a disabled but still-bound provider; Brevo verification makes read-only account/sender HTTP requests, although disabled delivery and test-send remain blocked. A disabled `CLEAR` configuration has no credential to verify. Therefore a disabled flag alone is not an outbound-network quarantine; use `CLEAR`, stop/drain senders and deny egress where zero vendor traffic is required.
- The provider API retains its existing response shape and four-character `keyFingerprint` **display hint**. The keyed binding, binding key material, full credential and encrypted envelope are not returned to clients. The new safe error `PROVIDER_CREDENTIAL_INTEGRITY_UNAVAILABLE` indicates a missing, invalid, revoked or mismatching identity; it deliberately does not distinguish secret details. Test-send and verification outcomes are fenced to the configuration version actually tested.
- This mission changes no frontend. If a client does not recognize the new diagnostic, it must treat the failure as not configured/not ready, never as permission to fall back. Arena 2's F-01/F-05 frontend changes must be integrated without overwriting each other's provider changes. The external API has no capability for silently upgrading an old approval.
- The approved exception preserves the existing AES-256-GCM encrypted-DB workflow and historical encrypted proposal/configuration rows. It does not authorize plaintext persistence, extra reversible copies, or disclosure. Free-text proposal/approval fields are not a place to paste credentials.

## Binding and rotation

`NOTIFICATION_PROVIDER_BINDING_KEYRING_JSON` is an independently generated, secret JSON map of version names to canonical base64-encoded 32-byte keys; `NOTIFICATION_PROVIDER_BINDING_ACTIVE_KEY_VERSION` selects the version used for new commitments. Do not commit, log, display or reuse these keys. The code rejects literal reuse of any configured AES provider-encryption key, but equality checking cannot prove independent generation or safe custody; security/operations must attest both. A missing/malformed ring, missing active or historical version, or mismatched credential fails closed. No default key is embedded and no production key is created by this mission.

Each MAC is a domain-separated, length-prefixed HMAC-SHA-256 over the exact validated effective credential, channel, provider and selected source. Verification is constant-time for the MAC. The reconstructed v2 action fingerprint includes the proposal ID, expected version, complete governed configuration, source, binding metadata, maker/reason and a digest of any existing encrypted envelope. Maker/checker roles, separate identities, MFA, approval scope, expiry, consumption and optimistic version checks remain enforced. Checker and activation transactions also serialize by channel; runtime passes the same in-memory string that passed verification to the fake/real adapter.

For a vendor credential rotation, stage the new value through the selected existing source and create a new proposal with that exact value, independent checker approval and activation. A changed value cannot be used under the old approval, even when its last four characters match. With `ENV_SECRET`, staging a new value in a process currently serving the old configuration intentionally blocks that process until the new approval/activation; plan for interruption, coordinate all instances, and never route around it. A variable itself carries no immutable upstream version or revocation event: a change-and-revert between observations cannot be detected, and a vendor-side revocation is not known locally before a provider response. Follow the governed rotation/disable procedure for every operational change; do not infer upstream revocation detection.

For binding-key rotation, distribute both old and new verification versions consistently to all makers, checkers, API instances, workers and direct security-message senders. Select the new active version, then create and independently approve a new `USE_ENV_SECRET` or `SET_ENCRYPTED` proposal for each affected external configuration. `KEEP_EXISTING` retains its existing binding version and does **not** rebind it. Only retire the old verification version once every desired active binding and pending proposal has been migrated or intentionally blocked. A retired/missing version blocks all affected uses. Rebinding or changing credential material clears prior verification/delivery-test readiness when identity changes; a new test is not evidence for a different configuration.

## Deployment and rollback gates

1. Obtain separate security, infrastructure, key-custody and product/operations release authorization. Keep all live providers disabled, quarantine outbound vendor egress, pause/drain all notification workers and direct/test-send paths, and verify no old process or rollback image can send. Back up the database and historical audit evidence under existing security controls. These are release dependencies, not actions performed in Mission 25O.
2. Apply migration 102 under the established deployment process. A mixed fleet is **unsafe**: older binaries ignore the nullable binding columns and can continue using an old unbound credential. Do not restore egress or workers until every execution path runs the enforcement code and this is independently verified. An unguarded rollback to an older binary has the same risk.
3. Provision the independent binding keyring securely to every relevant instance. Validate consistent active and historical versions without printing them; restart/reconfigure and verify fleet-wide propagation according to the deployment platform. Missing or inconsistent keys/credentials block affected nodes, not trigger fallback. Monitor safe error codes and queue age. No production value is supplied in the repository.
4. Keep existing records unbound and fail-closed. Any eventual reapproval, provider activation, controlled test, restoration of egress and live delivery requires its own explicit authorization, MFA, independent checker and operational verification. This runbook is not that authorization.
5. For emergency disable or revocation, use governed disabled/`CLEAR` proposals and/or remove the relevant verification key version from **all** instances, then fence network egress and drain or terminate in-flight work. A call that has already passed its pre-send check may complete while a disable or key retirement propagates; neither an environment change nor a DB update can retroactively cancel an in-flight HTTP request. To guarantee zero subsequent vendor traffic, confirm every sender has stopped and egress is denied before declaring the fence complete. Revoking one binding-key version can block multiple configurations and pending approvals; plan the blast radius.
6. `down()` intentionally refuses while provider governance rows exist. Even an empty-table rollback must not restore an older, non-enforcing application while external egress is available. Preserve evidence; use a separately authorized teardown/rollback plan rather than deleting governance history to defeat the guard.

Delivery errors detected before an outbound call use the existing bounded retry/lease/idempotency machinery. They can exhaust retries while an integrity problem persists; alert and remediate through governance rather than replaying blindly. Ambiguous outcomes after a provider call remain subject to the pre-existing conservative fencing; the binding change does not make ambiguous calls safely retryable.
