# Real-browser run — dashboard drill-down → failed-delivery queue → delivery trace → audit search

Generated by `node scripts/arena6-real-browser.cjs --executable /tmp/chromium --lib-path /tmp/al2023/lib --out <dir>`
(kept in the repo as the entry point for the browser leg; see the script's own header for the environment it needs).

This is the **real** evidence class for the drill-down work: a headless Chromium loaded the built
`apps/admin-web` bundle, signed in through the DOM, and talked to a **real** Nest backend
(`arena6-real-browser-backend.ts`, which calls the same `verifyStartup()` gate as `main.ts`) over
**real HTTP** against a **fully migrated disposable PostgreSQL** database. Nothing is stubbed inside the
page: the harness proxies `/api/v1` to the live backend and asserts both what the screen shows and what
the browser actually put on the wire.

## The one check this renderer could not paint

`the audit workspace opened` is recorded as **advisory**, not as a product failure, and there is no audit
screenshot. Reason: this sandbox's single-file Chromium dies at the moment the audit workspace **mounts** —
a clean renderer `disconnected` with empty stderr, and not memory pressure (3.3 GB free at the time). The
request is not the problem: the run log shows the backend answering `GET /api/v1/internal/audit?… <- 200`
before the paint.

The harness does not simply give up on that paint. It retries the whole flow **once on a freshly launched
browser** (new instance, new context, no screenshots taken beforehand, in case the death were cumulative);
the detail recorded is the outcome of that experiment:

> `not painted on either renderer (TimeoutError: locator.waitFor: Timeout 45000ms exceeded. / TimeoutError:
> locator.waitFor: Timeout 45000ms exceeded.); covered by the admin-web jsdom suite and the real-session
> HTTP test`

Two independent renderers dying at the same mount is what makes "this Chromium build cannot mount this
workspace" the accurate finding — and it is why the restricted-role leg still ran: after the audit browser
died, the harness relaunched a third browser and asserted the restricted sign-in on it (see
`requests.restricted` in the report: a sign-in, a dashboard read and one widget read — no protected read).

So the **behavioral** half of the audit leg is asserted mandatorily and does pass, from the captured request
URLs rather than the DOM:

> `the trace jump issues an audit search bound to the delivery's correlation id`

What the renderer cannot show is covered elsewhere rather than dropped: the audit view and its route are
asserted by the `apps/admin-web` jsdom suites, and the same funnel over real HTTP (delivery row → trace →
audit entry carrying the delivery's `correlationId`, plus the `audit.search` permission boundary) is asserted
by `test/arena6-real-session-workflow.integration.spec.ts`. The harness therefore records the environment
limit in the report (`advisoryUnavailable`, `environment`) instead of letting a browser defect look like a
green run or a red one. A run that *truncates* — fewer checks than the legs it contains — still fails: the
ledger is gated on the mandatory legs completing, and `scripts/arena6-real-browser.cjs` exits non-zero on any
non-advisory miss.

## What this run does **not** certify

Listed verbatim in `browser-run.json` under `notCertified`:

- the delivery rows, outbox event and audit trail are synthetic records in a disposable database;
- no real provider was contacted, so a provider receipt can only be `NONE_RECORDED` here;
- the backend was started the way the integration suites start it; the production readiness gate still
  refuses `dist/main.js` (`readinessRefuses: true` is asserted, not bypassed);
- the browser is a headless Linux Chromium — not Safari, not a screen reader, not a handset.
