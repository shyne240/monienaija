# P1.4 Customer Wallet Provisioning

## Scope

P1.4 adds an internal customer-wallet provisioning registry for customers whose P1.2 onboarding is `COMPLETED` and whose P1.3 eligibility is `ELIGIBLE`.

This milestone does not create an existing financial `WalletAccount`, create a ledger account, post journals, move money, change balances, create transactions, invoke reconciliation, process payments, or call external services.

## Domain entities

| Entity                      | Purpose                                                                                        |
| --------------------------- | ---------------------------------------------------------------------------------------------- |
| `CustomerWallet`            | Customer wallet provisioning record, type, currency, lifecycle status, and optimistic version. |
| `WalletProvisioningHistory` | Append-only provisioning and lifecycle history.                                                |
| `WalletAlias`               | Globally unique normalized wallet alias.                                                       |
| `WalletOwnership`           | Immutable customer-to-wallet ownership record.                                                 |

All entities use UUID identifiers and PostgreSQL persistence. Wallets, aliases, ownership records, and history records expose soft-deletion fields. Wallets, aliases, and ownership records have optimistic version columns. History is append-only and has no update API.

## Wallet types and statuses

### Wallet types

- `PRIMARY`
- `SAVINGS`
- `BUSINESS`
- `ESCROW`

Only one non-deleted `PRIMARY` wallet is allowed per customer. Other wallet types are represented by their normalized type and product context; P1.4 does not provision financial accounts for them.

### Wallet statuses

- `PENDING`
- `ACTIVE`
- `SUSPENDED`
- `CLOSED`

The lifecycle transitions are:

| Current     | Allowed next statuses           |
| ----------- | ------------------------------- |
| `PENDING`   | `ACTIVE`, `SUSPENDED`, `CLOSED` |
| `ACTIVE`    | `SUSPENDED`, `CLOSED`           |
| `SUSPENDED` | `ACTIVE`, `CLOSED`              |
| `CLOSED`    | None                            |

A suspended wallet remains suspended until an explicit `PATCH` changes it to `ACTIVE`. A closed wallet cannot become active again.

## Provisioning rules

A customer wallet may be provisioned only when:

1. The customer exists.
2. A non-deleted P1.2 onboarding record is `COMPLETED`.
3. A non-deleted P1.3 eligibility record is `ELIGIBLE`.

The same checks apply when a wallet is explicitly moved to `ACTIVE`. Wallet provisioning does not inspect or mutate the existing financial wallet module.

## Ownership and aliases

Wallet ownership is created in the same transaction as the customer-wallet record. It contains the wallet UUID and customer UUID and has no update endpoint. Ownership is never transferred by P1.4.

Aliases are normalized to lowercase safe identifiers and are globally unique across all customer wallets while not soft-deleted. Alias creation is audited and adds an append-only wallet history entry.

## Provisioning history

The following history actions are stored:

- `PROVISIONED`
- `OWNERSHIP_CREATED`
- `STATUS_CHANGED`
- `ALIAS_ADDED`

History records retain the previous and new status where applicable, the actor, and JSON metadata. History is appended in the same transaction as the associated wallet, ownership, alias, or lifecycle mutation.

## Audit behavior

The existing immutable `AuditService` records every P1.4 mutation in the same transaction as the domain write. Entity types are:

- `CUSTOMER_WALLET`
- `WALLET_OWNERSHIP`
- `WALLET_PROVISIONING_HISTORY`
- `WALLET_ALIAS`

No audit or history record is created by read-only endpoints.

## DTO payloads

The global validation pipe transforms DTOs, rejects unknown properties, validates enums, and validates UUID route parameters in the service.

### Create wallet

```json
{
  "type": "PRIMARY",
  "currency": "NGN",
  "actor": "wallet-ops"
}
```

The status defaults to `PENDING`. An explicit status can be supplied when it is a valid wallet status.

### Update wallet

```json
{
  "status": "ACTIVE",
  "actor": "wallet-ops"
}
```

An optional optimistic-lock version may be supplied:

```json
{
  "status": "SUSPENDED",
  "version": 2,
  "actor": "wallet-ops"
}
```

### Create alias

```json
{
  "alias": "main-wallet",
  "actor": "wallet-ops"
}
```

## APIs

All routes use the global `/api/v1` prefix.

| Method  | Route                                        | Purpose                                     |
| ------- | -------------------------------------------- | ------------------------------------------- |
| `POST`  | `/customers/:id/wallets`                     | Provision a customer wallet.                |
| `GET`   | `/customers/:id/wallets`                     | List customer-wallet records.               |
| `GET`   | `/customers/:id/wallets/:walletId`           | Read one customer-wallet record.            |
| `PATCH` | `/customers/:id/wallets/:walletId`           | Apply a validated wallet status transition. |
| `POST`  | `/customers/:id/wallets/:walletId/alias`     | Add a globally unique wallet alias.         |
| `GET`   | `/customers/:id/wallets/:walletId/history`   | Read append-only provisioning history.      |
| `GET`   | `/customers/:id/wallets/:walletId/ownership` | Read immutable wallet ownership.            |

These routes are distinct from the existing financial `/wallets` module. P1.4 does not call or modify that module.

## Database migration

Migration `1785753600011-CreateCustomerWalletProvisioning.ts` creates:

- `customer_wallets`
- `wallet_provisioning_histories`
- `wallet_aliases`
- `wallet_ownerships`

It adds foreign keys to customer and P1.4 wallet records, enum constraints, soft-deletion-aware unique indexes, query indexes, and version columns. Earlier migrations are unchanged. Production startup compatibility expects migration head `1785753600011 / CreateCustomerWalletProvisioning1785753600011`.

## PowerShell manual verification

### Setup

Run from the repository root:

```powershell
$ErrorActionPreference = 'Stop'
$BaseUrl = 'http://localhost:3000/api/v1'
$Headers = @{ 'Content-Type' = 'application/json' }

npm ci
npm run migration:run
npm run start:dev
```

Use a second PowerShell window for API requests. Complete the P1.2 onboarding and P1.3 eligibility verification first, or set `$CustomerId` to an existing customer that has completed onboarding and `ELIGIBLE` eligibility.

### 1. Verify provisioning prerequisites

```powershell
$CustomerId = '<eligible-completed-customer-uuid>'

$Onboarding = Invoke-RestMethod `
  -Method Get `
  -Uri "$BaseUrl/customers/$CustomerId/onboarding"

$Eligibility = Invoke-RestMethod `
  -Method Get `
  -Uri "$BaseUrl/customers/$CustomerId/eligibility"

$Onboarding | ConvertTo-Json -Depth 8
$Eligibility | ConvertTo-Json -Depth 8

if ($Onboarding.status -ne 'COMPLETED') {
  throw 'Customer onboarding must be COMPLETED'
}
if ($Eligibility.status -ne 'ELIGIBLE') {
  throw 'Customer eligibility must be ELIGIBLE'
}
```

Record the ledger journal count before provisioning when PostgreSQL is running in the repository Docker Compose service:

```powershell
$LedgerBefore = docker compose exec postgres psql -U monienaija -d monienaija -tAc "SELECT COUNT(*) FROM ledger_journals;"
$LedgerBefore
```

### 2. Provision a primary wallet

```powershell
$WalletBody = @{
  type = 'PRIMARY'
  currency = 'NGN'
  actor = 'wallet-ops'
} | ConvertTo-Json

$Wallet = Invoke-RestMethod `
  -Method Post `
  -Uri "$BaseUrl/customers/$CustomerId/wallets" `
  -Headers $Headers `
  -Body $WalletBody

$Wallet | ConvertTo-Json -Depth 8
$WalletId = $Wallet.id
```

Expected result:

- A UUID wallet ID is returned.
- `type` is `PRIMARY`.
- `currency` is `NGN`.
- `status` is `PENDING`.
- No ledger account ID or balance is returned.

A second primary-wallet request must return `409`:

```powershell
try {
  Invoke-RestMethod `
    -Method Post `
    -Uri "$BaseUrl/customers/$CustomerId/wallets" `
    -Headers $Headers `
    -Body $WalletBody
  throw 'Duplicate PRIMARY wallet unexpectedly succeeded'
} catch {
  $_.Exception.Response.StatusCode.value__
}
```

### 3. Read wallet and create an alias

```powershell
Invoke-RestMethod `
  -Method Get `
  -Uri "$BaseUrl/customers/$CustomerId/wallets" | ConvertTo-Json -Depth 8

Invoke-RestMethod `
  -Method Get `
  -Uri "$BaseUrl/customers/$CustomerId/wallets/$WalletId" | ConvertTo-Json -Depth 8
```

```powershell
$AliasBody = @{
  alias = 'main-wallet'
  actor = 'wallet-ops'
} | ConvertTo-Json

$Alias = Invoke-RestMethod `
  -Method Post `
  -Uri "$BaseUrl/customers/$CustomerId/wallets/$WalletId/alias" `
  -Headers $Headers `
  -Body $AliasBody

$Alias | ConvertTo-Json -Depth 8
```

Attempting the same alias again must return `409`:

```powershell
try {
  Invoke-RestMethod `
    -Method Post `
    -Uri "$BaseUrl/customers/$CustomerId/wallets/$WalletId/alias" `
    -Headers $Headers `
    -Body (@{
      alias = 'MAIN-WALLET'
      actor = 'wallet-ops'
    } | ConvertTo-Json)
  throw 'Duplicate alias unexpectedly succeeded'
} catch {
  $_.Exception.Response.StatusCode.value__
}
```

### 6. Verify provisioning history and immutable ownership

```powershell
$History = Invoke-RestMethod `
  -Method Get `
  -Uri "$BaseUrl/customers/$CustomerId/wallets/$WalletId/history"

$Ownership = Invoke-RestMethod `
  -Method Get `
  -Uri "$BaseUrl/customers/$CustomerId/wallets/$WalletId/ownership"

$History | ConvertTo-Json -Depth 8
$Ownership | ConvertTo-Json -Depth 8
```

History must include `PROVISIONED`, `OWNERSHIP_CREATED`, `ALIAS_ADDED`, and the wallet status changes. Ownership must retain the original `$CustomerId` and `$WalletId`.

### 7. Verify missing-prerequisite validation

Use a customer that is not eligible or whose onboarding is not completed:

```powershell
$BlockedCustomerId = '<non-eligible-customer-uuid>'

try {
  Invoke-RestMethod `
    -Method Post `
    -Uri "$BaseUrl/customers/$BlockedCustomerId/wallets" `
    -Headers $Headers `
    -Body $WalletBody
  throw 'Wallet provisioning unexpectedly succeeded'
} catch {
  $_.Exception.Response.StatusCode.value__
}
```

The request must return `409`.

### 8. Verify no ledger or balance mutation

```powershell
$LedgerAfter = docker compose exec postgres psql -U monienaija -d monienaija -tAc "SELECT COUNT(*) FROM ledger_journals;"
$LedgerAfter

if ($LedgerBefore.Trim() -ne $LedgerAfter.Trim()) {
  throw 'Wallet provisioning changed the ledger journal count'
}
```

P1.4 must not create rows in `ledger_accounts`, `ledger_journals`, or `ledger_lines`, and must not change balances.

### 9. Verify audit events

```powershell
Invoke-RestMethod `
  -Method Get `
  -Uri "$BaseUrl/internal/audit?entityType=CUSTOMER_WALLET&entityId=$WalletId&limit=100" | ConvertTo-Json -Depth 8

Invoke-RestMethod `
  -Method Get `
  -Uri "$BaseUrl/internal/audit?entityType=WALLET_ALIAS&entityId=$($Alias.id)&limit=100" | ConvertTo-Json -Depth 8
```

Creation, status updates, alias creation, ownership creation, and provisioning-history creation must have immutable audit events.

### 10. Verify DTO and UUID validation

```powershell
$InvalidWalletBody = @{
  type = 'NOT_A_WALLET_TYPE'
  currency = 'NGN'
  actor = 'wallet-ops'
} | ConvertTo-Json

try {
  Invoke-RestMethod `
    -Method Post `
    -Uri "$BaseUrl/customers/$CustomerId/wallets" `
    -Headers $Headers `
    -Body $InvalidWalletBody
  throw 'Unexpected wallet DTO validation success'
} catch {
  $_.Exception.Response.StatusCode.value__
}

try {
  Invoke-RestMethod `
    -Method Get `
    -Uri "$BaseUrl/customers/not-a-uuid/wallets"
  throw 'Unexpected customer UUID validation success'
} catch {
  $_.Exception.Response.StatusCode.value__
}
```

Both requests must return validation errors.
