## 1. Purpose and boundary

A4T01 records the current repository baseline that A4 must use when defining a central capability/policy decision boundary. It inventories source ownership, current decision-like views, capability-shaped inputs, evidence freshness, privacy boundaries, and A2/A3 handoff inputs.

This task does **not** define the final A4 policy vocabulary, precedence, policy version schema, evaluator, decision persistence, route, or consumer API. Those are later A4 tasks. This document must not be read as an authorization decision or as evidence that A4 runtime behavior exists.

A4 must produce an action-specific policy result while preserving these authorities:

```text
Customer.id                         -> customer identity authority
CustomerOnboarding                  -> onboarding workflow/evidence authority
CustomerEligibility                 -> eligibility/restriction/limit/enrollment/permission authority
CustomerRiskProfile                 -> manual risk evidence authority
CustomerComplianceCase              -> compliance case/evidence authority
CustomerFinancialAccountBinding     -> A3 customer/account association authority
WalletAccount / LedgerAccount       -> financial wallet/account authority
Ledger journals/lines/balances       -> posted financial value authority
A2 principal/authorization          -> runtime access authority
Operations                          -> audit/idempotency/outbox/diagnostics authority
Reconciliation                      -> independent read-only control authority
A4 policy decision                  -> action-specific derived decision authority
```

A4 is not permitted to turn any derived decision, source projection, dashboard, or policy result into a competing source writer.

## 5. A2/A3 handoff baseline

### 5.1 A2 inputs available to A4

A2 defines the runtime context that A4 may consume:

- Authenticated principal type: `CUSTOMER`, `SUPPORT`, `OPERATOR`, `SERVICE`, or `PRIVILEGED`.
- Principal ID, optional canonical customer UUID, session ID, audience, roles, scopes, customer-access scope, assigned customer IDs, and assurance level.
- Authorization decision containing allowed/denied state, denial reason, resource type/ID, customer scope, action, required scopes/roles, and evaluation timestamp.
- Request, correlation, trace, and causation context as operational evidence, not customer or financial identity.
- Protected-route and data-exposure boundary from A2.

A4 must not copy credentials, tokens, password hashes, reset/recovery values, MFA proofs, device fingerprints, or privileged-action fingerprints. A4 must not issue or validate a principal in place of A2.

### 5.2 A3 inputs available to A4

A3 defines the customer/account evidence that A4 may consume:

- Canonical `Customer.id`.
- CustomerWallet ID, currency, lifecycle, ownership evidence, and source version.
- Binding ID, CustomerWallet ID, WalletAccount ID, LedgerAccount ID, binding state, currency, accounting unit, source customer version, source wallet version, and binding version.
- WalletAccount status/currency and exact `ledgerAccountId` relationship.
- LedgerAccount status, currency, accounting unit, account type, normal balance, negative-balance rule, and active state.
- A3 read/control states: `MISSING_BINDING`, `STALE_BINDING`, `PENDING`, `SUSPENDED`, `REPAIR_REQUIRED`, `CLOSED`, and `LEDGER_UNAVAILABLE`.
- A3 reconciliation discrepancy type, severity, owner, recovery state, and scope where a capability needs control evidence.

A3 explicitly does not provide policy eligibility or authorization. A4 must not infer a binding from `WalletAccount.customerId`, customer reference, wallet alias, payment reference, provider ID, or balance. A4 must not mutate A3 binding records or any Wallet/Ledger source.
